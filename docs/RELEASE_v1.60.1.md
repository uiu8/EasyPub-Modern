# EasyPub Modern v1.60.1

> 别名：duplicate-position　·　重点：**允许修改原文**，而且改得可撤销、可恢复
>
> 本次发布把 v1.60.0 与 v1.60.1 合并在一起 —— v1.60.0 只在本机构建过，没有对外发布。

上一版的结尾写着「下一版方向：允许修改原文」。这一版把它做完了，而且做得比原计划更保守：
原文确实可以被修改，但每一次修改都要先备份、装进一个可中断的事务、并且在中断之后能自动收尾。

跨度：`v1.59.0` → `v1.60.1`，**30 个提交**，Core 从 11.6k 行到 18.4k 行。

---

## 一、可以改原文了

### 一次修复，两种落地

修复方案本身只算一次。要不要落到文件上，是应用前的一个选择：

| | 只改章节树 | 同时改原文 |
|---|---|---|
| 章节树 | 改 | 改 |
| 原始 TXT | **不动** | **被重写** |
| 记录 | 无（没有文件改变） | 完整事务记录 + 备份 |

**同一个动作在两种模式下含义完全相同**，只是能不能落到文件上不同。重构之前这两种模式各有自己的代码路径，会互相漂移 —— 那是这一轮专门要消灭的东西。

### 改之前先备份，改的过程可以中断

写 TXT 走的是一个可中断的事务，顺序固定：

```
备份 → 渲染到临时文件 → 冻结「这次要做什么」→ 原子替换 → 重载 → 迁移内存模型 → 收尾
```

任何一步崩溃，下次打开发自动收尾。恢复规则里**只有一格**允许程序自己往前走（日志说「还没替换」且文件也证实没替换）——其余每一格，日志都在宣称一次文件没有显示的提交，那时**停下来交给人**，绝不猜。

**恢复永远不会第二次替换原文。** 文件里已经是商定的那一版时再替换一次，是唯一能毁掉「程序之外有人改过它」的动作。

### 改完之后章节树跟着走

原文行号变了，章节树、手工改过的标题、层级、目录勾选都得跟着搬到新行号上。迁移会**逐章报告谁能跟过来、谁不能**：

> 原文版本迁移已完成。 章节身份：保留 468 个，无失效

被改写的标题行会明确失配（那一行已经不是原来的文字，保住身份等于把两章悄悄融合）。删掉整章时相邻的两章**不会**被合并 —— 实测撞见过「第六章第七章吞掉第八章」，现在只有中间那些行确实是本次删掉的空行时才合并。

## 二、修什么由你勾

### 预览说改 69 行，就真的改 69 行

确认窗上显示的每一个数字，和接下来真正发生的事，来自**同一份编译产物**。这是这一轮重构的核心成果 —— 在此之前，预览与执行是两套计算，会各自漂移。

样书实测：默认勾选 117 / 191 个动作，预览说改 69 行，**逐行数出来正是 69 行**。

### 没有目录也能修

过去没有参考目录就完全没有方案。现在会退回「这本书自己能看出什么」：

- 重复标题（保留第一次出现的那一份）
- 数字标题写法不规范（`第1章` → `第一章`，纠正形式由标题自身推得）

样书实测：无目录时给出 32 个动作，全部默认勾选；改原文后 2502 行 → 2470 行，**正好是 32 行**被删，且删掉之后不再有任何标题多于一份。

**凡是要靠目录才能决定的（这一章是不是真的缺了、这个标题该不该采用、这一章是不是多余的）一律不做。** 从书自身猜这些就是凭空造章，规则是永远不造。

## 三、能改原文之后补上的四件事

| 能力 | 现在的样子 |
|---|---|
| **崩溃恢复入口** | 程序启动时会自动收尾上次没做完的原文修改；「原文备份」窗口也有「完成未完成的原文修改…」按钮，两者调的是同一个入口 |
| **快照带章节树** | 每次修复前的快照现在连当时的章节树一起存。以前只存字节，所以「恢复到当时的完整书稿状态」这个选项在界面上永远选不到 |
| **恢复此版本** | 「原文备份」窗口新增：选中一份快照 → 问你要「只恢复原文」还是「恢复原文与当时的章节树」→ 走和修复完全相同的事务路径（先给当前版本做备份，所以恢复本身还能再恢复回去） |
| **「原文已变化 · 刷新」走迁移** | 用记事本改了书稿某句正文再回工作台点刷新，**不再丢掉手工编排**，而是把树搬到新行号上，并点名说哪些章没能跟过来 |

## 四、修掉的两个缺陷

**重复正文的补丁会丢行。** 两版文本行尾约定不同时，推出的补丁会把「改一行」写成「删一行 + 插一行」，于是坐标表对那一行没有答案 —— 包含它的章节正文出现一个洞，那一章被判成「没有正文」并失去身份（实测：`第三章 转折 → LostNoBody`）。现在逐行配对成改写。

**从异步回调里开对话框会杀掉进程。** 工作台在 `async void` 的续体里给对话框设 Owner，而那时窗口可能已经关闭 —— 那里抛出的异常没有任何地方接得住，**应用直接消失**。这个缺陷在 v1.59.0 上同样存在。

---

## 五、重复正文对比现在告诉你哪一份在原位置

一本书里同一章出现在相隔几千行的两处、正文又几乎一样时，对比窗过去只并排显示两段正文让你选 —— 而**正文一样，你没有任何依据可选**。

现在它会说：

> 参考目录把这一章对在第 5234 行，也就是前一份。两处相隔 5380 行、正文相同，位置是唯一能分辨它们的东西。

目录认定的那一侧会标出「← 参考目录的位置」。没有目录、目录里没这一章、或者定位不出位置时，**如实说**，不猜。

**留哪一份仍然由你点** —— 这里只补上信息，没有改任何删除行为。

## 已知问题

- **不同卷里的合法重名章节可能被判为副本。** 无目录自修复只按标题文字分组，不看层级与分卷，所以「第一卷 第一章 缘起」与「第五卷 第一章 缘起」会被当成重复，而且默认勾选。只改章节树时会让成品少一章（可撤销、原文不变）；改原文还需要再勾一次「并从原文删除这一份」。**尚未实测复现**，但代码路径清楚，下一版优先处理。
- 恢复到「当时的完整书稿状态」之后，分层识别的开关与三个层级正则不在快照里，会回到全局设置。只影响「恢复之后又点了一次重新识别」，已恢复的树本身不受影响。
- 桌面端测试套件本身不稳定（`Application` 是进程级单例，由创建它的线程独占）。已知会随机出现若干失败，本版的验收按单类运行 + 样书探针进行，不是「全量绿」。
- 主窗口里有四处「代码活着但界面上到不了」的入口（详见仓库里的全貌文档第 3.3 节）。
