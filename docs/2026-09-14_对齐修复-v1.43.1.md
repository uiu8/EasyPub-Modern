# 一键修复为什么把章节树搞乱了：三处根因（v1.43.1）

用户截图里的树：`《疯巫妖的实验日志》正文` 下面挂着「新书《我怎么还活着》已经十万+」，
另一个顶层节点叫「那啥，新书疯骑士的宇宙时代，已发起点」，真正的「第一章」被埋在下面。
这不是显示问题，是三个真实缺陷叠在一起。

## 根因 1：定位器用"标题词相同"打败了"章号相同"

`ReferenceLocator` 给每个候选行打分，然后**按分数排序**取第一个在游标之后的。

`ReferenceOutline.PairScore` 的规则是：

| 情况 | 得分 |
| --- | --- |
| 章号相同 + 标题词相同 | ExactScore（最高） |
| **章号不同 + 标题词相同** | **WordsScore** |
| **章号相同 + 标题词部分相同** | **PartialScore（更低）** |

于是参考目录的 `第十六章 预谋`：

- 第 1002 行的 `第十六章 预谋（新）` → 章号对、词差一点 → PartialScore
- 第 23690 行的 `第二百五十七章 预谋` → 章号差 241、词完全一样 → **WordsScore，更高**

**定位器选了 23690 行**。实测证据：

```
修复前:  16  L1  23690  第十六章 预谋      ← 跳到全书 38% 的位置
        17  L1  27931  第十七章 真相和重逢
        18  L1  1181   第十八章 小红龙      ← 又跳回来
修复后:  16  L1  1002   第十六章 预谋
        17  L1  1103   第十七章 真相和重逢
        18  L1  1181   第十八章 小红龙      ← 行号单调递增
```

行号一旦乱跳，"按参考目录顺序重排"就会让正文互相跨越大段内容，整棵树看着就是乱的。

**修复**：在排序里加一个**章号一致**的首位键。相同章号的候选永远排在只有词相同的候选前面。
同时第三遍"全文子串搜索"也改成优先命中章号一致的行，而不是第一个包含该词的行。

## 根因 2：作者的推广段落被当成章节

源文件末尾（61735–61747 行）：

```
61735| 那啥，新书疯骑士的宇宙时代，已发起点      ← 没有全角缩进
61739| 合作新书地下城堡：前夜已上线
61743| 新书《我怎么还活着》已经十万+
61747| 巫妖后第一本西幻千面之龙已发书
```

正文段落都带 `　　` 缩进，这几行没有，而且上下都是空行——正好符合"孤立短行"的标题特征，
于是被识别成章节标题，再被塞进参考目录的顺序里。

**修复**：`ReferencePlanner.Apply` 里，**官方目录没有列出、且标题里没有章号**的行不再成为条目，
它们的内容自然并入前一章（正文范围本来就是"到下一行标题为止"）。
有章号的未列出章节（加更、番外）**照样保留**——如果目录不完整，那些不能丢。

## 根因 3：选源规则把书交给了最差的镜像

`RepairAsync` 原来的排序是"卷数最多优先"。实测那一轮的候选：

```
[和图书]                          卷 0  章 837
[偶书网 → biquge365]              卷 0  章 856
[偶书网 → biqusa]                 卷 1  章 851   ← 被选中
```

被选中的那个目录，**前五个"章节"全是作者的推广**：

```
C [-] 巫妖后第一本西幻千面之龙已发书
C [-] 新书《我怎么还活着》已经十万+
C [-] 合作新书地下城堡：前夜已上线
C [-] 那啥，新书疯骑士的宇宙时代，已发起点
C [-] 番外 第四章 简单任务:寻找走丢的母亲
```

它的卷名是 `《疯巫妖的实验日志》正文`——把书名和"正文"拼在一起，本身就说明这个源的结构不可信。
"卷数最多"这条规则恰好把它挑了出来。

**修复**：在完整度达标（≥ 最全者 90%）的候选里，**按用户配置的书源顺序取第一个**。
`DiscoverAsync` 已经按起点、番茄、和图书……的顺序返回，所以直接取第一个就是用户要的优先级。
选源结果：`参考 0卷/837章`（和图书），干净、从第一章开始。

## 顺带修掉的两个会崩/会误导的地方

- `catalogs.Max(...)` 在**空目录池**上会抛 `InvalidOperationException`。
  没有参考目录是正常情况（没有源收录这本书），这条路径以前会直接崩，现在如实报告。
- 起点对未登录的搜索返回**空 202 页面**。以前提示"站点结构特殊"或"没有这本书"，
  现在直接说：**起点对未登录的搜索返回空页面（反爬拦截），填 Cookie 后即可搜索。**

## 一键修复的进度窗口

以前点下去界面直接冻住几十秒，用户只能反复点。现在弹一个进度窗口，分阶段报告：
读取 TXT → 备份 → 按书源顺序搜索目录 → 逐章定位 → 重建章节树。
窗口在确认对话框出现之前关闭，两者不会叠在一起。

## 番茄搜索：为什么还是没攻克

用户要求先攻克番茄搜索，这里如实说明卡在哪：

- **目录页不需要签名**：`https://fanqienovel.com/page/<bookId>` 服务端渲染，实测《十日终焉》
  拿到 **10 卷 1496 章**，卷名真实。这一条已经接进产品（番茄源，"仅网址/编号"）。
- **搜索需要签名**：搜索页 `/search/<书名>` 是 SPA，数据走
  `api5-normal-sinfonlineb.fqnovel.com/reading/bookapi/search/page/v`。
  补全 `aid / channel / app_name / version_code / device_platform / device_id / iid / filter /
  page_count / page_index / query_type` 全部参数后，服务端仍返回
  `{"code":100103,"message":"PARAM_INVALID"}`——缺的是 `a_bogus`/`msToken` 这组字节风控签名，
  不是设备号。
- **无头浏览器也不行**：用系统 Edge 无头渲染 `/search/十日终焉`（真实 UA、禁用自动化特征、
  10 秒虚拟时间），页面渲染完成，正文渲染出 **"共 0 项相关的结果"**——风控识别了无头环境。

逆向 `a_bogus` 不在这个项目该做的范围内，而且对方一改版就会失效。
所以番茄目前的能力是：**粘贴书籍网址或编号即可读出完整分卷目录**（书名框里粘贴网址也能识别）。
