## 0. 一句概括

这一阶段唯一的硬性产出是：**建立一个完整可用的备份层，并且在任何写回能力出现之前，证明它从不改动书稿。**

「恢复备份」在 Phase 2 只是**导出副本**。把备份写回源文件本身就是一次源文件改动，需要事务、journal 与崩溃恢复（Phase 5）——一个恢复了一半的 TXT 配上一棵陈旧的章节树，比不恢复更糟。

## 1. 交付内容

### 1.1 Core：备份布局与浏览

| 文件 | 职责 |
|---|---|
| `SourceBackupLayout.cs` | 目录命名、路径解析、默认根 |
| `SourceBackupInventory.cs` | 列举、清单读写、导出、保留策略 |
| `SourceBackupStore.cs` | 扩建：接入新布局，保留全部旧 API 与旧备份可见性 |
| `AppSettingsStore.cs` | 新增 `SourceBackupRoot` / `SourceBackupRetentionLimit`，新增同步 `Load()` |

**目录形状**（每本书一个，文件夹名是源路径的哈希前 32 位）：

```
<备份根>/<源路径哈希>/
    manifest.json                 索引：源路径、首次原文校验值、快照数、保留数
    baseline/original.bak         首次准备修改此路径时看到的版本
    snapshots/<sha256>.bak        修复前快照，内容寻址，同内容不重复
```

**两条设计规则**

1. **文件是真相，清单只是索引。** 列举一律先扫文件夹再读清单；清单丢了或坏了，备份照样列得出来（有测试固定这一点）。看不见的备份等于没有备份。
2. **旧备份必须仍然可见。** 早期版本把 `.bak` 留在书稿旁边、把首次原文放在 `<哈希>/<文件名>.bak`。这两个位置继续被查找，且**新备份只在没有旧的情况下才写**——否则会用较晚的状态覆盖真正的首次原文。

### 1.2 Desktop：备份窗口

`SourceBackupWindow` 重写。上半是书籍列表（首次原文时间、快照数、最近备份、原文是否还在），下半是所选书籍的全部备份。

| 按钮 | 行为 |
|---|---|
| 更改备份位置… / 恢复默认位置 | 写入设置。**不移动已有备份**——未经询问就搬动用户可能正依赖的文件，是那种会丢数据的"贴心" |
| 导出为 TXT 副本… | 导出一份到用户选定路径；拒绝覆盖项目原文 |
| 导出所选书籍的全部备份… | 按时间顺序导出到所选文件夹，文件名带时间与校验值 |
| 打开备份位置 | 资源管理器中打开 |
| 按保留数清理… | 只删超出上限的**较早快照**，首次原文永不参与 |
| 将所选备份移入回收站… | 回收站，不是永久删除；选中首次原文时额外警告 |

窗口标题从「原文备份管理」改为「原文备份」；按钮从「恢复为 TXT 副本…」改为「导出为 TXT 副本…」——旧名字描述的一直是导出，只是名字没说清。

## 3. 本阶段修掉的两个缺陷

### 3.1 保留数被忽略（探针发现）

`EnsureSnapshot` 内部调 `Inventory()`，而 `Inventory` 用的是**默认的 20**，不是 store 上的设置——于是把保留数设成 3 完全不生效，快照会一直堆到 20 份。

这类"设置读了但没用"的错误不抛任何异常，只会让用户在磁盘上慢慢攒下几百份备份。修法：`SourceBackupInventory` 增加 `RetentionLimit`，由 store 注入。回归测试 `Automatic_pruning_honours_the_stores_own_retention_limit` 固定它（写 6 份、上限 3、断言剩下 3）。

> 这条正是"每个阶段都必须用样书实测"的直接收益：只跑单元测试看不出来，因为单元测试各自新建 store、各写一份。

### 3.2 清理顺序不是全序（写测试时发现）

保留策略按 `SavedAt` 排序取最新 N 份。文件系统时间戳的分辨率有限，同一批快照可能**时间戳相同**，此时"最新 N 份"每次都是不同的集合——一次清理可能删掉它刚刚保留的那份。

修法：并列时按路径做次级排序，使顺序成为全序。回归测试 `Pruning_is_stable_when_timestamps_tie` 固定它。

## 4. 一个必须先讲清的测试基础设施问题

**`EasyPub.Desktop.Tests` 本身不稳定，且失败会级联。**

实测（回滚到纯 Phase 1 提交状态，连跑两次）：

| 次 | 结果 |
|---|---|
| 1 | 失败 1 / 通过 134 / 135 |
| 2 | 失败 4 / 通过 131 / 135 |

在同一份**未改动**的代码上，两次结果不同。失败时间常常只有 1–20ms，是构造期就抛，不是断言不成立。

**根因**：`Application` 是进程级单例，只能属于创建它的线程。套件里每个测试各自开一条 STA 线程，谁先建 `Application` 谁独占，线程一结束它就属于一条死线程。此后：

- 任何调用 `Application.Current.Windows` 的测试抛跨线程异常；
- 任何需要 `Application.LoadComponent` 加载资源的窗口抛「应用程序对象正在关闭」；
- 而 `MainWindowLayoutTests` 有五十多个测试共用同一个窗口——它们会**一起**倒。

所以「135/135 全绿」与「90 个失败」都可能在同一个 commit 上出现，取决于哪个测试先跑。

**已经排除的**：这不是 Phase 2 引入的（纯 Phase 1 状态同样失败），也不是 `RepairCandidate`/`RepairReviewWindow` 改动引入的（单独跑全过）。

**一次失败的尝试**：曾引入 `WpfTestHost`，把 `Application` 建在一条永不结束的专用 STA 线程上。方向是对的（所有权固定），但遗漏了一点——测试里创建的裸 `Application` 没有 `App.InitializeComponent()`，**没有加载 `App.xaml` 的资源与资源包**，于是 `ChapterEditorWindow.InitializeComponent()` 直接崩。结果是把偶发 1 个失败变成稳定的 90 个。已回滚。

**已确认的具体规则**（本轮踩过两次，记下来免得再踩）：

> `dotnet test` 的 `--filter` 必须放在 `--` **之前**。放在后面会被当成 xUnit 的参数，测试照跑全量，而输出看起来"正常"。

**本阶段的应对**：验收改用**单文件/单类跑**加**独立探针**，两者都稳定：

```powershell
# Core：稳定
dotnet test tests\EasyPub.Core.Tests\EasyPub.Core.Tests.csproj -c Release

# Desktop：只跑自己关心的
dotnet test tests\EasyPub.Desktop.Tests\EasyPub.Desktop.Tests.csproj -c Release -m:1 `
  --filter "FullyQualifiedName~SampleBook" -- xUnit.MaxParallelThreads=1
```

**建议**：把「修好 Desktop 测试宿主」当作一项独立工作排进去（需要让 `Application` 与 `App` 资源在整个运行期间存活于同一条线程，并把所有自建 STA 线程的测试迁到它上面）。在它修好之前，**不能**用「Desktop 全量绿」作为任何阶段的验收依据。

## 6. 下一阶段的前置

1. `SourceBackupInventory.JournalFolderName`（现为 `"journal"`）与 Phase 5 的 journal 目录名必须一致——目前已经对齐，但两边都只是常量，没有互相引用。
2. `BackupSnapshotRef`（v3.3 §8.2）需要 `SnapshotId` / `RelativePath` / `ContentSha256`。当前快照路径已经是内容寻址，`RelativePath` 可直接由 `SourceBackupLayout.SnapshotPath` 给出，`SnapshotId` 待定。
