## 0.1 本版相对 v1 的六项修正（v2 指出，全部采纳）

1. **不把可变编辑层挂进 `ChapterTreeDocument`。** 它保持「某一固定 TXT 字节版本的不可变解析快照」；原文编辑由独立 `SourcePatch` + `SourceEditSession` 管理。
2. **计划绑定三类版本。** `BaseSourceSha256 + BaseTreeFingerprint + RecognitionFingerprint` 任一变化即失效，禁止旧计划套新树或新规则。
3. **`InsertHeading` 提为一级动作。** 「把现有一行解释为标题」与「原文没有标题、需要新增一行」是两种动作，前者不得被用来隐式推导后者。
4. **冲突在预览阶段失败，不靠操作次序吞掉。** 「先删 → 再改 → 最后插」只是执行期的可读性安排，不是正确性机制。
5. **`TreePatch` 与 `SourcePatch` 分离。** 树语义变化与物理文本变化不是一一对应，不能用同一组行操作表达。
6. **版本迁移统一走 `SourceVersionTransition`。** 缓存、undo/redo、确认组、断点、项目计划、目录存档一并处理，而非各模块各自补逻辑。

## 0.2 本版对 v2 的两处保留与一处修正

**保留一：`RepairPlan` 暂不统一两种依据的计划类型。**

v2 要求 `ReferencePlanner` 与 `LocalRepairPlanner` 产出同一种 `RepairPlan`。两者的证据形态本就不同（目录给的是「这一章应该存在、叫什么」，本地给的是「章号跳了」「标题重复」），强行统一会产生大量 adapter，收益仅是「UI 少一个分支」。

> v3 做法：**共用确认窗与共用执行器先行，计划类型保持两种**，各自产出 `RepairCandidate`；等两边动作真正收敛后再合并类型。v2 §25 自己承认「允许 adapter 过渡」，即承认统一不是免费的。

**保留二：不一次拆 17 个文件。**

v2 §25 的文件清单会把工作量从 2–3 天推到 1–2 周，而当前系统刚把 41 处错绑修到 0、刚建立可信度。v3 按「能跑起来」优先排序，只引入必要类型。

**修正：v2 §7 的映射表与其 §3.2 的「两维不可互相污染」自相矛盾。**

v2 §7 让 `RemoveDuplicate` / `DemoteHeading` 在不同落地模式下有不同物理行为，等于让「落地模式」反向决定「动作做什么」。

> v3 做法：**动作语义固定，每个动作编译出 `TreePatch` 与可选的 `SourcePatch` 两套产物**，落地模式只决定「用哪套」。详见 §6。

## 1. 问题定义

### 1.1 现状

同一对话框内混了三条依据不同的链路，且目录修复有两条互不相干的执行链：

```
目录辅助修复（获取、核对、补建）
├─ 一、获取目录          自动获取（联网多书源）        ┐
├─ 一、手动              粘贴 / 导入目录 TXT          ├─ 有依据
└─ 没有参考目录时         本地扫描 + 检测并预览补建      ┘  ← 无依据，却与上面同屏
```

| 界面元素 | 代码链路 | 建计划 | 应用 |
|---|---|---|---|
| 目录面板「预览章节调整…」 | `ReferenceOutlineAssist` | `ReferencePlanner.Build` | 自建表 + 自建勾选 |
| 工作台「预览目录修复」 | `ChapterAutoRepair.RepairAsync` | `ReferencePlanner.Build` 再算一遍 | `RepairReviewWindow` + `RebuildWithSelection` |

**同一个 `Build` 被两套 UI 各自调用、各自渲染、各自应用**，因此对同一棵树、同一份目录会给出不同结果。已发生的实例：新增 `AdoptHeading` / `MissingBody` 时只更新了后者，前者把新动作类型显示成「说明」，汇总数字也对不上。

### 1.2 不改原文造成的间接性

现行模型是纯引用：章节树条目只记 `TitleLineNumber` + `ContentRanges`。删除重复章 = 从树里移除条目，原文那些行仍在、只是不进成品。这带来一批间接处理：

| 需求 | 引用模型下的做法 | 代价 |
|---|---|---|
| 删重复章 | 只移除树中条目 | `RemovedDuplicate` + 移除清单 + 行守恒校验 |
| 补标题（原文无该行） | 只能在已存在的行上立标题 | 找不到行时只能报「正文缺失」 |
| 改标题 | 只改树 | 成品与原文不一致 |
| 顺序错乱 | 只能报告 | 「顺序异常 31 处」无出口 |
| 定位 | 文本重复导致按章号抓错行 | 曾出现 41 处错绑 |

### 1.3 样书所需的文本操作（本地推演）

| 缺陷 | 操作 | 数量 |
|---|---|---|
| 第一卷 30–40 整章重复（150–255 行） | 删行 | 55 |
| 第二卷 20–40 副本错位（663–767 行） | 删行 | 105 |
| 第三卷 40–60 原文本就没有 | 无操作（不补造正文） | — |
| 第四卷 30–40 标题行不存在（1117–1149） | **插行** | 11 |
| 第四卷 50–60 标题正文全缺 | 无操作 | — |
| 第五卷 101–120 三种写法 | 改行 | ~7 |
| 第六卷 每章双标题行 | 删行 | 100 |

合计：**删 260、改 7、插 11**。绝大多数是删除；唯一需要插入的是第四卷 30–40——也正是引用模型下唯一修不好的一类。

## 2. 设计目标与非目标

### 2.1 目标

1. 一份修复意图，两种落地；计划只算一次，选择只记一次。
2. 依据明确：每个动作都知道来自参考目录、本地规则还是人工决定，并由 UI 直接显示而非反推。
3. 章节树语义与物理文本编辑解耦：不为了统一代码而强迫两种落地执行相同物理操作。
4. 原文写回可审计：每个物理改动有来源、旧值、目标值与前置条件。
5. 原文写回可恢复：事务任意阶段崩溃都能判断「继续 / 回滚 / 等待人工」。
6. 现有安全机制不被绕过：`RepairIntegrity`、`SourceBackupStore`、源 SHA 校验、外部修改检测。
7. 计划过期可检测：源文件、章节树或识别规则变化后，旧计划不得继续应用。
8. 二次执行幂等：同一修复成功后重新预览，不再产生已完成动作。

### 2.2 非目标（第一期）

- 自动补造真正缺失的正文
- 任意正文块搬移或跨章节重排
- 多用户协同编辑
- EPUB 原文写回
- 自动解决所有顺序异常
- 无证据情况下猜测章节边界

## 3. 总体架构

### 3.1 主干

```text
SourceSnapshot + ChapterTree + RecognitionSettings
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
ReferencePlanner        LocalRepairPlanner        ← 分叉 A：依据
（有目录）                （无目录）
     └───────────┬───────────┘
                 ▼
        IReadOnlyList<RepairCandidate>
                 │
        RepairReviewWindow（唯一确认窗）
                 │
             Selection
                 │
        RepairPlanCompiler
          ┌──────┴──────┐
          ▼             ▼
      TreePatch    SourcePatch?
          │             │
   TreeOnlyExecutor  SourceEditTransaction   ← 分叉 B：落地
          └──────┬──────┘
                 ▼
        CanonicalRepairResult
                 │
   RepairIntegrity + SourceCommitVerifier
                 │
        Persist / SourceVersionTransition
```

### 3.2 两个正交维度

**依据维度**只决定候选从哪里来：
- `ReferencePlanner`：目录定位、目录标题、卷信息
- `LocalRepairPlanner`：跳章、重复标题、疑似未识别标题、编号错误

**落地维度**只决定已确认的意图如何执行：
- `TreeOnly`：TXT 不变，只改章节树与成品语义
- `EditSource`：先写 TXT，再把同一意图物化到新源版本的章节树

两维不可互相污染：`EditSource` 不重新决定哪些动作正确；`LocalRepairPlanner` 不决定是否写文件。**动作语义在编译前已固定**（见 §6）。

### 3.3 四层边界

```text
RepairCandidate / RepairAction   决定「为什么改、想改成什么」
TreePatch                        决定「章节语义怎么变」
SourcePatch                      决定「TXT 的物理文本怎么变」
SourceEditTransaction            决定「如何安全提交并迁移整个应用状态」
```

四层分开后：`RepairIntegrity` 继续只负责章节语义与 coverage；`SourceBackupStore` 继续负责版本快照；`ChapterTreeDocument` 保持不可变；新增的事务层只处理原文写回与跨版本迁移。

## 4. 核心数据模型

### 4.1 计划与版本绑定

```csharp
public sealed record RepairBaseVersion(
    string BaseSourceSha256,
    string BaseTreeFingerprint,
    string RecognitionFingerprint);

public sealed record RepairCandidate(
    string Id,
    RepairPlanBasis Basis,
    RepairBaseVersion BaseVersion,
    IReadOnlyList<RepairAction> Actions);

public enum RepairPlanBasis { ReferenceCatalog, LocalHeuristic, Mixed }
```

### 4.2 动作

```csharp
public enum RepairActionKind
{
    AddChapter,          // 原文已有标题行，树未收录
    AdoptHeading,        // 原文已有一行，决定把该行解释为标题
    InsertHeading,       // 原文没有标题行，需要新增一行
    RetitleChapter,      // 已有标题改为确认后的标题
    RemoveDuplicate,     // 重复副本：排除（TreeOnly）/ 物理删除（EditSource，需明确确认）
    DemoteHeading,       // 取消章节边界，文字留在正文
    KeepExtra,           // 保留目录外章节
    BuildVolumeLevel,    // 仅树结构
    MissingBody,         // 事实性发现，不可执行
    OutOfOrderFinding    // 事实性发现，不可执行
}

public sealed record RepairEvidence(
    RepairEvidenceKind Kind,
    string Description,
    string? Source,
    double? Confidence = null);

public enum RepairEvidenceKind
{
    ReferenceCatalog, LocalNumberSequence, LocalTitleShape, DuplicateContent, UserDecision
}
```

**每条动作携带证据**，UI 不根据文字反推依据。

### 4.3 版本指纹

`BaseSourceSha256` **不足以**描述计划有效性：同一份 TXT（字节完全相同）可以被用户手工改成完全不同的章节树。因此：

**TreeFingerprint**：对以下字段规范化序列化后取 SHA-256

```
Title, Level, HeadingLevel, IncludeInToc, IsFrontMatter,
TitleLineNumber, ContentRanges, RecognitionSource
```

`Entry.Id` **不参与**——纯重建产生的 GUID 变化不应使计划无意义失效。

**RecognitionFingerprint**：覆盖所有可能改变识别/定位结果的规则

```
普通章节正则、层级开关与 L1/L2/L3 正则、数字章节开关、
数字章节最小正文行数、数字章节正则、编号纠错表、本书级覆盖设置
```

**应用前校验**：

```csharp
RepairPlanValidator.ValidateCurrent(plan.BaseVersion, currentDocument, currentEntries, currentRecognition);
```

任一不一致 →

> 当前书稿、章节树或识别规则已变化。本次预览已经过期，请重新生成修复方案。

不允许「尽量继续套用」。

## 5. TreePatch 与 SourcePatch

### 5.1 TreePatch

```csharp
public sealed record TreePatch(
    string CandidateId,
    IReadOnlyList<TreeMutation> Mutations,
    CanonicalChapterModel ExpectedResult);

// TreeMutation: InsertEntry | RetitleEntry | RemoveEntry
//             | ReassignBodyRanges | ChangeLevel
//             | InsertVirtualHeading | BuildVolumeNode
```

### 5.2 SourcePatch

```csharp
public sealed record SourcePatch(
    string CandidateId,
    string BaseSourceSha256,
    IReadOnlyList<SourceOperation> Operations);

// 一期只允许三种物理操作：
//   DeleteOriginalLine | ReplaceOriginalLine | InsertLineAtAnchor
// 不允许物理「移动正文块」。
```

**每个操作必须带前置条件**：

```csharp
public sealed record ReplaceOriginalLine(
    string OperationId, int Line, string ExpectedOldText, string NewText,
    string ActionId, RepairEvidence Evidence);

public sealed record DeleteOriginalLine(
    string OperationId, int Line, string ExpectedOldText,
    string ActionId, RepairEvidence Evidence);
```

即使定位出错，也不会在「第 1889 行已经不是原来的内容」时静默覆盖。

### 5.3 插入锚点

单纯 `OriginalLine` 无法标识多个插入行：

```csharp
public sealed record SourceAnchor(int OriginalLine, AnchorPlacement Placement, int Ordinal = 0);
public enum AnchorPlacement { Before, After, EndOfFile }
```

同一锚点的多个插入由 `Ordinal` 保证稳定顺序。

## 6. 动作到两种落地的编译规则

**动作语义固定，两种落地各自编译出产物**——这是 v3 对 v2 §7 的修正。

| RepairAction | TreePatch（恒有） | SourcePatch（`EditSource` 时可有） |
|---|---|---|
| `AddChapter` | 在已有源行建立章节项 | **空**：标题已在原文中 |
| `AdoptHeading` | 把该行解释为标题边界；必要时规范化行文本 | 仅当需要规范化文本时产生 `ReplaceOriginalLine` |
| `InsertHeading` | 建立条目（`TreeOnly` 下 `TitleLineNumber = null`，正文按锚点切分） | `InsertLineAtAnchor` 插入真实标题行 |
| `RetitleChapter` | 改树标题 | `ReplaceOriginalLine` 替换标题原文 |
| `RemoveDuplicate` | 从语义中排除副本 | **仅在用户显式确认「从 TXT 删除」时**产生 `DeleteOriginalLine`；证据不足则该项在 `EditSource` 下退回 `TreeOnly` 行为并在界面标明 |
| `DemoteHeading` | 移除章节边界，文字并回正文 | **空**：不删除标题行，只让新树不把它当标题 |
| `KeepExtra` | 无改动 | 空 |
| `BuildVolumeLevel` | 建卷节点、调整 `Level` | **空**：不写 TXT |
| `MissingBody` | 只报告 | 无 |
| `OutOfOrderFinding` | 只报告（一期） | 无 |

**`RemoveDuplicate` 的二级决策必须在确认窗显式呈现**：

> 该项将从原 TXT 中删除 55 行，而不仅是从章节树排除。

### 6.1 规范化与冲突检测（写盘/预览前必经）

`SourcePatchNormalizer` 执行：

1. `Delete ∩ Replace == ∅`
2. 同一原始行最多一个 `Replace`
3. 同一原始行最多一个 `Delete`
4. 插入按 `(Anchor, Placement, Ordinal, OperationId)` 确定稳定顺序
5. 每个 `Delete/Replace` 的 `ExpectedOldText` 与 base snapshot 完全一致
6. 所有行号在合法范围内
7. 不允许一个动作依赖已被另一动作删除的证据行，除非计划明确声明依赖
8. 不允许不同 `RepairAction` 生成互相矛盾的物理操作

**冲突必须在预览阶段失败并要求重新生成计划**，不得靠执行期次序吞掉。

### 6.2 执行期次序（仅可读性）

```
1. 删除（样书 260 行）
2. 替换（样书 7 行）
3. 插入（样书 11 行）
```

次序不影响正确性（`SourcePatch` 以原始行号索引、一次渲染），只让变更清单更易读。

**新增硬规则**：`InsertHeading` 的锚点行不得落在 `DeleteOriginalLine` 的行集合内。否则会出现「先删副本、再往同一位置插标题」的自相矛盾（第三卷 40–60 与第二卷副本重叠区正是这种形状）。

## 7. CanonicalChapterModel：两种模式真正比较的对象

`EditSource` 会删除与插入行，压实后所有后续物理行号变化；`TreeOnly` 不会。因此最终树的 `TitleLineNumber` / `ContentRanges` **不可能**逐字段相等。

```csharp
public sealed record CanonicalChapter(
    string Title,
    int Level,
    bool IncludeInToc,
    CanonicalHeadingOrigin HeadingOrigin,
    IReadOnlyList<string> BodyContentHashes);
```

比较时忽略物理行号，关注章节顺序、标题、层级、是否进目录、每章正文内容集合与顺序、被明确删除的正文是否一致：

```text
Canonical(TreeOnlyResult) == Canonical(EditSourceResult)
```

> **这取代 v1 的「两个模式使用同一物理行集合」不变量。** v1 那条不成立：`DemoteHeading` 与 `RemoveDuplicate` 的物理操作在两模式下本就可以不同。

## 8. SourceEditSession：预览层，不污染 `ChapterTreeDocument`

### 8.1 `ChapterTreeDocument` 保持现状语义

> 某一固定 TXT 字节版本的不可变解析快照。

`SourceSha256`、`SourceLines`、`Entries` 必须始终指向同一源版本。

**不新增**：mutable edits、virtual current lines、pending patch。
**可新增**：只读 fingerprint helper。

### 8.2 新类型

```csharp
public sealed class SourceEditSession
{
    public ChapterTreeDocument BaseDocument { get; }
    public SourcePatch Patch { get; }

    public IReadOnlyList<SourceLineView> PreviewLines();
    public SourcePatchValidation Validate();
    public Task<SourceCommitPreview> PrepareCommitAsync(CancellationToken token = default);
}
```

它**不修改** `BaseDocument`。

### 8.3 预览行身份

```csharp
public sealed record SourceLineView(SourceLineIdentity Identity, string Text, SourceLineOrigin Origin);

public abstract record SourceLineIdentity;
public sealed record OriginalLineIdentity(int Line) : SourceLineIdentity;
public sealed record InsertedLineIdentity(string OperationId) : SourceLineIdentity;
```

多个插入行不共用伪 `OriginalLine`。

## 9. 写回编码与换行策略

### 9.1 不保存单一 `_newLine`

要做到「未修改部分不被重新格式化」，源文件读取需拆成：

- 原始 bytes
- Encoding
- BOM / Preamble
- 每行文本
- **每行之后的换行符类型**：`CRLF / LF / CR / EOF`

插入行使用「附近主导换行符」；文件仅一行或无换行时用检测出的默认换行符。

### 9.2 写回前空操作 round-trip 检查

首次允许 `EditSource` 前，**在内存中**执行：

```text
Decode(originalBytes) → Render(no-op patch) → 比较 bytes
```

若 no-op 都无法字节等价，则禁用原文写回：

> 当前 TXT 的编码或换行结构无法被安全无损重写。本次仍可使用「不改原文」模式。

**不得**通过「先写一次再比较」验证。

### 9.3 编码测试矩阵

`UTF-8 无 BOM` / `UTF-8 BOM` / `UTF-16 LE` / `UTF-16 BE` / `UTF-32 LE` / `UTF-32 BE` / `GBK` / `CRLF` / `LF` / `CR` / 混合换行 / 有尾换行 / 无尾换行 / 空文件 / 单行文件

## 10. SourceEditTransaction

### 10.1 职责

验证计划版本 → 规范化 `SourcePatch` → 读取并锁定当前源版本 → 创建备份 → 创建 journal → 写同目录 temp → 计算 expected new SHA → 替换源文件 → 重载新 `ChapterTreeDocument` → 把同一意图物化到新树 → `SourceVersionTransition` → 持久化项目状态 → 标记事务完成。

### 10.2 状态机

```csharp
public enum SourceTransactionState
{
    Prepared, BackupCreated, TempWritten, SourceReplaced,
    DocumentReloaded, StateMigrated, Committed, Conflict, RolledBack
}
```

### 10.3 提交流程

```text
A. ValidateCurrentVersion          （三 fingerprint）
B. NormalizeAndValidatePatch
C. CreateBackupSnapshot
D. journal: Prepared / BackupCreated
E. Render temp（原编码 / 原换行 / 原 BOM）
F. flush temp；计算 ExpectedNewSha
G. journal: TempWritten(ExpectedNewSha)
H. 再次验证当前源仍等于 BaseSha
I. Replace source
J. journal: SourceReplaced
K. LoadAsync 新源
L. journal: DocumentReloaded
M. 在新源版本上物化目标树
N. SourceVersionTransition
O. 持久化 project / catalog / recovery 状态
P. journal: StateMigrated
Q. journal: Committed
R. 清理 temp；保留审计 receipt
```

### 10.4 TOCTOU

- 应用级同一路径 mutation lock，阻止 EasyPub 自身并发写
- temp 写完、替换前重新计算目标文件 SHA
- 不等于 `BaseSha` 时停止替换
- 替换失败不继续迁移任何状态

第一期**不声称**跨进程绝对并发保证，只保证检测到可见版本冲突时停止写入。

## 11. Journal 与崩溃恢复

### 11.1 结构

每事务一个目录：

```text
<book>/.easypub/journal/<transaction-id>/
    transaction.json      # schemaVersion, transactionId, sourcePath, candidateId,
                          # baseSourceSha256, expectedNewSha256,
                          # baseTreeFingerprint, recognitionFingerprint,
                          # state, createdAt, updatedAt
    source-patch.json
    receipt-draft.json
```

状态更新用 temp + replace，避免 journal 自身半写。

### 11.2 恢复规则

| Journal 状态 | 当前文件 SHA | 动作 |
|---|---|---|
| `Prepared` / `BackupCreated` / `TempWritten` | `BaseSha` | 可安全继续或放弃 |
| `SourceReplaced` / `DocumentReloaded` | `ExpectedNewSha` | **禁止重新应用 `SourcePatch`**，只继续重载与状态迁移 |
| 任意未完成状态 | 既非 Base 也非 Expected | 标记 `Conflict`，停止自动恢复 |
| `StateMigrated` | `ExpectedNewSha` | 完成最终持久化检查并标记 `Committed` |
| `Committed` | `ExpectedNewSha` | 清理残留 temp/journal，保留摘要 |

**这避免最危险的情况**：源文件已成功替换，重启后又把同一个删除/插入 patch 执行第二次。

### 11.3 撤销的两种含义

- **提交前撤销**：丢弃 Selection / `SourcePatch`
- **提交后撤销**：从备份恢复旧源版本 + 一次反向 `SourceVersionTransition`

journal 不承担长期 undo 历史；事务完成后可清理，但**必须保留 backup 与 receipt**。

## 12. 备份设计

### 12.1 保留现有安全属性

`SourceBackupStore` 已具备：按完整源路径隔离、首次备份、基于内容 SHA 的 snapshot、写 snapshot 前验证 document SHA。**不删除这些属性。**

### 12.2 目录结构

```text
<书稿目录>/.easypub/backup/<原文件名>/
    manifest.json
    baseline/<sha256>.bak
    snapshots/<sha256>.bak
    receipts/<timestamp>-<transaction-id>.json
    receipts/<timestamp>-<transaction-id>.txt
```

`baseline` 语义为：

> EasyPub 第一次准备修改此路径时看到的版本。

**界面不得称其为「绝对原稿」**——用户可能在首次使用本工具之前就已改过该文件。

### 12.3 保留策略

- `baseline` 永久保留，除非用户主动删除
- `snapshots` 默认保留最近 20 个不同 SHA
- 相同 SHA 不重复保存
- 删除旧 snapshot 前确认无未完成 journal 引用
- 恢复 snapshot 前先 snapshot 当前版本
- 源目录不可写时回退到 `%LOCALAPPDATA%`，但 **UI 必须显示实际备份位置**

## 13. SourceVersionTransition

源 SHA 改变后统一走迁移对象，而非各模块各自补逻辑。

```csharp
public sealed record SourceVersionTransition(
    string SourcePath, string OldSha256, string NewSha256,
    SourceCoordinateMap CoordinateMap, string CandidateId, string TransactionId);
```

| 状态 | 处理 |
|---|---|
| `ChapterTreeDocument` | 丢弃旧实例，重新 `LoadAsync` |
| `ChapterTreeDocumentCache` | `Invalidate(sourcePath)` 全部变体 |
| Undo / Redo | 清空（旧行号历史不得进入新版本） |
| ConfirmedReviews | 清空或按新 fingerprint 重新确认，不直接继承 |
| Review breakpoints | 清空 |
| 旧 `ChapterTreePlan` | 不再套用；生成绑定 NewSha 的新计划 |
| `ReferenceCatalogInput` | 目录复制到 NewSha，**不删除旧 SHA 下的目录** |
| 项目恢复快照 | 保存新 `ChapterTreePlan` 与 NewSha |
| 工作台 `_sourceChanged` | 重载成功后归零 |
| UI 选择 | 按语义 ID 重新定位，不按旧物理行号恢复 |

### 13.1 目录迁移

目录不由源字节定义，源文本因安全修复改变后不应丢失已确认目录：

```text
oldCatalog = Load(OldSha)
if oldCatalog exists and transaction is same-book edit:
    Save(NewSha, oldCatalog)
```

## 14. SourceCoordinateMap

```csharp
public sealed record SourceCoordinateMap(
    IReadOnlyDictionary<int, int?> OriginalToNew,
    IReadOnlyDictionary<string, int> InsertedOperationToNewLine);
```

- 被删原始行 → `null`
- 未删原始行 → 新物理行号
- 新插入行 → 按 `OperationId` 得新行号

`TreePatch` 在 `EditSource` 下通过此映射物化到新 `ChapterTreeDocument`，**无需让旧 document 同时理解两套行号**。

## 15. 验证器的分工

### 15.1 `RepairIntegrity` 保持 Tree 层职责（不替换）

继续负责：描述章节树语义变化、区分 `ReassignedBody / Reordered / ChangedLevel / RemovedLines`、验证修复前后 coverage 守恒、保存被移除行清单。

### 15.2 新增 Source 层验证器

**`SourcePatchIntegrity`**：操作无冲突、`ExpectedOldText` 一致、操作来源可追溯、插入顺序稳定。

**`SourceCommitVerifier`**：temp 渲染 diff 与 patch 一致、未涉及原始行内容保持一致、新 SHA 与事务记录一致、receipt 与实际 diff 一致。

**不要让 `RepairIntegrity` 同时承担物理文件 diff**——否则它会从「章节语义验证器」变成职责混杂的超级类。

## 16. 安全边界：强制禁用 `EditSource` 的情形

1. `BaseSourceSha` 校验失败
2. `TreeFingerprint` 或 `RecognitionFingerprint` 过期
3. no-op 字节 round-trip 失败
4. `SourcePatch` 有冲突
5. 动作会触及无法可靠映射的手工结构
6. 源目录与备份目录都不可写
7. 存在未恢复的冲突 journal
8. 当前 SHA 既非 `BaseSha` 也非 `ExpectedNewSha`

以上情形**仍允许 `TreeOnly`**。

### 16.1 关于 `manual` 条目

**不再一刀切**。按动作影响范围判断，并加一条硬规则：

> `manual` 条目所在行区间，以及其**前后各一行**，禁止任何 `SourcePatch` 触碰。

理由：手工编辑的典型后果是「把原相邻两行拆开或合并」，其边界本身不可靠，只保护条目所在行不够。

## 18. 变更清单与审计 receipt

每次成功事务生成两份 receipt（JSON + 人类可读 TXT），**由实际提交结果生成**，不复制 preview。

### 18.1 JSON

```text
源文件：D:\...\缺陷样书.txt
原 SHA-256：...
新 SHA-256：...
依据：参考目录《...》
统计：删除 260 行、替换 7 行、插入 11 行

[删除]
原第205行  第三十章 ...
原因：目录只保留一份；正文内容与保留副本一致

[替换]
原第1889行
旧：第一百零久章 ...
新：第一百零九章 ...
原因：本书编号纠错表 久→九；参考目录章号为 109

[插入]
```

**`原因` 字段是必需的**：让用户能逐条判断程序为什么改，尤其「久→九」这类改写用户原文用字的操作。

## 19. 测试策略

### 19.1 Characterization tests 先行（Phase 0）

在任何架构拆分前冻结 `main` 当前行为：

- `ReferencePlanner.Build` 典型动作分类
- `ReferencePlanner.Apply` 对手工条目的保护
- `RepairIntegrity.Verify` coverage 守恒
- `RepairReviewWindow` 默认 selection
- `ChapterAutoRepair.RebuildWithSelection` 与 preview 一致
- `SourceBackupStore.EnsureSnapshot` 外部修改检测

**退出条件**：重构前行为可由自动测试复现。

### 19.2 计划与版本

同一 snapshot + tree + rules → 相同计划；三类 fingerprint 各自变化 → 计划失效；`InsertHeading` 必带 anchor；不可执行 finding 不产生 patch。

### 19.3 `TreePatch`

覆盖每个动作 + `manual` 条目保护 + virtual heading 行为 + `BuildVolumeLevel`。继续用 `RepairIntegrity.Verify`。

### 19.4 `SourcePatch`

单独行为、多插入同锚点稳定排序、`Delete + Replace` 同行冲突、错误 `ExpectedOldText` 拒绝、锚点越界拒绝、证据行依赖冲突、no-op 字节 round-trip。

### 19.5 事务故障注入

在 `Prepared` / `BackupCreated` / `TempWritten` / `SourceReplaced` / `DocumentReloaded` / `StateMigrated` 各阶段模拟崩溃，重启后验证：patch 不重复执行、SHA 能正确识别事务位置、元数据能继续迁移、外部修改时进入 `Conflict`。

### 19.6 端到端等价

```text
Canonical(ExecuteTreeOnly(plan, selection)) == Canonical(ExecuteSource(plan, selection))
```

### 19.7 Source diff 不变量

成功提交必须同时满足：

1. preview patch == 实际提交 patch
2. receipt patch == 实际文件 diff
3. 未被 patch 涉及的原始行文本保持不变
4. 每个 `Replace/Delete` 的旧内容满足预条件
5. 新文件 SHA == `transaction.ExpectedNewSha`
6. reload 后可通过 `ChapterTreeDocument.LoadAsync`
7. 新 `ChapterTreePlan.SourceSha256` == NewSha
8. 第二次运行同一修复入口不再产生已完成动作

### 19.8 样书验收

| 样书缺陷 | 期望 |
|---|---|
| 第一卷重复块 | 删除范围准确（55 行） |
| 第二卷副本错位 | 只删除确认副本（105 行） |
| 第三卷真实缺正文 | 只报告，不生成 `SourcePatch` |
| 第四卷 30–40 | 产生 11 个 `InsertHeading` |
| 第四卷 50–60 | 仍只报告缺正文 |
| 第五卷错误标题 | 只替换确认行（~7 行） |
| 第六卷双标题 | 只删除确认的重复标题（100 行） |
| 两模式对照 | `Canonical` 一致 |

## 20. 实施阶段

### Phase 0：冻结现状
补 characterization tests；固定六卷样书为回归 fixture；记录性能基线。
**退出**：重构前行为可由自动测试复现。

### Phase 1：删大表、合并链路（不写原文）
删除 `ChapterCatalogPanel` 的独立 apply 链；所有目录修复统一进入 `RepairReviewWindow`。
**退出**：原文仍完全不改，双链路消失，功能回归通过。
> **这一步可立即做，与后续架构无关。**

### Phase 2：备份层 + 设置骨架
用户可见备份夹、去重、保留策略、恢复入口、`manifest`；设置里三种模式。
**退出**：任何写回能力出现之前，备份机制已完整可用。

### Phase 3：计划版本绑定
`RepairBaseVersion` + `TreeFingerprint` + `RecognitionFingerprint` + `RepairPlanValidator`；确认窗显示版本状态并在过期时禁用应用。
**退出**：三类 fingerprint 变化都能正确拒绝旧计划。

### Phase 4：纯函数 `SourcePatch`（不写盘）
操作类型、anchor、normalizer、无损 decoder/renderer、内存 preview、source diff UI 接入确认窗。
**退出**：任一 patch 可在内存中得到稳定、可验证的预期 bytes 与 diff。

### Phase 5：`SourceEditTransaction`
扩展 `SourceBackupStore`、journal 状态机、同目录 temp + replace、crash recovery、`SourceCoordinateMap`、`SourceVersionTransition`。
**退出**：故障注入全部通过，源替换后无旧 SHA 状态残留。

### Phase 6：开启「有目录 + 改原文」
先支持最明确的动作：`RetitleChapter`、`InsertHeading`、明确确认的 `RemoveDuplicate`；其余动作若无安全 `SourcePatch` 则退回 `TreeOnly` 并显示「本项不改原文」。
**退出**：六卷样书有目录模式通过完整端到端验收。

### Phase 7：开启「无目录 + 改原文」
`LocalRepairPlanner` 为安全动作生成 `SourcePatch`；高风险启发式仍要求手动选择。
**退出**：2×2 矩阵完整，各组合走同一「计划 / 确认 / 执行」主干。

## 21. 性能要求

回归线（不要求激进优化）：

- 10 万行 TXT：加载与 fingerprint 不出现明显 UI 卡死
- `SourcePatch` normalize：`O(操作数 log 操作数)`
- source render：单次 `O(原始行数 + 插入数)`
- **不允许每个 operation 重新扫描整本书**
- `CanonicalChapterModel` 正文 hash 按 source range 流式计算，不复制整书字符串
- journal 与 receipt 不保存整本新文件内容，只存 patch 与摘要

UI 长任务继续使用可取消异步流程。

## 22. 验收标准

**架构**
- 参考目录与本地修复都产出 `RepairCandidate` 并进入同一确认窗
- 工作台只有一套修复确认与应用链
- `ChapterTreeDocument` 中不存在 pending mutable source edits
- `TreePatch` 与 `SourcePatch` 有独立类型与独立验证器
- `InsertHeading` 是显式动作

**数据一致性**
- 计划绑定三类 fingerprint
- 原文提交成功后旧 document / cache / undo / review state 不再使用
- 目录信息迁移到 NewSha
- 新项目 `ChapterTreePlan` 绑定 NewSha

**文件安全**
- 写盘前有 snapshot
- temp 与目标同目录
- temp 完整 flush 后才 replace
- 事务中断后不重复执行 patch
- no-op round-trip 失败时禁止 `EditSource`
- 实际 diff 与 receipt 一致

**行为**
- 当前 `TreeOnly` 功能不回退
- 六卷样书缺陷按既定策略处理
- 真正缺失正文永不被补造
- 第二次运行幂等
- 两模式 `Canonical` 语义一致

## 23. 一期明确不自动执行的情况

- `MissingBody`
- `OutOfOrderFinding`
- 无明确锚点的 `InsertHeading`
- 正文不同的重复章节物理删除
- 跨 `manual` 区域且无法建立稳定坐标映射的改动
- 需要搬移正文块才能修复的顺序异常
