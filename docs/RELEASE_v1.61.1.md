# v1.61.1 · true-count

一次把**章节数**这件事查到底的版本。

起因是六卷缺陷样书的走查：同一本书，界面上出现过 467、560、567 三个数。
一开始的判断是"系统里有三条识别路径在打架"。查完之后结论不一样 ——
**三个数里只有一个是错的，而且错的不是识别，是沉默。**

## 一、先纠正我自己的三次误判

这一版最重要的一条修复，是修复我上一版文档里的错误结论。写下来是因为
**三次错的形状是同一个**：先有了一个数，就把它当成"系统应该给出的唯一答案"，
再拿别的配置、别的口径下的数去证明它错了。

| 我说过 | 实际是 |
|---|---|
| 「Core 任何参数组合都给不出 560」 | 我只做了逐字段替换，**组合效应根本没测到** |
| 560 与 561「不可能来自同一个 document」 | 口径不同而已：561 含合成的「序」，560 不含。**两个数自洽** |
| 「同一本书能识别出 468/561/568 三种章节数」 | 那三个数分属**不同配置**；同一配置下章节树与预检一直是一致的 |

**预检路径从来没有缺陷。** 这一点现在有测试锁住（6 组识别配置全绿）。

## 二、修好了一个真 bug：分层识别把重复标题行拆成了空章

第六卷每章标题印了两遍。分层**关**时 `SkipRepeatedHeadingRun` 把它们合并成一章；
分层**开**时，第二遍被层级正则匹配成了一个**正文为空的独立条目**。

原因很直白：`SkipRepeatedHeadingRun` 只管**正文范围**，不管**条目列表**。

下表口径统一为「由标题行识别出的条目数」（不含合成的「序」）：

| 配置 | 修前 | 修后 |
|---|---|---|
| 现代默认 + 分层关 | 467 | 467 |
| 现代默认 + 分层开 | **567** | **467** |
| 旧正则 + 分层关 | 460 | 460 |
| 旧正则 + 分层开 | **560** | **460** |

**开不开层级目录，不再改变"这本书有多少章"。** 100 个空章消失。

## 三、章数差异不再沉默

没保存章节树时，转换走的是 v1.50 原样识别路径（`LegacyTextParser` 逐行），
它不合并连着印两遍的标题行。于是会出现「工作台说 467 章、点转换得到 567 章」。

**这个行为我们选择保留** —— 改它会让老用户的成品目录结构变化，属于用户主权，
不该由一次重构顺手改掉。**缺陷是沉默，不是错**，所以修的是沉默。

转换前检查现在会报出**实测**的两个数：

> 工作台识别出 467 章，但直接转换会产出 567 章（多 100 章，其中 100 章正文是空的）。
> 两条路径的识别规则不同：没保存章节树时走 v1.50 原样识别，且不合并连着印两遍的标题行。
> 这是为兼容旧成品保留的行为。要按工作台那份转换，请先在工作台保存章节树。

按这个提示按钮是「**在工作台保存章节树**」，不是通用的「处理章节」。

**关键做法：不推断差异，只实测差异。** 检查时用转换将要用的同一份参数、
同一条路径真的跑一遍，所以报出来的数**不可能与实际转换漂移**。
比"用正则再算一遍哪里重复"更省代码也更可靠 —— 后者会引入第二套识别逻辑，
正是这个项目已经吃过大亏的模式。

## 四、顺便查清了一个悬案

排查中发现：旧章节正则 + 分层开时，层级正则的新旧会改变章节数（460 vs 467，差 7）。

逐行对出来是 **7 个裸数字标题**：

```
一百零一章 戊101 断后险路        一百一十章   戊110 断后天光
一百零四章 戊104 断后暗河        一百一十三章 戊113 突围绝壁
一百零七章 戊107 断后反手        一百一十六章 戊116 突围死局
                                一百一十九章 戊119 突围长夜
```

没有「第」字。旧 `LegacyPattern` 要求首字符必须是 第 或 卷，**结构上就匹不上**；
现代层级正则的「第」是可选的，所以认得出。

**这 7 个是能力，不是缺陷。** 我原先为此写过一条「层级正则不该改变章节数」的契约，
测试红了 —— 但红的是**契约**，不是实现。契约写错时改契约，不是改实现去迁就它。
现在测试锁的是这个能力本身。

## 五、测试

新增 `tests/EasyPub.Core.Tests/ChapterCountContractTests.cs` —— 12 条全绿，锁四件事：

1. 工作台与转换前检查数出的章节数必须一致（6 组识别配置）
2. 开不开层级目录不改变章节数
3. 章数差异一旦存在，**转换前检查必须报出来**，且报的是实测值
4. 保存了章节树就不许再报 —— 一条永远出现的提醒等于没有提醒

第 3 条的前身要求"三条路径的数完全相等"。那个契约在产品决定之后是**错的**
（它会逼实现去掉兼容行为）。契约与产品决定冲突时改契约，但要换成一条**更硬的**，不是删掉。

## 验证

- Core：**836 通过 / 1 失败**。唯一失败是 `LongTextPerformanceTests` —— 它是一条
  对 28 MB 长篇设**墙钟预算**（转换前检查 < 400 ms）的测试，在全量跑（同时还有 836 条测试）
  时会超；**单独跑通过**。
- Desktop：`ChapterIssueActionTests` 22 通过。
- 样书三项约束不变：正文守恒、用户主权、可核对。

### ⚠️ 这一节原本写的是错的，记在这里

第一版发布说明写的是「该失败对机器负载敏感，**与本次改动无关**」。
**那句话是错的，而且它差点掩盖一个我自己引入的性能回归。**

真相是：第三节那个「实测差异」的检查，第一版**无条件**跑一整条无树转换路径
（读文件 + 解码 + 文本清理 + 逐行识别）。实测在 28 MB / 8000 章的长篇上，
它把转换前检查从 400 ms 以内顶到 **545 ms** —— 那条测试**单独跑也红**。

我当时的第一反应是"这条测试本来就是红的"，而没有先验证。把它临时关掉再跑一次，
测试立刻通过 —— 那一刻才确认是自己干的。

修法是一道**精确的闸门**：`ChapterTreeDocument.RepeatedHeadingLinesSkipped`
顺手记下识别时跳过了几行重复标题（`SkipRepeatedHeadingRun` 本来每个标题都要调一次），
为 0 就跳过那次昂贵实测。修后单独跑通过。

闸门的第一版也是错的：扫的是"有没有相邻的完全相同的非空行"。长篇里重复的正文行
到处都是，性能测试文件里 28 行正文压根就是同一句，于是闸门永远开着，只把 545 降到 419。
**判据必须落在"标题"上，不能落在"行"上。**

> 教训：**"这条测试本来就是红的"不是结论，是猜测。** 改动了那条路径，就先把它关掉跑一次基线。
> 三步，两分钟，换来的是没在发布说明里写下假话。
