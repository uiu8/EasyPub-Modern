# Phase 6：开启「有目录 + 改原文」

日期：2026-09-17
前置：Phase 5 全部完成（坐标表、版本迁移、恢复事务、六个阶段故障注入）

---

## 1. 这一阶段要解决的事

Phase 5 结束时，写原文的整条链路已经能跑：编译、渲染、事务、版本迁移、执行清单。但只有**测试夹具**
够得着它 —— 工作台里的按钮只做一件事，在内存里换一棵树。

验收条件写得很直白：

> 前端按钮必须与开发/测试路径调用同一套代码链路，不允许存在只有代码能走、按钮走不到的功能。

所以这一阶段不是"给窗口加个按钮"，而是**让按钮和测试没有第二条路可走**。

---

## 2. `ChapterRepairApplier`：唯一的应用入口

新类型，UI 与测试共用的唯一入口。它做两件事：

| 方法 | 做什么 | 什么时候用 |
|---|---|---|
| `Preview` | 编译、渲染、验算，**不写任何东西** | 窗口每次勾选变化时调用 |
| `ApplyAsync` | 按模式执行（TreeOnly 只算产物，EditSource 走事务） | 用户按下"应用所选修改"时调用 |

两个方法吃同样的参数，因而窗口上写的数字与接下来会发生的事来自同一次编译。这不是"顺手对齐"：
之前 `RepairReviewWindow` 的界面数字与 `ReferencePlanner.Apply` 的实际行为是两套各自演化的东西，
它们漂移过。

两种模式**只在"用哪套产物"上不同**：

- `TreeOnly` —— 编译树补丁，**从不创建事务**。这是设计里的不变量，不是优化：没有文件改变，
  为它建一条记录就是记录"什么都没发生"，而"原文一个字节都不动"正是这个模式的全部承诺。
- `EditSource` —— 两样都编译，走完整链路。

`ChapterRepairApplierTests`（11 个）里有一条专门钉住这件事：
`The_two_modes_do_not_disagree_about_what_an_action_means` —— 两种模式报出的**树变化数必须相同**
（模式不决定动作做什么），而文本操作数不同（0 vs 69）。

## 3. 落地模式的选择放在确认窗里

产品决定（用户选定）：**在核对窗口里选**，而不是两个独立按钮，也不是只靠设置。

理由：勾选之后窗口会列出"将改动原文的 69 行（69 个操作）"，这个数字来自 `Preview`；
用户在看到"哪些章节要改"的同时也看到"其中多少会落到我的文件上"。两个按钮的做法会让两份预览
再次各自演化 —— 这正是第一次重构要消灭的形状。

默认值：**同时改原文**（用户选定）。它写进了 `AppSettingsStore`，是一个设置项而不是硬编码，
所以下一次打开窗口时是用户上次的选择。

窗口底部原来固定写着一行「原始 TXT 不变 · 应用前自动备份 · 应用后可以撤销」。这句话对唯一存在过的
那个模式是真的，而第二个模式一出现它就变成了谎话。现在那一行是按模式算出来的两句话。

重复副本的第二问（`NeedsExplicitOptIn`）也在这一阶段接上：只有这类动作的行上才出现
「并从原文删除这一份」，勾了它效果才从"只从成品里排除"变成"真的从 TXT 删"。
这是设计里"用户只能让效果变强、不能变弱"的落点。

## 4. 修掉一处 Phase 3 留下来的占位

`RepairDecisionCompiler.Outcomes` 里写着：

```csharp
// Nothing can produce a source operation yet, so every conditional request is downgraded.
// When SourcePatch arrives this becomes a lookup instead of a constant.
_ => SourceEffectOutcome.Downgraded,
```

`SourcePatch` 早就到了，这个常量还留在原地。它意味着执行清单里**每一个条件性请求都被记成
"降级了"**，包括那些其实真的改了原文的。收据与事实不符，而且不会有任何检查报错。

现在拆成两个方法，各说各的时机：

- `Outcomes(decisions)` —— 编译之前，没有补丁可查，条件性请求如实答"降级"。
- `OutcomesFor(proposal, decisions, patch)` —— 编译之后，**去补丁里查这个动作有没有操作**。

后者是清单该用的那个。同时删掉了 `Func<ReferenceAction, bool>` 那个谓词重载：
它允许调用方用一个跟补丁无关的答案来回答"补丁里有没有"，而那正是错误来源。

## 5. 六卷样书实测

`sim phase6`，全部核对通过：

```text
默认勾选 117 个动作（方案共 191 个）

== 第一格：只改章节树 ==
   预览：可应用：127 条树变化，不动原文
   预览说会改原文：False；文本操作 0 个
   执行：章节树已更新：127 条变化，原文未改动。
   原文 SHA-256 未变：True        没有创建事务：True

== 第二格：同时改原文 ==
   预览：可应用：127 条树变化，69 个文本操作
   预览里会改动的原文行数：69
   执行：127 条树变化，69 个文本操作（改 69、删 0、插 0 行）；69 个章节身份没能跟过来。
   原文 SHA-256 已变：True（5C686D95691AAAED…）
   行数：2502 → 2502（只改行内文字，行数不变）
   真正被改的行数：69（预览说 69，应一致）→ 一致
   迁移后的树通过 ValidatePlan：True
   树的正文区间越界或与原文不符的行：0
   修复前的原文已备份：True        事务记录状态：Committed
   执行清单：落地模式 EditSource；决策 191 条（改到原文 69 条）；树变化 127 条；文本操作 69 个
   换过版本的文件能按章节树读回：True

== 第三格：方案过期 ==
   再次应用同一方案：被拒（原文已经不是这份章节树对应的那一版），原文未被二次改动
```

**"预览与实测一致"是这一阶段最该看的一行**：窗口说会改 69 行，逐行比较之后真的是 69 行。
不是"大致一致"，是逐行数出来的。

### 5.1 实测里先踩到的一个坑（在探针里，不在产品里）

第一版探针把 `Plan.Actions` 全部 191 个当成"用户勾选"传进去，于是预览回报
"73 个动作只是发现，不能执行"，整份方案被拒。

这不是缺陷，而是**产品语义被探针写错了**：那 73 个（`MissingBody` 41、`KeepExtra` 32、`VolumeNote` 1）
是发现的**问题**，不是要执行的**动作**。窗口把它们画成行供人看，但它们的复选框永远不勾，
所以它们从不出现在交给应用入口的集合里。

改对之后（只传 `DefaultSelection`，117 个）两种模式都正常。
这条值得记下来：如果当初实现时"顺手"把未勾选的动作也传进去，产品会在用户按下按钮时
整份拒绝，而不是执行该执行的那些。

## 6. 测试

**Core +11**（`ChapterRepairApplierTests`），Core 总数 761 → **772**。

覆盖：两种模式各自的预览说了什么、TreeOnly 不写文件且不创建事务、EditSource 真的改写并搬树、
应用前备份的是修复前那一版、事务记录收尾、执行清单逐字段核对（落地模式、proposal id、
69 个文本操作、69 条决策记为"已应用"）、两种模式对动作语义一致、
重复应用同一方案被拒（并说清原因）、以及一本小书的精确往返。

**Desktop +5**（`LandingModeWiringTests`）：两个模式选项都在且默认落在配置的那个上、
切到 TreeOnly 后不再承诺动文件、切回 EditSource 后"改标题"要求动文件、
窗口交出的决策与 `ChapterRepairApplier.DecisionsFor` 逐字段相同、按钮可用。

Desktop 套件本身是 flaky 的（`Application` 是进程单例，只属于创建它的那个线程；
每个测试各自开一个 STA 线程，于是谁先创建谁拥有它，随后连它的线程一起死掉）。
这一阶段做了两件事来控制它：

1. 新测试**不用 `ShowDialog`**。测试自己的 STA 线程里再开一层嵌套消息循环，是把"偶发失败"
   变成"成片失败"的做法，而这套件有五十多个窗口测试共用。
   `WithShown` 因此只用 `Show()`；按钮的 `DialogResult` 赋值只有对话框允许，
   所以"按钮交出什么"改为断言 `SelectedDecisions()`，而不是真的按下去。
2. `RepairReviewWindow` 的 `defaultMode` 默认值取 `TreeOnly` —— 也就是这个窗口在模式存在之前的行为。
   能真正写 TXT 的那个入口显式传 `EditSource` 并同时传预览回调；
   两样都不传的调用方保持旧行为，而不是承诺一件没人能执行的改写。

这两条之后，全量 Desktop 套件的失败数回到基线的同一水平（基线 4；实测 3 与 11 两次波动）。

## 7. 下一步

Phase 7：开启「无目录 + 改原文」。

现在的实测边界很清楚：**没有目录时统一入口不产生任何修复项**（这是真实的能力边界，不是缺陷）。
Phase 7 要解决的是"没有目录可对齐时，用户还能改什么原文" —— 可用的动作是那些不依赖参考目录的：
重复标题、纯数字标题、标题层级规范化、缺号区间的标题补识别等。

另外两件留到 Phase 7 或之后：

- 中文备份窗口的「恢复」按钮应当接 `RestoreTransaction`，并让用户选
  `SourceOnly` / `FullBookState`（后者只在那个版本存了树时可选；清单里的
  `FullStateSnapshotCount` 就是给这个判断用的）。
- 工作台里的"原文已变化 · 刷新"应当走 `SourceVersionTransition`，把"哪些章节失效了"报给用户。
