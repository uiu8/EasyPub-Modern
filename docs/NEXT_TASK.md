## 已排除：对齐层不是瓶颈（附数据）

《凡人修仙传》`auto` 的真实分布：

```
目录获取（网络）    7 754 – 27 922 ms   ← 98%，瓶口在这里
对齐 Build                  0 ms        ← 内部 <1 ms
  └ 候选行 / 前两遍 / 兜底   9 / 34 / 89–145 ms
重建 + 核对              ~170 ms
```

**「8700 万次迭代」是把疯巫妖的 61752 行安到了只有 1078 行的凡人头上**，
真实是 150 万次 / 92 ms，差 58 倍。

### 已经失败两次，而且本来就不该做

| 方向 | 为什么不该做 |
|---|---|
| 加「目录远大于文本就跳过第三遍」的闸门 | 只能省 1%，却会丢掉兜底救回的 27 章（30→3）。**收益 <0，风险 >0** |
| 把章号匹配建索引 | 前提就错：那 14.3 s 的大头不在定位里，复盘的基础不成立 |

**另一个反直觉结论：调并发没用。** `MaxConcurrentSources` 4→6 实测 10.0 / 8.8 s，
与 8.4 s 同量级，**无改善，已回滚**。慢的是单个站的目录抓取，不是排队。

## 诊断工具

```powershell
& $dotnet run --project work\chapter-audit -c Release -- <txt路径> <模式>
```

| 模式 | 作用 |
|---|---|
| `auto` | 完整 `RepairAsync`，打印参考/重建/缺章数 + **分段耗时 + 每源耗时**（与 UI 一键修复同一路径）|
| `repair` | 同上，并逐条打印重建后的树 + 分类报告 |
| `probe <行号>` | 打印指定源行在原始树中的身份（标题？正文？来源？长度？）|
| `tree` | 打印对齐后的树 |
| `sources` | 检测各书源可用性与响应耗时（和设置对话框同一段代码）|
| `reference` | 打印各源返回的目录前后各若干条，用来判断源的质量 |

**注意**：`chapter-audit` **只读** GUI 的目录缓存（`%LOCALAPPDATA%\EasyPub Modern\Catalogs`），
不写。所以命令行每次都走网络；GUI 第二次修同一本书只需约 200 ms。

- `C:\Users\13168\Desktop\novel\so-novel\*.txt`（37 本）
- `C:\Users\13168\Desktop\novel\tomato\*.txt`（7 本，番茄）

**注意**：部分语料本身不完整（凡人修仙传只有 0.18 MB / 1078 行）。
看到"缺 N 章"先核对**源文件本身有多少章**，再判断是不是软件的问题。
