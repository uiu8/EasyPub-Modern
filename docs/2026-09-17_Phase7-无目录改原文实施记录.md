## 1. 先量边界，再动手

Phase 5 的记录里写着一条实测事实：

> 无目录 → 统一入口不产生任何修复项（**真实能力边界**，Phase 7 处理）。

动手之前先把这条边界量清楚（`sim nocatalog`）：

```text
CatalogFound：False
方案对象：null
TreeOnly  预览：可应用=False｜这次没有可用的修复方案
EditSource 预览：可应用=False｜这次没有可用的修复方案

树自身能看出的问题：
   同名标题（同一标题出现多次）：32 组，涉及 64 个条目
   章号重启点（推断卷边界）：5 处
   标题编号的缺号总数：49
   没有标题行的条目：0 个
   没有正文的条目：0 个
```

结论改变了这件事的性质：**"无目录就什么都做不了"不是能力边界，是缺了一个判定来源。**

树本身就看得出 32 组同名标题。所以 Phase 7 要补的不是"更多动作"，而是"一条不依赖外部目录的判定路径"。

## 2. `SelfRepairPlanner`：从书自身得到方案

新类型。它的取舍是这一阶段唯一需要判断的事，而取舍只有一条：

> **只发不依赖外部目录就能判定的动作。**

因此它只发两类：

| 依据 | 动作 | 为什么不需要目录 |
|---|---|---|
| 同一标题出现多次 | `RemoveDuplicate` | 书要的是一章；留哪一份由**位置**决定，不由目录决定 |
| 编号写法不规范，且规范形式能从标题自己推出来 | `Retitle` | 规范形式是标题的函式（`1 起点` → `第一章 起点`），不查任何外部信息 |

**要靠目录才能判定的，一律不发**：某章是不是*缺失*、某段正文该不该*立成标题*、某一章是不是真的*多余*。
从书自身猜这些，就是让修复凭空造章节 —— 而"绝不凭空造章节"是这套东西从第一天起的规则。
`SelfRepairPlannerTests` 里有一条专门钉它：纯数字标题在数字识别关闭时树里没有标题行，
此时自修复**什么也不发**，而不是"看这一行像标题"就去改原文。

方案来源记在 `RepairProposal.Basis` 上：有目录是 `ReferenceCatalog`，没有是 `SelfRepair`。
两者是对同一次修复的不同断言，收据必须能分开。

## 3. 不新增协议

`SelfRepairPlanner` 发的是与目录路径**相同的** `ReferenceActionKind`，一个都不新增。

这是有意的：新增一种动作种类，就要在效果编译器、计划编译器、事务、落地模式里各加一个分支，
而每一个分支都是一处让两条路漂移的地方。复用现成的种类，整条链原样可用 ——
同一次编译、同一个事务、同一套落地模式。

它复用的是那个"把动作变成物理操作"的既有架构：动作 × 效果三个维度 × 补丁投影 × 事务。

## 4. 实测里改掉的两处缺陷（都在产品里）

### 4.1 编译器从没接上「显式要求物理删除」这条路

`RepairEffectCompiler` 里，重复副本有**两个**答案：

- `Describe(action, …)` → `SourceContentUnchanged`，也就是"只从成品里排除多余的副本，原文一个字不动"。
  这是保守的那个，也是默认那个。
- `DescribeDuplicateDeletion(action, lines)` → `SourceContentDelete`，真的从 TXT 删掉那几行。

`RepairPlanCompiler` 只调了第一个。于是当用户勾上「并从原文删除这一份」（决策是
`ApplyRequired`）时，编译器看到的是"承诺了改原文、却投影不出任何操作"，于是**拒绝整份方案**。
用户被告诉"这次修复无法应用"，而他要求的只是删掉一行重复的标题。

修法是在编译循环里补上那一步：效果是 `SourceContentUnchanged`、决策是 `ApplyRequired`、
且该动作种类的策略是 `ExplicitOptIn` 时，改用 `DescribeDuplicateDeletion` 重新表述效果。
判据用 `SourceEffectPolicies.NeedsExplicitOptIn` 而不是硬编码 `Kind == RemoveDuplicate`，
这样将来新增显式选择类动作时它自动跟上。

### 4.2 `RepairDecisionCompiler.Check` 的判据只问了一半

同一个形状的另一处：`ChapterRepairApplier` 判"这个动作能不能改原文"时，只问了 `Describe`。
对显式选择类动作，删除效果由另一个入口表述，所以它永远答"不能"，整份方案又被拒。

现在明确写成两条路：先问 `Project(Describe(...))`，再问该种类是否属于
"删除效果另行计算"的那一类。

**这两处合起来说明一件事**：把"能不能改原文"当成一个可以随手回答的问题，就会答错。
它取决于动作种类与它的策略，两处都得问。

### 5.1 探针里先写错的两处统计（不是产品缺陷，但值得记）

1. **拿"全书无同名标题"当判据。** 六卷各有「第一章」，跨卷同名是合法的；空白行更是必然重复
   （全书 961 个）。第一版统计因此报告"删除后仍有 168 组重复"。正确判据只有一条：
   **被删掉的那些文字，删除之后还多不多于一份。**
2. **删行之后逐行比较。** 删掉一行，它下面每一行的行号都上移，逐行比较于是报告
   "2007 行位置上的内容变了"。那是行号比较的必然结果，不是改动范围。
   数"被删掉的行"要按内容的出现次数来比。

两条都不是产品问题，但它们都会让人误以为产品错了 —— 所以记在这里。

## 6. 界面接线

`ChapterAutoRepairPanel` 里原本是：

```csharp
if (!outcome.CatalogFound) { CatalogAssist_Click(...); return; }
```

无目录就弹目录对话框。这在以前是对的（那时无目录必然没有方案）。现在不行了：
把一个有 32 项内容的方案挡在目录对话框后面，等于告诉用户"什么都做不了"，而实际上有。

改成只有**真的无事可做**才去要目录：

```csharp
if (!outcome.CatalogFound && (outcome.Plan?.Actions.Count ?? 0) == 0) { ... }
```
