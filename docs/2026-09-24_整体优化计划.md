# EasyPub Modern 整体优化计划

> 日期：2026-09-24
> 
> 目标：在保留现有章节修复能力、原文保护和 Kindling 转换出口的前提下，继续收敛代码结构、性能和前端细节。本文是接下来迭代的执行合同，不把尚未测量的改进写成已经完成。

## 1. 当前结论

章节工作台是主窗口打开的独立弹窗。它负责一件事：在当前书稿上检查、核对和提交章节修复。主窗口才负责品牌、制作流程、原文备份、转换记录和页面导航。

本轮已经完成的壳层修正：

- 移除 `ChapterEditorWindow` 左侧重复的品牌和主流程导航。
- 保留工作台自身的三栏：章节树、待核对、证据与原文。
- 保留顶部“检查依据 × 应用范围”、检查入口以及底部撤销/重做和“应用并返回”。
- 不修改 `MainWindow` 的导航、底部栏、导入页、检查总览、制作设置和转换验收页面。
- 不改变章节识别、参考目录对齐、修复方案、`Mutate`/事务写入、备份恢复或 Kindling 引擎。

真实工作台截图已生成：[`outputs/ui-shell-fix-20260924/00-章节工作台.png`](../outputs/ui-shell-fix-20260924/00-章节工作台.png)。这张图用于确认“弹窗只显示工作内容”的视觉结果，不能代替用户对最终配色和间距的人工确认。

## 2. 现状证据与主要风险

### 2.1 代码边界

当前工作区实测文件规模为：`EasyPub.Core` 112 个 C# 文件，`EasyPub.Desktop` 62 个 C# 文件和 23 个 XAML 文件。Desktop 的章节工作台由一个 XAML 壳层和多个 `partial class ChapterEditorWindow` 面板文件组成；Core 保持无 UI 依赖。

现有处理链可以概括为：

```text
TXT/EPUB → 文档缓存 → 章节识别 → 诊断与断点 → 参考目录对齐
       → 修复方案/会话 → 用户确认 → 章节树或 TXT 事务 → 复查 → Kindling/EPUB 输出
```

这条链已经包含缓存、取消、备份、撤销和完整性校验。接下来的优化应减少重复推导和 UI 状态分散，不能用重写框架替换已经验证过的边界。

### 2.2 性能基线

下列数字来自真实语料基线和独立长文本测试，作为后续对照，不是宣传指标：

| 项目 | 已测结果 | 用途 |
|---|---:|---|
| 真实物理 TXT | 47 个文件，42 种唯一内容 | 评估重复语料与缓存命中 |
| 冷加载 | 中位数 45.3 ms，最大 255.8 ms | 识别与文档加载基线 |
| 同进程热加载 | 中位数 44.5 ms，最大 252.8 ms | 缓存是否有效 |
| 本地诊断 | 中位数 35.8 ms，最大 679.2 ms | 找出大书或提示很多的热点 |
| 断点计算 | 中位数 0.5 ms，最大 18.3 ms | 断点算法基线 |
| 8000 章长文本预检 | 独立运行 295 ms，预算 400 ms | 不能因并发负载修改门槛 |

主要风险不是某一个按钮慢，而是同一份章节树在切换筛选、选择章节、刷新提醒、改变修复范围时被重复分析；其次是长列表和原文预览在 WPF 视觉树中产生不必要的布局工作。

### 2.3 产品风险

- 依据（当前书稿/参考目录）和落地范围（只改章节树/同时修改 TXT）必须始终成对显示，不能在某个弹窗里悄悄换模式。
- 参考目录说明“应该有什么”，不证明 TXT 中一定有正文；缺失正文不能自动造空章。
- 原始 TXT 只能经过备份、预览、用户确认和事务写入；删除必须保留清单。
- 主窗口和工作台弹窗的导航职责必须分开，不能通过复制左栏“看起来一致”来解决布局问题。

## 3. 总体目标和不变边界

### 3.1 到达状态

用户打开一本书后，可以在一个工作台内完成：

1. 看清当前树、依据和应用范围。
2. 选择一个问题组，看到证据、影响范围和可执行动作。
3. 预览方案后决定只整理成品，或明确写入修订文本副本/TXT。
4. 应用后复查章节数、正文覆盖、目录顺序和输出预检。

### 3.2 明确不做的事

- 不重写 WPF 为其他前端框架；当前问题是状态和布局职责，不是框架本身。
- 不重排主窗口的导入、检查总览、制作设置、转换验收架构。
- 不在没有真值或证据时增加“自动猜卷”“自动补正文”等启发式。
- 不把 Kindling 的快速转换误当成 Kindle 真机验收；真机仍需实际设备。
- 不以放宽测试阈值或只运行小样本来掩盖性能回归。

## 4. 代码结构优化

### 4.1 P0：固定窗口职责（本轮已完成）

**目标**：主窗口负责流程导航，章节工作台负责章节修复。

**落点**：

- `src/EasyPub.Desktop/ChapterEditorWindow.xaml` 只保留工作台内容和提交栏。
- `src/EasyPub.Desktop/MainWindow.xaml` 继续保留品牌、导航、原文备份和转换记录。
- `ControlStyleContractTests` 锁定两者不能互相复制壳层。

**退出条件**：工作台截图不再出现主窗口左栏；主窗口截图仍有原来的左栏和底部栏；相关定向测试全绿。

### 4.2 P1：集中工作台状态

当前 `ChapterEditorWindow` 的多个 partial 文件都能读写依据、落地模式、当前问题、选中节点和方案缓存。下一步建立一个只描述状态的模型，例如：

```text
ChapterWorkbenchState
├─ SourceRevision       原文路径、哈希、编码、是否有未提交副本
├─ EvidenceBasis        当前书稿或参考目录、目录来源与确认状态
├─ LandingMode          仅整理章节树或写入文本
├─ Selection            当前问题组、节点 ID、原文行范围
├─ AnalysisSnapshot     识别树、诊断、断点、目录匹配、生成时间
└─ PendingPlan          预览过的动作、用户决定、可撤回信息
```

实现顺序：

1. 先以现有字段做只读快照，不改变行为。
2. 让顶部模式条、中栏问题卡和右栏证据都读取同一快照。
3. 将“刷新分析”“切换筛选”“选择问题”拆成纯状态变更，再由一个渲染入口更新 UI。
4. 保留现有事件名和自动化控件名，避免破坏桌面测试和快捷键。

**验收**：改变依据或落地模式后，顶部状态、问题数量、右栏证据和底部说明在同一轮刷新中一致；不再出现列表数字和卡片数字来自不同分析结果的情况。

### 4.3 P1：统一命令和副作用入口

将按钮分为四类，并让每类只有一个进入点：

| 类别 | 例子 | 规则 |
|---|---|---|
| 观察 | 搜索、筛选、定位原文 | 不改变章节树，不创建备份 |
| 生成 | 检查章节、获取目录、生成建议 | 只生成快照或方案，不直接应用 |
| 应用 | 加入方案、应用并返回、写入副本 | 必须经过预览、确认和事务 |
| 恢复 | 撤销、重做、备份恢复 | 只作用于已有快照或事务收据 |

下一步将重复的 `UpdateReview...`、`Refresh...` 和按钮启用判断归并到命令状态计算中。UI 事件只负责收集输入和调用命令，不在事件处理器里再次推导整本书。

### 4.4 P2：Core 诊断快照

将章节识别、`ChapterReviewAnalyzer`、`ChapterBreakpoints` 和参考目录定位的结果组合为带版本的分析快照：

- 快照键包含源文件 SHA-256、识别规则版本、目录版本、落地模式和诊断选项。
- 仅切换 UI 筛选不重新读取 TXT。
- 只有源版本、规则、目录或相关树节点变化时才使对应部分失效。
- 诊断结果保留 entry id 和源行范围，禁止依赖可变的列表行号。

该层不改变“识别层”和“断点层”的职责边界；混用编号噪音仍在 `ChapterBreakpoints` 的作用域和 `present` 判定内收敛。

### 4.5 P2：文本副本和事务边界

修订文本副本继续遵循：

```text
选择动作 → 预览插入/移动/删除 → 用当前识别规则验证
→ 生成备份和逐行清单 → 事务写入副本 → 重新识别 → 用户应用
```

任何失败都回到副本或事务收据，不回写原始 TXT。该路径与只整理章节树共享方案模型，但不能共享会“顺便写文件”的 UI 事件。

## 5. 性能优化计划

### 5.1 先测量，再改算法

每轮优化保留四个独立时间：冷加载、热加载、诊断、断点/目录定位；网络目录获取单独计时。报告同时记录章节数、问题数、断点数、分配字节和源哈希。

禁止用全量并发运行的偶发慢值替换独立基线。若全量测试超过 400 ms，先确认是否是宿主并发和内存压力，再决定是否存在真实回归。

### 5.2 近期热点和处理方式

| 热点 | 处理方式 | 保护条件 |
|---|---|---|
| 选择章节后重复扫描全文 | 使用分析快照和节点 ID，只加载当前范围的原文预览 | 预览窗口固定为前后有限行，不拼接整章正文 |
| 同标题/重复正文比较过多 | 先按编号、标题规范化键、正文长度和哈希缩小候选，再做相似度 | 不以标题相同直接删除；保留证据和人工确认 |
| 参考目录定位 | 精确键一次建索引，模糊候选限制范围并支持取消 | 目录未确认时不参与修复判断 |
| 大型章节树布局 | 树和目录列表继续使用虚拟化与 Recycling | 不能因为虚拟化破坏选中、展开和键盘导航 |
| 获取目录/诊断阻塞界面 | 后台任务使用 linked cancellation token，窗口关闭时取消 | 取消后不提交半成品状态 |

### 5.3 目标门槛

这些是下一阶段的工程门槛，首次测量前不宣称已经达到：

- 47 本真实语料的冷/热中位数不超过当前基线的 110%。
- 8000 章独立预检继续低于 400 ms。
- 只切换筛选或选择问题时不重新读取源文件；界面响应目标为 100 ms 内完成可见状态更新。
- 原文预览只读取需要显示的范围，避免随选中章节增长而线性复制全文。
- 任何新增启发式必须在全部真实语料上记录新增提示、误报样本和耗时后才进入默认路径。

## 6. 前端细节优化计划

### 6.1 工作台弹窗布局

- 弹窗使用全宽工作区，不再有主窗口侧栏。
- 顶部只放“检查依据”“应用范围”和唯一的“检查章节”主入口。
- 中间三栏保持稳定顺序：章节树 → 待核对 → 证据与原文。
- 右栏动作按“查看证据 → 定位/预览 → 加入方案”排序；“应用并返回”只在底部作为提交入口。
- 撤销/重做固定在底部，不和问题处理按钮混成一排。

### 6.2 信息层级与文案

每个操作同时回答“作用对象、是否生成方案、是否写 TXT、如何恢复”：

- “检查章节”只生成建议，不应用。
- “加入方案”只改变待应用方案，不写文件。
- “应用并返回”提交当前方案；若选择写 TXT，先展示备份和差异。
- “定位原文”只移动到证据行，不改变树。
- “重新识别章节”会替换当前树，必须明确提示可撤销。

主按钮只保留一个视觉主色；次级按钮使用轻边框，危险/缺失状态用状态色而不是大面积实色。

### 6.3 响应式和可访问性

- 验证 1480×900 和最小 1080×680 两个窗口尺寸。
- 三栏宽度在小窗口按内容优先级收缩，右栏正文预览允许滚动，不挤压底部提交栏。
- 每个按钮保留稳定的 `x:Name`、自动化文本和 ToolTip；键盘焦点必须可见。
- 章节树复选框继续只表示目录收录/批量操作，不与问题选择复用含义。
- 截图测试同时检查主按钮、状态条、三栏标题、取消和应用按钮可见。

### 6.4 视觉范围

本阶段只优化章节工作台的间距、层级、禁用态和信息密度。全局原版配色、主窗口架构和底部栏保持现状；任何新的风格方案都要单独出预览并经用户确认后再改。

## 7. 执行顺序

| 阶段 | 工作 | 交付证据 |
|---|---|---|
| P0 | 移除弹窗重复主导航（已完成） | XAML 回归约束、Desktop 定向测试、工作台 PNG |
| P1 | 工作台状态快照与命令入口收敛 | 状态一致性测试、模式切换测试、前后快照差异 |
| P2 | Core 诊断快照和失效键 | 47 本语料前后耗时、问题数和源哈希报告 |
| P3 | 虚拟化、取消、原文预览窗口化 | 小屏截图、交互响应测量、取消回归 |
| P4 | 文案和间距收口 | 1480×900/1080×680 截图、用户视觉确认 |
| P5 | 全量回归和发布 | Core/Desktop 全绿、Kindling 转换矩阵、ZIP/Setup 内容核对 |

每个阶段都先写实施记录，再进入下一阶段；如果指标变差，保留失败报告并回到上一阶段，不通过修改阈值“修绿”。

## 8. 验证矩阵

### 8.1 代码和功能

- `ControlStyleContractTests`：保证资源和弹窗壳层约束仍成立。
- `ChapterEditorWindowTests`、`WorkbenchContextBarTests`、`RepairApplyWorkflowTests`：保证章节树、模式、证据和应用链不回归。
- Core 章节修复与完整性测试：保证正文守恒、用户手工决定优先和缺失正文不造空章。
- 文本写入路径：只用临时副本，核对备份、逐行清单、事务收据和源哈希。

### 8.2 转换和验收

涉及转换的验证全部使用 Kindling 引擎；同时检查输出头、文件大小、日志、章节树正文章数和转换计划条目数。Kindling 通过不等于 Kindle 真机通过，真机项目继续单列。

### 8.3 视觉

每次改动工作台布局都生成单独 PNG。先检查截图里的职责边界和按钮可见性，再请用户确认视觉；截图不能代替交互测试，交互测试也不能代替截图。

## 9. 下一步

当前 P0 已完成，下一步进入 P1：先建立工作台状态快照的只读层，盘点 `ChapterWorkbench.cs`、`ChapterReviewPanel.cs`、`ChapterAutoRepairPanel.cs` 和 `ChapterReviewOverview.cs` 的字段读写关系；不改变按钮文案和业务行为。完成后用模式切换、问题选择、刷新和撤销四条路径验证状态是否始终来自同一份快照，再决定是否移动代码。

本计划的第一条硬约束仍是：章节工作台是弹窗，主窗口导航不复制进来；第二条硬约束是：所有修复动作都必须可解释、可预览、可恢复。
