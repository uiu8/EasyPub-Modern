# EasyPub Modern 全面质量与产品体验评估

评估日期：2026-09-06 至 2026-09-07。对象是当前本地工作区，包括尚未提交的自动检查和 UI 调整；不是仅审查 GitHub 上的正式版本。本次只分析、测试和新增报告，不修改产品代码、不发布版本。

## 一、结论：方向正确，下一阶段应完成质量收口

EasyPub Modern 应继续定位为 **EasyPub 增强版、面向中文小说整理的 Windows 电子书转换器**。不需要为了差异化转型为写作平台、出版管理系统或另一个 Calibre。

现在已经有足够多的实用功能。真正妨碍用户长期使用的，不再主要是“少几个选项”，而是：用户还不能始终准确判断自己选了什么、设置影响哪些书、问题是否已处理，以及生成成功是否等于成品完整。

这不是纯粹的主观体验判断。本次复现了一个需要在下次正式发布前解决的问题：**保存章节树后，跨行自定义清理改变行数，可能使转换成功的 EPUB 丢失正文，而现有结构验收仍显示通过。** 另外发现自动检查结论与转换前检查存在语义分歧，以及控件模板、输出落盘等方面的明确缺口。

建议投入顺序：正文完整性和输出安全 → 检查/设置/任务状态一致性 → 控件功能与布局收口 → 性能与维护成本 → 少量高价值转换功能。

### 已经值得保留的部分

- 中文 TXT 的章节识别、层级编辑、拆分合并、清理预览、自定义规则、插图和元数据，构成了一条有实际用途的转换流程。
- 源 TXT 与转换处理分开，章节树有源文件指纹，清理支持逐项排除。这些是正确的安全设计基础。
- 已有 Core、Desktop、CLI 分层，不是必须推倒重来的代码库；缓存、列表虚拟化、进度节流、失败重试也已有实现。
- 书稿勾选与右侧当前操作书稿分开、保留底部格式/排版快捷入口、统一转换设置，符合用户实际操作需求。
- 最近的细滚动条、收藏菜单适配、检查摘要折叠等调整应保留，不把旧截图中的问题当作仍未修复的问题。
- 保留右侧封面及占位区尺寸；本报告不建议缩小封面，也不建议整页改版。

整体评价：**已经具备有用的工具能力，但组合功能的可靠性和跨界面的状态一致性，尚未跟上功能增长速度。** 不宜靠继续增加按钮掩盖这些问题，也不应据此否定现有功能的价值。

## 三、用户为什么选择它：不靠格式数量竞争

最合适的用户是：已有 TXT/EPUB，需要在 Windows 上整理中文小说，再生成 EPUB 或供相应 Kindle 使用的 MOBI；愿意调整章节和排版，但不想自己编辑 XHTML/CSS。

不适合优先争取的用户是：主要管理数万本藏书、需要书店和跨设备云同步、编辑复杂学术 EPUB、修复扫描 PDF 或进行专业写作协作的人。

| 对照对象 | 对方已具备的能力 | EasyPub 应采取的策略 |
| --- | --- | --- |
| 原版 EasyPub | 用户熟悉的转换结果和操作习惯 | 保持兼容输出及低学习成本，让批量整理、排错和现代 Windows 操作更顺手；不把原版兼容当作必须淘汰的包袱 |
| Calibre | 多阶段转换流水线、丰富排版参数、启发式处理、按书保存转换设置 | 不声称清理、目录和预设本身独有；把中文小说的常见问题处理得更直观、可确认、可重复。[官方转换手册](https://manual.calibre-ebook.com/conversion.html) |
| Sigil | EPUB 源码编辑、预览、目录生成、查找替换、检查点等 | 不复制一整套 EPUB IDE；把深度手工编辑交给外部编辑器，做好导入、转换和风险提示。[官方功能介绍](https://sigil-ebook.com/sigil/) |
| 在线转换网站 | 上传文件、选择格式、下载结果的短流程 | 学习其低操作成本；突出本地处理和转换前后的可见控制，而不是宣称网站都不安全。CloudConvert 本身也有隔离和数据安全措施。[转换页面](https://cloudconvert.com/mobi-converter)、[安全说明](https://cloudconvert.com/security) |
| Amazon 工具与渠道 | Send to Kindle 接收 EPUB；Previewer 提供 Kindle 预览及面向旧款设备的 MOBI 导出说明 | 把“格式”与“传书方式”说明白，不让用户误以为所有 Kindle 使用场景都应输出 MOBI。[Amazon 文档](https://kdp.amazon.com/en_US/help/topic/G200641240) |

以上竞争策略是根据官方能力和当前项目做出的产品判断，不是已经证明的市场优势。需要用真实任务验证：用户能否更快完成一本有广告、有卷章层级的小说，并且不需要返回修正成品。

目前支持范围也应写成明确映射：TXT → EPUB/MOBI；EPUB → MOBI，分保留原版式与兼容重排。不要让“TXT / EPUB → EPUB / MOBI”的宣传文字暗示所有组合、MOBI 输入或 EPUB 原位编辑都已支持。

## 四、优先修复的发现

### F01：章节树与跨行清理会失配，导致“成功但正文不完整”

**优先级 P0；动态复现；证据 E04。**

用户先保存章节树，再使用跨行自定义规则插入或删除行。清理后的行数组长度和位置发生变化，但章节树仍用原文行号截取正文。

最小测试书稿是两章四行：

```text
第一章 开始
甲段独有内容
第二章 后续
乙段独有末尾
```

保存章节树后，将第二行替换为“甲段独有内容 + 换行 + 新增一行”：

- 不使用这条规则的对照 EPUB：包含“乙段独有末尾”。
- 使用该规则的 EPUB：转换无异常，但“新增一行”和“乙段独有末尾”均未出现在章节正文中，第二章标题还进入了正文。
- 对后者调用现有验收：`StructurePassed = true`。

原因位于 [LegacyTextParser.cs](../src/EasyPub.Core/LegacyTextParser.cs) 第 24、85、99–101 行，以及 [TextCleanupPipeline.cs](../src/EasyPub.Core/TextCleanupPipeline.cs) 第 240–253 行。源文件指纹验证只能证明磁盘上的原文没变，不能证明清理后的坐标仍与章节树一致。按行定位的插图也应纳入同类检查。

建议分两步：近期在检测到行数/坐标变化且无法安全映射时阻止这类组合输出，并给出明确处理方式；随后让清理返回原文位置到处理后位置的映射，或基于稳定文本片段定位。不要静默丢弃已编辑的章节树，也不要简单改成“重新识别”而丢失用户的重排和合并。

验收：增行、删行、跨章匹配、章节重排、插图定位组合下，每个未被明确删除的正文片段都必须进入成品，且归属章节正确。不能仅检查 ZIP 能打开或目录数量相等。

### F02：自动检查、清理配置和转换前检查还没有形成一致的状态

**优先级 P1；动态复现与静态确认；证据 E03。**

发现四类问题：

1. 开启自动检查但取消所有检查项，在未配置 KindleGen 的合成 MOBI 任务上，列表结果是“可直接转换”；同一任务的完整转换前检查却是“必须处理”。转换前的必要检查仍会拦截，但列表结论超过了实际检查范围。
2. 已为输出开启广告清理后，自动检查依然扫描原文，并将相同广告计为待处理警告，缺少“已计划清理”和“仍未处理”的区别。
3. 非法自定义正则 `(` 被归类为 `input_unreadable`，提示无法读取 TXT。真正需要处理的是规则，而不是书稿。
4. 从某条 `cleanup_check` 打开清理窗口，初值取自动检查的整套清理规则；应用后直接替换项目级 `_textCleanupOptions`。此前启用、但没有加入自动检查的输出清理规则可能被覆盖。当前界面以一本书预览，不代表规则只影响这本书。

依据：[ConversionPreflightInspector.cs](../src/EasyPub.Core/ConversionPreflightInspector.cs) 第 121–130、169–176 行；[BookAnalysisCoordinator.cs](../src/EasyPub.Core/BookAnalysisCoordinator.cs) 第 19–33、82–89 行；[MainWindow.xaml.cs](../src/EasyPub.Desktop/MainWindow.xaml.cs) 第 1830–1845 行。

应统一三个概念：

- **检查范围**：用户选择检查什么；关闭或部分检查不能等同于完整通过。
- **处理计划**：原文有问题，但成品已计划处理；也可能已被用户排除、忽略或确认保留。
- **转换必需条件**：文件可读、输出安全、所需编译器存在等底线检查；不应该因为用户关闭后台检查就绕过。

建议显示“未检查 / 检查中 / 所选检查通过 / 建议确认 / 无法转换”，同时展示“已检查哪些项目”。关闭后台检查，不应偷偷重新启用全部广告、标点等建议规则；必要安全检查可以继续执行，但要说明。

从检查结果进入处理时，合并用户此次修改到已有输出计划，而不是用扫描配置覆盖整个计划。应用前明确“本书预览、应用于本项目全部 TXT”，或提供显式的本书覆盖设置。

另一个一致性细节：[MainWindow.xaml.cs](../src/EasyPub.Desktop/MainWindow.xaml.cs) 的 `UpdateTextCleanupSummary` 只统计部分内置规则，没有覆盖全部 11 项及自定义规则。只启用遗漏项时，摘要可能仍说“不做额外清理”。应从同一规则目录生成设置列表、摘要、检查结果和执行配置。

### F03：MOBI 最后落盘没有沿用 EPUB 的临时文件保护

**优先级 P0；静态确认的故障风险，未制造断电或磁盘耗尽；证据 E01。**

[LegacyMobiWriter.cs](../src/EasyPub.Core/LegacyMobiWriter.cs) 第 219 行直接把完整字节数组写入最终输出路径。选择“覆盖旧文件”时，如果最终写入阶段失败或取消，旧成品可能已被截断，新成品也可能不完整。

默认自动改名降低了破坏旧文件的风险，但不能保证失败时没有残留半成品。[LegacyEpubWriter.cs](../src/EasyPub.Core/LegacyEpubWriter.cs) 已使用同目录临时文件，再移动替换；MOBI 应复用这一落盘策略。

建议：先完成临时成品及必要验证，再提交到最终文件；所有格式共享同一输出提交 Module。覆盖失败时保留原文件，并明确报告临时文件与恢复方式。这里应通过故障注入测试证明保护有效，而不是只修改说明文字。

### F04：EPUB“兼容重排”存在内容和目录信息损失路径

**优先级 P0（先提示/拦截不安全输入），完整兼容扩展 P2；静态确认；证据 E01。**

[EpubImportReader.cs](../src/EasyPub.Core/EpubImportReader.cs) 的重排导入器只提取 `p/li/blockquote/pre/h1…h6` 等指定块元素中的文本。直接放在 `div`、`body` 或某些表格单元格中的文本可能漏掉；简单拼接文本节点也不足以表达全部换行与混排语义。

目录解析以去掉 `#fragment` 的文件路径作为键。同一个 XHTML 内的多个章节锚点会合并为一个键，导入时又按 spine 文件生成章节，不能完整保留这类目录结构。代码位置为第 54–56、96–119、416、460–461、491 行附近。

这针对兼容重排路径，不等于“保留原 EPUB 版式”也存在相同问题，更不等于所有 EPUB 转换都会丢字。

近期应检测不支持的结构并提示选择保留版式，不能继续把“未处理的文本”静默忽略。中期用“文档路径 + 锚点 + 层级”的目录模型表达一文件多章，补齐文本遍历和结构保留。

验收样本必须包含：div 正文、表格、br 换行、图片混排、脚注，以及同一 XHTML 内多个目录项。先明确支持范围，再决定是否扩大重排能力。

### F05：自定义控件样式尚未完整保留控件功能

**优先级 P1；静态确认，完整交互仍需专项验收；证据 E06。**

- 全局 ComboBox 模板没有 `PART_EditableTextBox`，而类别、语言仍设置 `IsEditable="True"`。这不是单纯外观问题，需要恢复编辑状态和输入能力。[App.xaml](../src/EasyPub.Desktop/App.xaml) 第 149–201 行；[MainWindow.xaml](../src/EasyPub.Desktop/MainWindow.xaml) 第 221、223 行。微软文档明确列出了该编辑部件的作用：[ComboBox 模板](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/combobox)。
- 主按钮沿用普通按钮悬停时的浅灰背景，但保留近白文字。按当前浅色主题色值计算，对比度约 **1.23:1**；这是配色计算，不是屏幕实拍测量。应给主按钮独立的悬停/按下状态。
- 窗口最小宽度是 1040，紧凑布局条件却是 `ActualWidth < 980`，正常缩放不会进入这个分支。[MainWindow.xaml.cs](../src/EasyPub.Desktop/MainWindow.xaml.cs) 第 4071 行。
- 部分状态仍直接使用 `Brushes.DarkOrange/SeaGreen/SlateGray`，绕过了主题资源；浅色和深色模式的可读性及语义容易不一致。

验收应覆盖普通、悬停、按下、禁用、键盘焦点、展开、可编辑、错误状态，而不只是“截图看上去统一”。

### F06：规则执行的超时、取消和错误定位需要统一

**优先级 P1；静态确认；证据 E01。**

自定义清理正则已有超时保护，这是优点。但自定义章节/层级正则还有未设置超时的构造路径，例如 [ChapterTree.cs](../src/EasyPub.Core/ChapterTree.cs) 第 206–207 行及 [LegacyTextParser.cs](../src/EasyPub.Core/LegacyTextParser.cs) 第 33、129–131 行。实际转换的清理调用也未传入外层取消令牌。

因此不能仅凭“运行在后台”保证可以及时停止异常规则。建议统一正则编译和执行策略，标明具体规则名、超时或语法原因、所在阶段；长循环检查取消，必要时为无法合作取消的外部工具使用独立执行 Adapter。

不用拿真实超长小说故意触发灾难性正则来证明卡死；可用受控超时测试和独立测试进程验证取消契约。

### F07：生成成功与验收成功仍混在统计里

**优先级 P1；静态确认；证据 E01。**

[BatchConverter.cs](../src/EasyPub.Core/BatchConverter.cs) 第 182 行的 `Succeeded` 仅表示有转换结果。即使结构验收含错误，最终仍走 Warning，主界面成功数量依据 `Succeeded` 统计，失败重试也不会自然包含这些任务。[MainWindow.xaml.cs](../src/EasyPub.Desktop/MainWindow.xaml.cs) 第 3464–3485 行。

应区分“已生成”“验收通过”“生成但验收未通过”“转换失败”“已取消”。结构未通过的文件可保留给排查，但不能与可交付成品混为一个成功计数。普通提醒也不应被全部升级为失败。

F01 进一步说明：结构验收本身不是正文完整性验收，两者应该分别显示。

## 五、UI：保持布局，建立一致的交互规则

现有暖色、低饱和、圆角风格可以继续使用。问题更多来自层级与状态规则不统一，而不是缺少装饰。

| 区域 | 建议 | 保留的现有设计与验收重点 |
| --- | --- | --- |
| 书库列表 | 复选框只改变批量集合；行点击改变当前查看书稿；全选明确是当前筛选结果还是全部书库，显示半选状态 | 不回退到点行就清空批量勾选；连续勾选/取消、Shift 操作、筛选后的隐藏已选项都应测试 |
| 右侧书稿 | 标题和已有前后切换控件可固定在滚动内容之外；显示“所选 2/5”，切书不改变勾选 | 保留完整封面大小；保持本书编辑目标明确，测试删除当前书、取消当前书和筛选变化后的退路 |
| 底部操作区 | 保留输出格式、排版方案和设置快捷入口；只显示一条当前最重要状态 | 不再堆重复设置按钮；闲置时不应伪装成任务进行中，已完成的这类调整保持即可 |
| 转换设置 | 保留五类统一入口，所有类别始终可发现；不适用的参数明确说明“仅 EPUB 输入/仅 MOBI 输出” | 不要求先选中某格式才看见设置；取消不影响实际配置，应用一次性提交，修改项和作用范围可见 |
| 应用设置 | 只放主题、密度、编辑器、窗口、默认目录等程序偏好 | 本次转换参数仍在转换设置；“保存为默认”与“仅应用本次项目”明确分开 |
| 自动检查区 | 折叠摘要显示开启数量，展开显示规则和范围；结果区区分待确认、已计划处理、已忽略 | 不把所有规则铺满首页，不把所有格式偏好都涂成警告色 |
| 任务中心 | 每条问题显示规则名、原文位置、建议动作及处理状态；处理后回到原问题位置 | 章节问题不导向清广告按钮；普通转换成功、验收错误、取消需要不同后续动作 |
| 收藏与更多菜单 | 延续当前统一样式，补齐键盘、焦点、子菜单、禁用和深色状态 | 不再只改单个顶层按钮；系统文件选择器保留系统行为，无须为了视觉一致强制重写 |

字体不建议继续反复“换一种字体、全局加粗”。应固定中文字体基线，正文用普通字重，标题少量半粗，图标字体独立；在 100%、125%、150%、200% 缩放和跨显示器场景比较 `Ideal`/`Display` 的实际结果。不能仅凭截图断言某一种渲染模式必然最好。

细滚动条应保留足够的拖拽命中区，滚轮、触控板和键盘仍可操作。主按钮和状态文字采用主题语义色，不单靠颜色传递结果；遵循微软关于键盘访问、焦点和对比度的建议。[Windows 无障碍说明](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-overview)

关键原则：**一套样式必须同时交付视觉状态和交互状态；一个设置必须同时交付作用范围和实际生效状态。**

## 六、功能投入：核心、辅助和不建议投入

### 真正值得继续深化的核心能力

| 方案 | 用户场景与价值 | 与现有能力结合 | 难度 / 阶段 | 验证方式 |
| --- | --- | --- | --- | --- |
| 可解释、可撤回的清理 | 用户担心漏广告，也担心小说对白被删；能看到依据、上下文及处理计划 | 在现有清理预览/排除机制上统一规则 ID、检测与执行，不另造一套扫描器 | 中；近期 | 广告正样本和正常对白负样本分别统计；不通过扩大删除范围换取表面命中率 |
| 正文完整性保障 | 用户最怕读到中途才发现缺段、缺章 | 将清理计划、章节树、插图和成品验收连接起来，记录有意删除与未覆盖片段 | 高；近期开始 | F01 的组合样本全部通过；无意丢失内容必须阻止交付 |
| 章节异常定位 | 超长小说里缺号、重复标题、误把广告识别为标题、卷内重编号很难人工找 | 章节树已有结构可供分析；只提出可定位的异常，不自动补正文或重排全书 | 中；中期 | 包含正常卷内重置、番外、重复章名的负样本；用户确认后才修改 |
| 可复用的转换方案 | 同一来源、同一阅读设备重复转换时不想重新设置，也不想影响下一批书 | 深化现有项目和预设，保存有效设置快照、版本及必要资源引用；补充迁移和缺资源提示 | 中；中期 | 换目录/重开项目/切换预设后结果可解释；不隐式覆盖本书元数据和排除项 |
| 一次整理、双格式输出 | 用户同时要 EPUB 留存/发送和 MOBI 侧载，不想重新跑全部清理和解析 | 同一不可变书稿快照分发给两个输出任务，各自有路径、进度和验收 | 中；中期 | 两份成品正文和章节语义一致；一种格式失败不毁掉另一种；与用户实际需求验证后再做 |
| 合集、拆卷 | 将若干本小说合成一个电子书，或把极长小说按卷拆开 | 复用章节树与元数据，但必须先解决稳定文本定位 | 高；后续 | “合集 → 单书 → 卷 → 章”层级、跨书上一/下一章、目录回跳、真机兼容逐项验证 |

合集仍属于转换器的合理延伸，但应作为独立操作：选书、排序、确认目录层级、输出。不要顺便引入收藏系统、系列数据库和复杂出版流程。深层目录在不同阅读器的表现应实测后限定，不能以格式能表达就保证设备都好用。

### 主要提升体验的辅助能力

- 显示检测到的编码和少量原文预览；疑似乱码时允许选择其他编码，不把所有可解码文件都视作文字正确。
- 导出“清理后的 TXT 副本”，满足用户想拿到实际整理文本的需求。它不同于修改源文件，也无需内置完整编辑器。
- 继续使用外部 TXT 编辑器；返回后清楚提示源文件变化、章节树失效及重新识别的后果。
- 补齐配置搜索、修改项标记、分组恢复默认；不是增加更多隐藏层级。
- 完成后打开文件夹、复制路径、导出简明诊断包；诊断包默认不含原文。
- 将现有 CLI 扩展为能复用项目或有效配置快照的批量入口，优先服务可复现和自动化测试；不急着把每个 UI 控件都映射为命令行参数。

这些能力有价值，但单独不构成用户放弃 Calibre 的理由。应以减少实际操作次数和返工验证，而不是增加功能计数。

### 当前不建议投入

- 云书库、账号、社交、推荐、在线商店和跨设备同步：不符合当前主要任务，且增加长期运维及隐私成本。
- AI 自动改写正文、默认把书稿上传识别广告：成本、误改和隐私问题明显；本地可解释规则仍有很大改进空间。
- 全功能内置文本编辑器或 EPUB 编辑 IDE：先把现有外部编辑和清理预览做好。
- 扫描 PDF OCR、大量低需求格式、复杂专业排版：只有获得稳定真实需求和测试语料后才考虑。
- 为了外观把 WPF 换成 Electron/WebView/新框架：当前缺陷主要是状态与数据契约，换技术栈不会自然解决。
- 一开始重写 KindleGen 或自研完整 MOBI 编译器：兼容性代价高。应先测阶段耗时、复用中间结果、减少编译输入开销。

## 七、前后端架构：整理真实复杂度，不做“大重构项目”

这里的前端是 WPF 界面，后端是本机 Core 和转换执行过程，不需要为此搭建服务器。

主窗口代码约 4,573 行，但行数本身不是质量判决。实际问题是：勾选、当前编辑对象、项目脏状态、清理设置、自动检查、转换启动和结果展示彼此耦合，增加一个入口就要同步修改多个地方。

按 codebase-design 的 Module/Interface/Seam 思路，建议逐步收拢以下真实复杂度：

| Module | 对外 Interface 应承担的责任 | 放入其中的 Implementation |
| --- | --- | --- |
| 书稿快照与处理计划 | 输入源版本与已选规则，返回处理后文本、位置映射、变更记录或明确失败 | 解码、行索引、章节和插图定位、规则顺序、跨行映射；调用方不再自行拼接 |
| 书稿检查 | 输入书稿快照、检查策略及处理计划，返回有范围、有状态、有位置的结果 | 规则目录、缓存、忽略/排除、已计划修复、必要条件和可选建议；界面只展示，不重新推导严重程度 |
| 转换任务计划 | 冻结本次目标书稿、有效设置和输出路径 | 应用默认、项目设置、本书覆盖的合并；检查与执行引用同一计划版本，运行期间的 UI 修改不污染已排队任务 |
| 成品提交 | 只交付完整成品，失败可恢复 | 临时文件、输出冲突策略、必要验收、原子提交、清理；EPUB/MOBI 使用同一契约 |
| 书库交互状态 | 明确批量书稿集合、当前查看书稿、筛选结果和任务状态 | 切书、勾选、删除、筛选后的稳定行为；与控件事件解耦后可单独测试 |

目标流程：

```text
原文件快照 → 清理计划及位置映射 → 章节/插图组织 → 固定转换计划
           → 临时成品 → 内容与结构检查 → 提交输出 → 可解释的任务结果
```

同一份书稿快照和规则目录被自动检查、预览、正式转换共享；并不意味着所有步骤都必须每次执行或所有检查都强制开启。

KindleGen 是明确的外部依赖，可以在 Seam 处使用真实执行 Adapter 与可控失败的测试 Adapter，分别验证真实兼容和超时/取消/落盘故障。纯内存的规则和状态逻辑直接测试，不必为每个小类增加一层抽象。

优先围绕 F01/F02/F03 提取这些 Module；每次提取都应修掉一个真实问题、替代一组重复逻辑。不要先改全项目 MVVM、再等待未来收益，也不要以减少主窗口行数为唯一目标。

## 八、性能：已有优化有效，下一步要测对瓶颈

以下是最后一轮探针结果，均在本机 Release 构建下获得：

| 书稿 | 大小与候选章节数 | 无应用缓存的默认自动检查 | 同配置缓存复查 | 开启 11 项内置布尔清理规则 |
| --- | --- | --- | --- | --- |
| A《国民法医》 | 11,662,993 字节；1,404 个候选 | 190 ms | 小于 1 ms | 463 ms |
| B 用户提供的另一小说 | 3,119,064 字节；367 个候选 | 48 ms | 小于 1 ms | 136 ms |

这是少量单次测量，不是 P95，也不是冷磁盘、冷启动、窗口打开或 MOBI 转换耗时。此前同条件近似测量有所波动是正常现象。全规则列不包含简繁转换和自定义规则；命中数量也不代表全部判断正确。

两本书的默认广告规则分别报告 2 处、8 处，原始文件 SHA-256 前后相同。这表明当前代码已经能对第二本书检测出多处广告，不能再沿用“完全没有识别”的旧结论；剩余重点是漏报/误报语料及结果是否准确呈现。

性能建议按收益排列：

1. **减少重复工作。** 当前缓存键序列化整个 `ConversionRequest`，自动检查配置与完整转换前检查不同；每本书又只保留最新键，可能相互淘汰。将源文本/章节分析与输出条件检查分层缓存，改输出目录不应重做所有正文规则。[ConversionPreflightCache.cs](../src/EasyPub.Core/ConversionPreflightCache.cs)
2. **控制批量内存。** 当前自动并发主要看 CPU 数和是否含 MOBI，没有按书稿/图片规模估算内存。超长书与小书混合时，限制重任务并行数量比单纯提高最大并发更稳。[ConversionConcurrencyPolicy.cs](../src/EasyPub.Core/ConversionConcurrencyPolicy.cs)
3. **保留虚拟化与节流。** 章节原文和清理差异按需取片段，不为更新统计重新构建全部 UI 对象；先用性能跟踪确认分配热点，再考虑池化等优化。
4. **分阶段计时。** 区分读取、解码、清理、章节组织、图片、EPUB 打包、KindleGen、MOBI 后处理及验收。用户的整体用时不能一概归因于 KindleGen。
5. **清晰的暂停/取消语义。** 现有暂停主要暂停新任务派发，已运行的转换继续完成，应写清楚；取消则要贯穿本机处理和外部工具。
6. **单文件包冷启动单独测。** 当前发布启用单文件压缩和自包含运行时；是否影响首次启动需要测量，不能据此直接认定是卡死原因。只有数据证明收益后才调整包结构。

后续建立 1 MB、10 MB、50 MB、千章/万章及多书混合样本，记录总耗时、UI 线程停顿、峰值内存、取消响应和缓存命中率。基准必须注明硬件、设置、缓存状态；不能用某次快几秒替代可重复的性能结论。

## 九、验收、可靠性和输入安全

测试数量不是当前最大的缺口，**跨功能组合和最终内容语义**才是。

建议建立三层自动验证：

- 纯逻辑：规则范围、错误分类、忽略/恢复、批量选择与焦点、配置合并。
- 跨 Module：清理增删行 + 已存章节树 + 章节重排 + 插图；EPUB 多锚点目录；错误规则 + 取消；故障注入 + 覆盖旧成品；验收失败 + 重试。
- 成品：实际解包比对规范化正文片段、章节归属、目录锚点、图片及资源引用。仅比字数也不够：遗漏与重复可能相互抵消。

样式测试应补上真实键盘与输入行为，以及 100%–200% DPI、窄窗口、深浅色、长书名/路径/菜单、零本/一本/多选/正在转换/错误等状态。现有测试已有窗口实例与交互检查，应在此基础上扩展，不需要把它们说成全是文本搜索测试。

Kindle 兼容分四级记录：生成成功、结构检查、Previewer、具体型号/固件/传输方式的真机确认。此前用户确认的章顶导航行为应成为固定回归样例；涉及锚点、分页、压缩合并等变更，必须同时测试普通与长篇优化路径。

EPUBCheck 可作为可选标准验收器，先集成在开发/发布流程，再根据体积和运行依赖决定是否提供给用户。它验证 EPUB 规范符合性，不证明中文内容完整或 Kindle 点击行为正确。[官方仓库](https://github.com/w3c/epubcheck)

输入安全方面，当前 EPUB XML 解析已禁用外部解析器，这是应保留的基础措施。进一步建议评估压缩包解压量/条目数、图片尺寸、字体与外部资源路径、自定义正则耗时等资源上限；这是加固清单，不是在没有复现的情况下宣称存在漏洞。

日常检查和预览继续不修改原文；诊断包、日志和问题反馈默认脱敏路径、不携带整本书。项目只引用外部文件时，要清楚说明“保存项目不等于备份了源书稿与封面”。

## 十、发布、维护和用户信任

当前本地包的 `FileVersion` 为 `1.19.5.0`，产品版本包含 `1.19.5+79e1ba9…`；但源码项目版本、主窗口和安装脚本仍分别使用 1.19.0/v1.19/1.19。发布时覆盖版本号能生成正确 EXE，却仍容易让用户分不清手上的修复版。

建议：

- 版本号从一个来源生成，窗口、关于页、EXE、ZIP、安装器与更新记录一致；预览版加明确后缀。
- 正式版本从已提交状态构建，记录提交、SDK、构建参数、KindleGen 版本和包哈希。仅记录同一个提交哈希不足以区分多次未提交构建。
- 本地仓库未发现 `.github/workflows`；应建立构建、测试、成品样例验收和打包的持续检查，而不是每次靠临时命令回忆发布步骤。
- 本次检查的 v1.19.5 EXE 未签名。签名可作为后续分发信任投入，但不能承诺一签名就消除所有 SmartScreen 提示；近期先做好明确来源、校验值和一致版本。
- 仓库根目录未发现许可证文件。应厘清项目自身许可证及 KindleGen、字体、图片等第三方分发说明；本报告不据此判断任何分发行为违法。
- 安装版和便携版分别验收：全新用户目录、无开发 SDK、带空格/中文的路径、覆盖升级、项目恢复及用户配置保留。
- README 保留正式发布基线是合理的；只有实际发布新版本时才同步说明，不把尚未发布的本地能力写成已交付事实。

GitHub/下载页应先回答：它适合谁、支持哪些真实输入输出组合、最短转换步骤、源文件是否会改、EPUB 与 MOBI 分别怎么使用、遇到问题去哪看。用一个自行创作的小样本演示“广告被定位 → 用户确认 → 章节正确 → 成品可读”，比堆大量选项截图更有说服力。

不要把“兼容原版”“结构验收通过”“支持 Kindle”写成没有范围的保证。可信的限制说明，本身就是让用户愿意长期用下去的一部分。

## 十一、建议实施顺序和完成标准

P0 表示下次正式发布前需要消除或可靠拦截的风险；P1 为下一轮质量收口；P2 为之后增益；P3 为暂缓。难度是相对工程复杂度，不是工期承诺。

| 顺序 | 工作 | 难度 | 完成标准 |
| --- | --- | --- | --- |
| P0-1 | F01 章节树与跨行清理定位 | 高；近期安全拦截较低 | 对照样本及组合回归不丢正文；不支持的组合明确停止 |
| P0-2 | F03 统一安全落盘 | 中 | 取消/写入失败时原成品不变；不把半成品当完成结果 |

可以分成三个小版本：第一版专注安全与检查一致性；第二版做交互、取消、发布及性能观测；第三版再挑一两个转换能力增强。每版明确“不改什么”，避免再次同时触碰清理、导航、布局、状态和发布流程而难以定位回归。
