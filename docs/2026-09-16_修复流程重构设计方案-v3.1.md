## 0. 本版摘要

v3 的主干不再改动。v3.1 只做四件事：

1. **补两个未闭合的事务边界**（评审 P0 两条）：持久化 `RepairExecutionManifest`；引入 `RepairDecision`，让编译器不再做用户语义决策。
2. **修正 v3 的 2 处硬错误**：§16 的写权限合取条件写成了析取；`RepairCandidate` 不是「候选动作」而是一次完整修复方案，名不副实。
3. **形式化 6 个此前只有叙述的概念**：manual 保护改为结构边界保护区、`SourceAnchor` 改判别联合、换行插入算法定死、metadata 迁移要求幂等、verifier 改为字节判等、`TreePatch`/`Canonical` 前移。
4. **补 3 条评审未提及、但会真实咬人的问题**（见 §10）：清单过期校验、软崩溃的恢复判据、动作语义影响面表（评审 P1-5 只看到 `HeadingOrigin` 一处，实际还有两处）。

**结论：v3 的架构判断经复核成立；本版之后可以按 Phase 0 → 6 实施，不需要 v4。**

### 1.2 采纳但需修正的（1 条）

**评审 §3 的 `SourceEffectDecision` 只有 `None` / `ApplyIfAvailable` 两个值，不够。**

考虑三种真实情形：

| 情形 | 用户勾选 | 期望 |
|---|---|---|
| A. 只想排除重复副本，保留 TXT | `Selected = true` | 树里排除，原文不动 |
| B. 确认物理删除重复副本 | `Selected = true` | 树里排除 + 删 TXT |
| C. **勾了「删 TXT」但该动作没有可靠 `SourcePatch`**（v3 §6 的「证据不足」） | `Selected = true` | **必须在写盘前失败，不得静默降级** |

两值枚举只能表达 A/B。C 若静默降级为 A，用户在写盘之后才发现要删的行还在，而这种错误无法靠事后校验发现（两模式对照会「通过」，因为降级确实自洽）。

**v3.1 定义**：

```csharp
public enum SourceEffectDecision
{
    None,                 // 语义上不需要动原文
    ApplyIfAvailable,     // 希望动原文；无可靠 SourcePatch 时 → 树级落地并明确标注
    ApplyRequired         // 必须动原文；无可靠 SourcePatch 时 → 整个编译失败，拒绝写盘
}
```

`ApplyIfAvailable` 与 `ApplyRequired` 的区别是**失败时机**，不是失败与否：

- `ApplyIfAvailable` → 编译成功，`manifest.SourcePatch == null`，UI 标「本项不改原文」，`SourceEffectOutcome = Downgraded`
- `ApplyRequired` → 编译失败，预览期就报「所选动作无法可靠改原文，请取消勾选或改选其他项」

这正是评审想要的「用户意图不得被 executor 重新解释」，只是把 `ApplyIfAvailable` 的降级从**隐式**改成**显式记录在 manifest 里**（见 §2.3 的 `SourceEffectOutcome`）。

## 2. P0：`RepairExecutionManifest`

### 2.1 问题确认

评审的推导链条成立，且我核对 v3 §11.1 后确认属实：事务目录只有

```text
transaction.json      # schemaVersion, transactionId, sourcePath, candidateId,
                      # baseSourceSha256, expectedNewSha256,
                      # baseTreeFingerprint, recognitionFingerprint, state, ...
source-patch.json
receipt-draft.json
```

`transaction.json` 里没有 `TreePatch`，也没有用户选择。于是：

```text
1. 用户确认 → 2. SourcePatch 生成 → 3. TXT 已替换为 NewSha
4. journal = SourceReplaced → 5. 崩溃
```

重启后有 `SourcePatch`、`CandidateId`、新旧 SHA，但**不知道目标章节树是什么**。

不能重新规划：源已是 `NewSha`，planner 当初基于 `BaseSha`；章节树可能仍是旧版本；重算得到的结果不保证等于用户当时确认的内容。

> 「知道 SourcePatch 已执行」≠「知道目标章节树应该是什么」——这一句是全部问题的准确表述。

### 2.2 定义

```csharp
public sealed record RepairExecutionManifest(
    int SchemaVersion,
    string TransactionId,
    string ProposalId,
    RepairBaseVersion BaseVersion,
    IReadOnlyList<RepairDecision> Decisions,
    IReadOnlyList<RepairDecisionSnapshot> DecisionSnapshots,  // 见 §2.3
    TreePatch TreePatch,
    SourcePatch? SourcePatch,                                 // TreeOnly 落地时为 null
    CanonicalChapterModel ExpectedCanonicalResult,
    string? ExpectedNewSha256,
    NewLinePolicy NewLinePolicy,                              // 见 §8
    string BaseSnapshotPath);                                 // 恢复时渲染所需的源快照
```

事务目录：

```text
<book>/.easypub/journal/<transaction-id>/
    transaction.json           # 轻量状态机字段，高频更新
    execution-manifest.json    # 提交前写死，之后只读
    receipt-draft.json
    temp/
```

**写入时机（硬规则）**：

> `execution-manifest.json` 必须在**任何源文件替换之前**写完、flush 完（含目录项），此后视为不可修改。

分配在 v3 §10.3 步骤序列的 **D 之前**（`Prepared` 状态内），即：

```text
C. 创建 journal（transaction.json = Prepared）
D. 写 execution-manifest.json + flush     ← 新增，且此后不可变
E. Render temp（原编码 / 原换行 / 原 BOM）
F. flush temp；计算 ExpectedNewSha → 回填 transaction.json（不回填 manifest）
...
```

`ExpectedNewSha256` **不写进 manifest**，写进 `transaction.json`。因为它在 D 时刻还不存在；manifest 保持「提交前完全确定」的性质。`manifest.ExpectedNewSha256` 字段保留为 `null` 并在恢复时以 `transaction.json` 为唯一来源——或者更干脆：从 manifest 中删除该字段。**v3.1 选择删除。**

### 2.3 决策快照：保持 manifest 自足

`RepairDecision` 引用 `ActionId`，而 `ActionId` 指向 planner 产出的动作。崩溃重启后 planner 已不在内存中，为了「不让 executor 重新解释用户意图」，manifest 必须自足——不能要求重启后再去问 planner「ActionId X 是什么动作」。

```csharp
public sealed record RepairDecisionSnapshot(
    string ActionId,
    RepairActionKind Kind,
    string? SemanticTarget,        // 章节语义 ID，非物理行号
    string? DesiredValue,          // 例如目标标题
    int? SourceAnchorLine,         // 例如替换/删除所在原始行
    bool Selected,
    SourceEffectDecision SourceEffect,
    SourceEffectOutcome Outcome);  // 编译后的实际结果

public enum SourceEffectOutcome
{
    NotRequested,   // SourceEffect = None
    Applied,        // 有 SourcePatch 覆盖本动作
    Downgraded,     // 请求了但无可靠 SourcePatch，已明确标注
    NotApplicable   // 本动作本就只改树
}
```

`Decisions` 保留为正式决定记录，`DecisionSnapshots` 为冗余快照。看起来重复，但**冗余是刻意的**：恢复路径只读 manifest，不需要能重建 planner；`Decisions` 供 receipt 与审计对账使用。

### 2.4 恢复流程

```text
journal = SourceReplaced
    ↓ 读 execution-manifest.json（不重新规划）
    ↓ 校验 BaseVersion.BaseSourceSha256 与 BaseSnapshotPath 指向的快照字节一致
    ↓ 校验当前源文件 SHA == transaction.ExpectedNewSha256
    ↓ ChapterTreeDocument.LoadAsync(新源)          ← 得到新坐标
    ↓ 丢弃 manifest 中的物理行号，改用 SourceCoordinateMap
    ↓ 物化 TreePatch（按 SourceBinding 解析，见 §12.2）
    ↓ 校验 Canonical(物化结果) == manifest.ExpectedCanonicalResult
        ├─ 相等 → 继续 SourceVersionTransition
        └─ 不等 → Conflict，停止自动恢复，保留全部证据
    ↓ SourceVersionTransition（幂等，见 §9.2）
    ↓ documentReloaded → stateMigrated → committed
```

**关键区别**：v3 的恢复只能「继续重载与状态迁移」，目标是未知的；v3.1 的恢复有 `ExpectedCanonicalResult` 作为**判据**，物化错了会当场发现而不是静默产出一棵错误的树。

### 2.5 撤销的选择与备份一致性

`SourceEffectOutcome = Downgraded` 的项在 receipt 中必须与 `Applied` 分列。用户从备份恢复旧版本后，`Downgraded` 项的存在解释了「为什么这一项当时没生效」。

## 3. P0：`RepairDecision` —— 编译器不得再做用户语义决策

### 3.1 问题确认

v3 §6 的表格里写着：

> `RemoveDuplicate` …… **仅在用户显式确认「从 TXT 删除」时**产生 `DeleteOriginalLine`

而 v3 模型只有三个维度：

```text
RepairAction + Selection + LandingMode
```

「是否物理删除」**没有存放位置**。若编译器看到 `LandingMode == EditSource` 就自行决定生成 `Delete`，那么它就替用户做了决定——这正是 v2 被批评、v3 声称已修掉的问题。

评审说这是「隐式第三维度」，准确。

### 3.2 定义

```csharp
public sealed record RepairDecision(
    string ActionId,
    bool Selected,
    SourceEffectDecision SourceEffect);
```

编译器变为**纯函数**：

```csharp
public static RepairPlanCompiler.Result Compile(
    RepairProposal proposal,
    IReadOnlyList<RepairDecision> decisions);
```

```
Compile(proposal, decisions) → { TreePatch, SourcePatch? }
```

**此后结果完全冻结。** `LandingMode` 不再参与「产生什么 patch」：

```text
TreeOnly   → 提交 TreePatch
EditSource → 提交 TreePatch + SourcePatch（若 SourcePatch 为 null 则退化为 TreeOnly 并标注）
```

### 3.3 每个动作的默认 `SourceEffect`

| RepairAction | 默认 `SourceEffect` | 理由 |
|---|---|---|
| `RetitleChapter` | `ApplyIfAvailable` | 用户要求标题改成 X，原文标题不同则应改 |
| `AdoptHeading` | `ApplyIfAvailable` | 仅当需要规范化行文本 |
| `InsertHeading` | `ApplyIfAvailable` | 原文无标题行，改原文才有标题行 |
| `RemoveDuplicate` | `None`（默认）/ `ApplyRequired`（用户显式确认删除时） | 默认只排除，不删 TXT |
| `DemoteHeading` | `ApplyIfAvailable` | 见 §10.3，此项语义需重新定义 |
| `AddChapter` | `None` | 标题已在原文中 |
| `BuildVolumeLevel` | `None` | 只建树 |
| `KeepExtra` / `MissingBody` / `OutOfOrderFinding` | `None` | 只报告 |

**确认窗必须为默认 `None` 的动作提供二级开关**（v3 §6 已要求，v3.1 补齐承载它的数据类型）。

### 3.4 与 v3 自定规则的一致性

v3 §0.2 已声明：

> 动作语义固定，每个动作编译出 `TreePatch` 与可选的 `SourcePatch` 两套产物，落地模式只决定「用哪套」。

`RepairDecision` 是这条声明的**必要实现**：没有它，「用哪套」这句话里藏着一次未建模的用户决策。评审的修正是把声明补成真的。

## 4. `RepairCandidate` → `RepairProposal`

v3 同时写了：

```csharp
public sealed record RepairCandidate(string Id, RepairPlanBasis Basis,
    RepairBaseVersion BaseVersion, IReadOnlyList<RepairAction> Actions);
```

以及主链：

```text
IReadOnlyList<RepairCandidate> → RepairReviewWindow
```

「多个 Candidate，每个 Candidate 内又有多个 Action」——语义不清，且直接影响 `Selection` / `CandidateId` / receipt / journal / UI 勾选的粒度。

### 4.1 处置

v3.1 采用评审建议的前者：**它代表「一次完整预览」**，改名 `RepairProposal`。

```csharp
public sealed record RepairProposal(
    string Id,
    RepairPlanBasis Basis,
    RepairBaseVersion BaseVersion,
    IReadOnlyList<RepairAction> Actions);
```

`RepairAction` 保持「一条候选修改」的语义不变，并持有自己的 `ActionId`（§12.1）。

### 4.2 为什么必须是一个 Proposal 而非多个

因为**用户面对的是一次勾选集合**：勾选状态、`Selection`、`Decision[]` 都以「本次预览」为单位提交。若有多个并行 Proposal，就会出现「A 的 proposal 未勾选项与 B 的动作冲突」这类必须额外定义的问题。当前 UI（`RepairReviewWindow` 一张表）本来就是一个 Proposal 的呈现形式。

若将来「有目录修复」与「本地发现」确需分两次确认，做法是**同屏两个分区、一次提交**，而不是两个 Proposal 类型。

## 5. `CanonicalChapterModel`：只表达业务语义

### 5.1 问题确认

v3 的 canonical 含 `HeadingOrigin`。若该枚举用 `Virtual / Physical` 表达落地实现，则：

```text
Canonical(TreeOnly)  ≠ Canonical(EditSource)
```

因为 `InsertHeading` 在 TreeOnly 下是 virtual heading、在 EditSource 下是 physical heading。这与 v3 §7 声明的核心不变量**直接冲突**。

评审的判断正确。

### 5.2 定义

```csharp
public enum CanonicalHeadingOrigin
{
    ExistingSourceHeading,   // 原文本就有这一行标题
    InsertedByRepair,        // 本次修复新增的章节标题
    AdoptedByRepair,         // 本次修复决定把已有行解释为标题
    Manual                   // 用户手工编辑产生/确认
}
```

`InsertHeading` 在两种落地下一律为 `InsertedByRepair`。**`Virtual` / `Physical` 属存储层，不得进入 canonical。**

### 5.3 补树结构字段

v3 的 canonical 只有 `Title / Level / IncludeInToc / HeadingOrigin / BodyContentHashes`，不足以区分「标题相同、层级相同、正文相同，但父节点归属不同」的两棵树。

```csharp
public sealed record CanonicalChapter(
    string Title,
    int Level,
    bool IncludeInToc,
    CanonicalHeadingOrigin HeadingOrigin,
    CanonicalNodeKind Kind,               // Chapter | Volume | FrontMatter
    bool IsFrontMatter,
    IReadOnlyList<int> ParentPath,        // 从根到父节点的序号路径
    IReadOnlyList<string> BodyContentHashes);
```

**附注（评审未提及）**：`BodyContentHashes` 必须是**物化后树的正文归属**，不是原始源文件的字节。这一点决定了 `RemoveDuplicate` 在两模式下能否相等——见 §10.3。

## 6. manual 保护：结构边界保护区

### 6.1 问题确认

v3 §16.1 写的是：

> `manual` 条目**所在行区间**，以及其**前后各一行**，禁止任何 `SourcePatch` 触碰。

对一个 `TitleLine = 5000`、`ContentRange = 5001..6500` 的手工章节，这会锁死 `4999..6501`——1303 行。若一本手工修过的书中有若干长章节，`EditSource` 基本失效。

评审是对的。而且这条规则在 v3 里连「所在行区间」都没定义（是 `TitleLine` 单行？`TitleLine ∪ ContentRanges`？），是实现歧义。

### 6.2 定义

```csharp
public sealed record ManualGuardZone(IReadOnlyList<SourceLineRange> ProtectedRanges);

public static ManualGuardZone Build(IReadOnlyList<ChapterTreeEntry> entries, int radius = 1);
```

对每个 `RecognitionSource == Manual` 的条目，保护以下边界及其 `± radius` 行：

```text
TitleLine                  （若有）
ContentRange.Start         （每个区间）
ContentRange.End           （每个区间）
Virtual/manual anchor      （若有）
以及紧邻上述边界的连续空白 separator 行
```

对 `radius`：

- **默认 `1`**
- 设置项暴露为 `1 / 2`，默认 `1`
- 第一期取保守值 `2`（评审建议）也可，但必须与设置项一致且写进测试

**规则**：

```text
Delete / Replace 命中 GuardZone → 拒绝（该动作在 EditSource 下降级或失败，按 SourceEffect 决定）
Insert anchor 落在 GuardZone  → 拒绝
正文中间行（非边界）          → 不自动禁止
```

**保护的语义**：

> 人工确认过的章节**边界**，而不是「manual 章节的全部内容」。

这同时解决了 v3 那条规则「保护范围无定义」的问题——边界是可枚举的有限集合。

### 6.3 与 §16 禁用条件的关系

v3 §16 第 5 条「动作会触及无法可靠映射的手工结构」现在有了可计算的定义：**命中 `ManualGuardZone`**。

## 7. `SourceAnchor`：判别联合

### 7.1 问题确认

```csharp
public sealed record SourceAnchor(int OriginalLine, AnchorPlacement Placement, int Ordinal = 0);
public enum AnchorPlacement { Before, After, EndOfFile }
```

非法状态：

```text
OriginalLine = 123, Placement = EndOfFile     ← 无意义
OriginalLine = 0,   Placement = Before        ← 0 不是合法源行
```

且**空文件根本无法表达**（不存在任何 `OriginalLine`）。

### 7.2 定义

```csharp
public abstract record SourceAnchor
{
    public int Ordinal { get; init; }
}

public sealed record BeforeOriginalLine(int Line, int Ordinal = 0) : SourceAnchor;
public sealed record AfterOriginalLine (int Line, int Ordinal = 0) : SourceAnchor;
public sealed record EndOfFileAnchor   (int Ordinal = 0)           : SourceAnchor;
```

构造时校验：

```text
Line >= 1 && Line <= baseSnapshot.LineCount
```

非法状态无法构造。空文件只有 `EndOfFileAnchor` 一种可能，天然合法。

### 7.3 对 `SourceCoordinateMap` 的影响

`InsertedOperationToNewLine` 的 key 不变（`OperationId`）。但插入顺序排序键由 `(Anchor, Placement, Ordinal, OperationId)` 变为 `(Anchor 判别类型, Line, Ordinal, OperationId)`，实现更直接。

## 8. 换行符：定死算法

### 8.1 问题确认

v3 说「插入行使用附近主导换行符」，这句话至少有三实现：

```text
A. 取上一行
B. 取下一行
C. 前后 10 行多数
```

同一计划在不同实现下产生**不同 `ExpectedNewSha`**，那么 `ExpectedNewSha` 就不能作为严格可重复的事务结果，§2.4 的恢复校验也随之不可靠。

### 8.2 定义

**行模型**：源文件按行终止符切分。`Line(N).Terminator ∈ { CRLF, LF, CR, None }`。最后一行允许 `None`（文件末尾无换行）。

**文件级 `DefaultNewLine`**（在事务开始时确定一次，**持久化**）：

```text
DefaultNewLine = 文件中第一个出现的行终止符
若文件中不存在任何行终止符（单行文件） → CRLF
```

**插入行使用的换行符**：

```text
BeforeOriginalLine(N):
    N > 1                → Line(N-1).Terminator
    N == 1               → Line(1).Terminator，若为 None → DefaultNewLine

AfterOriginalLine(N):
    Line(N).Terminator  若不为 None → Line(N).Terminator
    否则                            → DefaultNewLine

EndOfFileAnchor:
    若原文件最后一行 Terminator == None：
        先补一个 DefaultNewLine（把原最后一行终结掉）
    所有新增行使用 DefaultNewLine
    新增的最后一行 Terminator = None（保持「末尾无换行」的形态）
```

**持久化要求（硬规则）**：

> `DefaultNewLine` 与「原文件末行是否有终止符」必须写入 `transaction.json` 与 `execution-manifest.json`，恢复时**读取而非重算**。

理由：崩溃后重算 `DefaultNewLine` 若与当事事务不同，`ExpectedNewSha` 必然不符，恢复会永久卡在 `Conflict`。这不是理论风险——`CRLF` 文件被编辑器转成 `LF` 后再崩溃就会命中。

### 8.3 可测性

必须写成表驱动测试，覆盖：

```text
全 CRLF / 全 LF / 全 CR / 混合（首行 CRLF 后 LF）/ 单行无终止符
/ 末行无终止符 / 空文件（0 行）/ 仅一个换行符（1 空行）
```

每例断言：渲染字节、`DefaultNewLine`、末行终止符、以及**二次渲染字节完全相同**。

## 9. 三处安全与验证修正

### 9.1 `EditSource` 写权限 preflight（v3 确为错误）

v3 §16 第 6 条：

> 6. 源目录与备份目录**都**不可写

这是**析取→合取写反**。举反例：源目录只读、备份目录可写 → 按 v3 不触发禁用，但实际上根本无法执行 `EditSource`（无法在源目录建同目录 temp）。

**v3.1 定义**：

```csharp
public sealed record SourceEditPreflight(
    bool CanReplaceSourceFile,
    bool CanCreateSiblingTemp,
    bool CanWriteJournal,
    bool CanWriteBackupTarget);

public static bool CanEditSource(SourceEditPreflight p) =>
    p.CanReplaceSourceFile && p.CanCreateSiblingTemp
    && p.CanWriteJournal && p.CanWriteBackupTarget;
```

任一失败 → 禁用 `EditSource`，**且必须在确认窗显示具体哪一项失败**（而不是笼统的「无法改原文」）。

同时修正 v3 §12.3 的连带问题：

> 源目录不可写时回退到 `%LOCALAPPDATA%`

在 `EditSource` 语境下这条**不再成立**，因为源目录必须可写才能替换源文件（§9.1 已要求）。所以：

- 备份位置默认仍在 `<书稿目录>/.easypub/backup/`，保留 v3 §12.1 的全部安全属性
- 用户把备份位置改到别处时，若**无法在源目录写入指针**，则 `CanWriteJournal = false` → 禁用 `EditSource` 并说明原因
- `%LOCALAPPDATA%` 回退仅保留给**只读** 场景（`TreeOnly` 下的树计划备份），不再与 `EditSource` 混用

### 9.2 metadata 迁移必须幂等

**问题**：`project` / `catalog` / `recovery state` 不可能作为一次真正的文件系统原子事务提交。可能出现：

```text
Catalog(NewSha) 已保存 → Project 未保存 → 崩溃
journal 仍停在 DocumentReloaded
```

重启后必须**重跑整个 transition**。

**v3.1 新增不变量**：

> `SourceVersionTransition` 的每一步必须满足 **Idempotent（重复执行一次 ≡ 只执行一次）**、**Postcondition-verifiable**、**Safe to retry**。

| 步骤 | 幂等实现 |
|---|---|
| `SaveCatalog(NewSha)` | 已存在且内容相同 → success |
| `InvalidateCache(path)` | 重复执行 → success |
| `ClearUndoRedo()` | 重复执行 → success |
| `ClearConfirmedReviews()` | 重复执行 → success |
| `SaveChapterTreePlan(NewSha)` | 同版本覆盖写 → success |
| `SaveRecoverySnapshot(NewSha)` | 同版本覆盖写 → success |

**恢复流程不得依赖「上次执行到哪个 metadata 子步骤」**，必须允许从 `DocumentReloaded` 重跑完整 transition。

### 9.3 verifier：字节判等为一级验证

**问题确认**：这本书本身就有大量重复标题、重复正文、重复章节块。普通 LCS/Myers 行 diff 在重复内容附近存在多组同样合法的对齐。例如两个完全相同的 55 行块，「删前一个」与「删后一个」的 diff 结果未必稳定表达实际删的是哪一份。

§19.7 第 2 条「receipt patch == 实际文件 diff」把 diff 当成了正确性判据，评审指出应当降级。

**v3.1 定义**：

```text
一级验证（correctness oracle）：
    ExpectedBytes = Render(BaseSnapshotBytes, SourcePatch)
    ExpectedBytes == TempBytes
    ExpectedBytes == FinalSourceBytes

二级验证（可读性 / 审计）：
    receipt 直接由 SourcePatch + SourceCoordinateMap 生成
    通用文本 diff 仅用于 UI 展示
```

即 §19.7 改为：

| # | 不变量 | 判据 |
|---|---|---|
| 1 | preview patch == 提交 patch | 对象判等 |
| 2 | **temp bytes == 由 base snapshot 渲染的 expected bytes** | 字节判等 |
| 3 | **最终源文件 bytes == expected bytes** | 字节判等 |
| 4 | 未被 patch 涉及的原始行文本逐行不变 | 逐行判等 |
| 5 | 每个 `Replace/Delete` 的旧内容满足预条件 | `ExpectedOldText` 判等 |
| 6 | 新文件 SHA == `transaction.ExpectedNewSha` | SHA 判等 |
| 7 | reload 后 `ChapterTreeDocument.LoadAsync` 成功 | 无异常 |
| 8 | 新 `ChapterTreePlan.SourceSha256` == NewSha | 判等 |
| 9 | 物化树 `Canonical` == `manifest.ExpectedCanonicalResult` | canonical 判等 |
| 10 | 第二次运行同一修复入口不再产生已完成动作 | 计划为空 |

原第 2 条（receipt == 实际 diff）删除，receipt 改为**生成物**而非**验证对象**。

## 10. 评审未提及的 3 个问题

### 10.1 manifest 必须校验计划的时效性

`RepairExecutionManifest` 冻结了 `TreePatch`，但**没有冻结它所依据的树**。

崩溃恢复路径：

```text
journal = SourceReplaced → 读 manifest → Apply(manifest.TreePatch, 新 document)
```

若在此期间（同一次事务内、替换之后、物化之前）发生软崩溃（进程被挂起后恢复，内存中 `ChapterTreeDocument` 已被其他地方改过），`TreePatch` 的 `SourceBinding` 所指的原始行可能不再对应同一章节。

**修正**：`BaseVersion` 的三个 fingerprint 在恢复路径上**仍须校验一次**（对 `BaseSnapshotPath` 指向的快照重新计算），而不是只在提交前校验。恢复流程 §2.4 已包含这一步；此处明确它是**硬性前置**，不是可选优化。

### 10.2 软崩溃的恢复判据（journal 状态与磁盘状态不一致）

v3 §11.2 的恢复表把 journal 状态作为唯一判据，但 journal 是**我们自己写的**，它可能与磁盘真实状态不一致。

具体风险：`File.Replace` 在 NTFS 上是原子的（对读取者要么旧要么新），所以「文件半写」不是主要问题。真正的问题是：

```text
journal = SourceReplaced  ，但磁盘 SHA 仍是 BaseSha
    → 说明替换本身没成功，或 journal 先于替换被更新
journal = TempWritten      ，但磁盘 SHA 已是 ExpectedNewSha
    → 说明替换成功但 journal 更新丢了
```

**v3.1 恢复决策表**（journal 状态 × 磁盘实际 SHA → 动作）：

| journal 状态 | 磁盘 = BaseSha | 磁盘 = ExpectedNewSha | 磁盘 = 其他 |
|---|---|---|---|
| `Prepared` | 放弃（零副作用） | **异常**：Conflict | Conflict |
| `BackupCreated` | 放弃或继续 | **异常**：Conflict | Conflict |
| `TempWritten` | 继续替换 / 放弃 | 视为已替换 → 走恢复物化 | Conflict |
| `SourceReplaced` | 重新执行替换 | 走恢复物化 | Conflict |
| `DocumentReloaded` | **异常**：Conflict | 重跑 transition（幂等） | Conflict |
| `StateMigrated` | **异常**：Conflict | 完成最终检查 → `Committed` | Conflict |
| `Committed` | **异常**：Conflict | 清理 temp，保留 receipt | Conflict |

标 **异常** 的格子含义：journal 声称已完成的事，磁盘却显示没做——说明有第三方改动或磁盘层问题，**一律进 `Conflict` 并要求人工处理**，绝不自动推测。

这张表也顺带定义了 v3 §16 第 8 条「当前 SHA 既非 BaseSha 也非 ExpectedNewSha → 进 Conflict」的完整边界。

### 10.3 动作语义影响面表（评审 P1-5 只看到 `HeadingOrigin` 一处，实际还有两处）

评审指出 `CanonicalHeadingOrigin` 不得含存储层概念。方向对，但**根因更普遍**：v3 §6 的映射表在三个动作上，`TreePatch` 与 `SourcePatch` 的语义是**不可互换**的，不只是 `HeadingOrigin` 一个问题。

逐项复核 v3 §6：

| 动作 | v3 的 `SourcePatch` | 问题 |
|---|---|---|
| `DemoteHeading` | **空**：「不删除标题行，只让新树不把它当标题」 | **真问题**。`EditSource` 下不删标题行 → 保留该行文字，但删掉章节条目后它归入前一章的正文范围；而 `TreeOnly` 下该行本来就在正文范围里。**结果看起来一致**，但 `Level` 变化时（章节降为小节）语义不同；且「文字并回正文」在字节层面并未发生。更关键的是这句话本身自相矛盾：删掉条目后该行到底归谁，v3 没有规定 |
| `AdoptHeading` | 仅当需要规范化文本时产生 `ReplaceOriginalLine` | **真问题**。若标题行被采纳但正文割点未定义，`EditSource` 下插入的行归属与 `TreeOnly` 下的虚拟归属可能不同 |
| `InsertHeading` | `InsertLineAtAnchor` | **有隐式依赖**。正文割点（哪些原始行属于新章节）在 v3 未作为动作字段显式定义 |

**修正一：正文归属与物理行号解耦（这是 §5.3 附注的形式化）**

> `CanonicalChapter.BodyContentHashes` 必须由**物化后树的正文归属**计算，不得由原始源文件字节计算。

两类模式的物化结果应当相同，因此 canonical 相同。若 `TreeOnly` 与 `EditSource` 的物化结果在本定义下仍然不同，那就是**真实缺陷**，应当暴露而不是靠放宽 canonical 掩盖。

**修正二：`InsertHeading` 必须显式携带正文割点**

```csharp
public sealed record InsertHeading(
    string ActionId,
    string Title,
    int Level,
    SourceAnchor Anchor,
    BodyCut Cut);                 // ← 新增，必填

// BodyCut: 明确新章节正文从哪个原始行开始、到哪个原始行结束
public sealed record BodyCut(int FirstLine, int LastLineExclusive);
```

`TreeOnly` 与 `EditSource` 使用**同一个 `Cut`**，因此两者的章节正文归属必然一致。v3 把这个信息留给「按锚点切分」的隐含推导，是等价性风险的来源。

**修正三：`DemoteHeading` 需要重新定义**

v3 的 `DemoteHeading` 混了两种语义：

```text
(a) 取消章节边界          → 只改树（Level 或移除条目）
(b) 文字并回正文          → 必须改原文（删掉那一行标题）
```

`EditSource` 下的「并回正文」在物理上是**该行文字必须出现在正文流中**。若原行是 `第一章 开始`，保留它即已满足；若该行还要被 `ReplaceOriginalLine` 规范化，则 (b) 变成一次替换。

**v3.1 处置**：`DemoteHeading` 拆为两个字段显式表达：

```csharp
public sealed record DemoteHeading(
    string ActionId,
    int Level,                    // 降为哪一级；0 表示移除条目
    bool MergeTextIntoBody,       // true = 该行文字必须保留在正文流中
    SourceAnchor? Anchor);
```

`MergeTextIntoBody = true` 且 `Level > 0` 时产生 `ChangeLevel`（树）+ 无 `SourcePatch`（文字本来就在正文流里）。
`Level = 0`（移除条目）时，若用户选择物理删除该行，则产生 `DeleteOriginalLine`；否则只改树并在界面标注。

**修正四：硬规则（新增）**

> 每个可执行 `RepairAction` 必须在编译时静态产出**三元组**：
> `(树形态影响, 文本内容影响, 正文归属影响)`。
> 任一维度无法确定 → 该动作在 `EditSource` 下禁用（按 `SourceEffectDecision` 升级为编译失败或降级并标注）。

这条规则把「动作语义固定」从叙述变成可静态检查的约束。

## 11. Phase 重排

评审 §12 指出 v3 的顺序矛盾，成立：

- v3 §5 已把 `TreePatch` 定义为核心模型
- v3 §7 已把 canonical 等价定义为核心不变量
- Phase 5 的 `SourceEditTransaction` 需要在替换后**物化目标树**
- Phase 5 的恢复必须知道目标树（§2.4）
- Phase 6 开真实写回前必须验证两模式等价

却把这两者放在 Phase 6–7「按需」。若照 v3 顺序实施，Phase 5 只能建出一个「会换 TXT 但无法证明新章节树是什么」的半事务。

### 11.1 调整后

```text
Phase 0  冻结现状
         补 characterization tests；固定六卷样书 fixture；性能基线

Phase 1  删大表、合并链路（不写原文）        ← 可立即做
         删除 ChapterCatalogPanel 独立 apply 链；统一进 RepairReviewWindow

Phase 2  备份层 + 设置骨架                   ← 可立即做
         用户可见备份夹、去重、保留策略、恢复入口、manifest、三种模式设置

Phase 3  计划版本绑定 + RepairDecision
         RepairProposal 改名、RepairBaseVersion、三 fingerprint、
         RepairPlanValidator、RepairDecision、SourceEffectDecision

Phase 4  TreePatch + CanonicalChapterModel + SourcePatch + SourceEditSession
         ← 全部只做内存，不写盘
         SourceAnchor 判别联合、SourcePatchNormalizer、
         无损 decoder/renderer（含 §8 换行算法）、
         ManualGuardZone、Compile 纯函数、canonical 等价测试

Phase 5  ExecutionManifest + SourceEditTransaction + Journal + Recovery
         execution-manifest.json、SourceEditPreflight（§9.1）、
         journal 状态机、同目录 temp + replace、故障注入（§10.2 全表）、
         SourceVersionTransition（幂等）、SourceCoordinateMap

Phase 6  开启「有目录 + 改原文」
         先支持最明确动作：RetitleChapter、InsertHeading、
         用户显式确认的 RemoveDuplicate；其余按 §10.3 硬规则决定

Phase 7  开启「无目录 + 改原文」
         LocalRepairPlanner 为安全动作生成 SourcePatch
```

**与 v3 顺序的差异**：`TreePatch` / `CanonicalChapterModel` 从 Phase 6–7 前移到 Phase 4；`RepairDecision` 加入 Phase 3；`ExecutionManifest` 明确为 Phase 5 交付物。`LocalRepairPlanner` 仍可留到最后（与 v3 一致）。

### 11.2 各期退出条件

| Phase | 退出条件 |
|---|---|
| 0 | 重构前行为可由自动测试复现 |
| 1 | 原文仍完全不改，双链路消失，功能回归通过 |

| 6 | 六卷样书有目录模式通过完整端到端验收 |
| 7 | 2×2 矩阵完整，各组合走同一「计划 / 确认 / 执行」主干 |

## 12. 稳定 ID 与坐标绑定

### 12.1 ID 生成（评审 P2-13）

若用 `Guid.NewGuid()`，同一计划每次生成都不同，破坏「同一 snapshot + tree + rules → 相同计划」的测试要求，也破坏 UI selection 恢复、receipt 对账、journal 关联。

```text
ProposalId  = H(BaseVersion, Basis, PlannerSchemaVersion)
ActionId    = H(ActionKind, SemanticTarget, SourceLocator/Anchor, DesiredValue, BasisIdentity)
OperationId = ActionId + ":" + OperationOrdinal
```

**硬规则**：ID 计算**不得包含 UI 文案或 `RepairEvidence.Description`**——否则改一句提示文字就会让全部 ID 变化，journal 与 receipt 全部失联。

### 12.2 `TreeMutation` 需要 `SourceBinding`（评审 P2-14）

`InsertHeading` 压实后：

```text
TreePatch:   InsertVirtualHeading
SourcePatch: InsertLineAtAnchor(OperationId = X)
```

`SourceCoordinateMap` 有 `InsertedOperationToNewLine`，但 `TreeMutation` **不知道自己该查哪个 key**。

```csharp
public abstract record SourceBinding;
public sealed record OriginalLineBinding(int Line)                 : SourceBinding;
public sealed record InsertedOperationBinding(string OperationId)  : SourceBinding;
public sealed record NoPhysicalSourceBinding                       : SourceBinding;
```

完整链路：

```text
TreeMutation.SourceBinding → SourceCoordinateMap → 新物理行号
```

`NoPhysicalSourceBinding` 用于 `BuildVolumeNode` 等纯树动作。
