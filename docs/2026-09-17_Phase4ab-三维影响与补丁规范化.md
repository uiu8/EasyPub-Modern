## 1. 交付内容

| 文件 | 内容 |
|---|---|

### 1.1 三个维度分开的理由

它们可以不同，所以不能合成一个：

| 动作 | 树形态 | 文本内容 | 正文归属 |
|---|---|---|---|
| 收录一个已定位的标题行 | 增加条目 | **不变** | 不变 |
| 改标题 | 改标题 | **替换一行** | 不变 |
| 摘掉重复副本（只从成品） | 移除条目 | **不变** | **变** |
| 把一行立成标题 | 增加条目 | **不变** | **变** |

每一维都有 `Indeterminate`，而且必须由编译器**显式写出来**。这条设计是整层的支点：一个没人
定义过效果的新动作，不能悄悄退化成"没有影响"，而要说明自己没定义 —— 于是 `EditSource` 拒绝它，
`TreeOnly` 照常可用。

### 1.2 规范化模型装不进存储细节

`CanonicalChapter` 里没有行号、没有 id、没有"虚拟/物理标题"标志。这些恰恰是两种落地模式**必然
不同**的东西：`EditSource` 删行插行之后每一个物理行号都变了。把它们放进模型，等于让等价性检查
从一开始就不可能通过。

正文哈希按「章节内第几行 + 该行文字」算，不按绝对行号。位置参与是为了区分"同一句话在正文里出现
两次"；不含绝对行号是为了让整段行号平移不改变结果。

## 3. 两个实现陷阱（都是"看起来对"的那种）

### 3.1 基类的 `Ordinal` 被位置参数遮蔽

```csharp
public abstract record SourceAnchor { public int Ordinal { get; init; } }   // ← 这一行有害
public sealed record AfterOriginalLine(int Line, int Ordinal = 0) : SourceAnchor;
```

派生记录的位置参数 `Ordinal` **遮蔽**了基类同名属性。于是通过基类读 `anchor.Ordinal` 永远是 0，
而真实值躺在派生记录上。排序看起来在工作 —— 所有插入都被当成 ordinal 0，然后按操作 id 排。

只有当测试真的去区分两个**不同 ordinal** 的插入时才暴露。修法：基类不声明它，改由
`SourceAnchor.OrdinalOf(anchor)` 按类型读。

### 3.2 用 `0` 当"这个操作不针对行"的哨兵

规范化器第一版这样判断操作针对哪一行：

```csharp
var line = operation switch { DeleteOriginalLine d => d.Line, ReplaceOriginalLine r => r.Line, _ => 0 };
if (line == 0) continue;   // ← Delete(0) 这个越界请求被静默跳过
```

`0` 是**非法行号**，不是"不适用"。用它当哨兵，越界检查就恰好漏掉了最该抓的那个值。
参数化测试里 `line: 0` 那一格立刻红。改成按类型 `switch`，不适用就用 `continue` 明确跳过。

## 4. 补丁规范化的八条规则

全部在**写盘之前**检查，违规即拒绝。次序不是用来消解冲突的 —— 那是旧做法，它把错误藏起来：
两个动作对同一行有不同意见时，产出的文件同时不满足它们俩，而没有任何地方会说这件事。

| # | 规则 | 违反时的报告 |
|---|---|---|
| 1 | `Delete ∩ Replace == ∅` | 同一行被多个操作占用 |
| 2 | 同一行最多一个替换 | 同上（并区分"2 个动作"与"同一个动作") |
| 3 | 同一行最多一个删除 | 同上 |
| 4 | 插入按 `(锚点, ordinal, 操作 id)` 稳定排序 | —（由排序保证） |
| 5 | 每个删除/替换的预期旧文本与当前一致 | 前置条件不符 |
| 6 | 所有行号在 `1–行数` 之内 | 行号越界 |
| 7 | 插入锚点不得落在被删除的行上 | 锚点落在被删除的行上 |
| 8 | 不同动作不得产生互相矛盾的物理操作 | 同一行被多个操作占用 |

第 7 条来自样书的真实形状：「把副本删掉，再往它原来的位置插一个标题」读起来通顺，实际不成立 ——
那个锚点不存在了。

## 6. 4c：无损文本模型与补丁渲染（已完成）

### 6.1 交付

| 文件 | 内容 |
|---|---|
| `SourceTextDocument.cs` | 逐行保留各自换行符（CRLF / LF / CR / 无） |
| `SourcePatchRenderer.cs` | 单遍渲染，按原始行号索引；`SourceRenderVerifier` 无损校验 |

### 6.2 为什么无损是硬要求

允许改原文之前，先把计划对着**原始字节**渲染一遍并比对：不带任何改动的渲染若不能原样还原文件，
说明编码或换行还没被理解到可以下笔的程度 —— 此时应当拒绝，而不是存回一个会悄悄变得不一样的文件。

旧模型（`ChapterEditingDocument`）全文件用一个换行符。一致的文件够用，不一致的文件就错了：
混合换行确实存在，而按多数换行符重写每一行会把**一行改动变成整篇 diff**。

插入用的换行符规则写死，不留"就近取主导"这种判断 —— 那句话至少有三种合理读法（取上一行、取下一行、
取前后十行多数），每种给同一个计划算出不同的预期哈希，而一个取决于实现者选了哪种读法的哈希
没法用来校验任何东西。

### 6.3 样书实测

```
=== 4. 无损渲染（样书真实的 75299 字节）===
   无损校验          原文可以无损读入并还原。
   行数              文件模型 2502  章节树模型 2503（差 1：旧模型把末尾空元素算作一行）
   默认换行符        LF
   逐行换行符是否一致 True
   渲染 69 个替换 → 行数 2502 → 2502（删除 0 / 替换 69 / 插入 0）
   实际变化的行数    69（应等于替换数）
   字节数            75299 → 75314
```

**两个模型对"行"的定义不同，这是查出来的、不是猜的**：旧模型把 `text.Split('\n')` 末尾那个空元素
当成一行（文件末尾本来就以换行结束），新模型按行终止符切分。两者对**任何真实存在的行**给出的行号
完全一致（69 个替换的位置逐一对上），差的只是末尾那个并不存在的"行"。

### 6.4 写测试时自己写错一次

我先前断言"样书末行没有换行符"。**断言失败暴露的是我的假设错，不是代码错** —— 末行有换行符。
那条断言已删除：2502 这个数字的正确性由无损往返本身保证，不需要额外的形态假设去背书。

## 7. 4d：TreePatch 与两模式等价性验证（已完成）

### 7.1 交付

| 文件 | 内容 |
|---|---|
| `TreePatch.cs` | `ChapterTreeMutation` 变化清单、`BodyAssignmentCalculator` 正文归属计算 |

`TreePatch` 的每条变化强制携带 `SourceBinding` 与 `ActionId`：

- **binding**：改动之后行号已经失去意义 —— 删过插过，第一个改动下面的全都移位了。变化只能说明
  自己指的是哪一类位置（原始行 / 插入操作 / 无物理来源），由坐标映射去解析。
- **ExpectedResult**：谁执行它谁就能证明建出来的树正是当初商定的那棵。没有这一件，恢复只能重跑
  一遍并祈祷。

### 7.2 Phase 4 真正的验收点：两种落地模式产出同一本书

```
TreeOnly：444 条，移除 160 行（只从成品移除，TXT 不动）
EditSource：160 个删除 → 补丁有效 → 渲染 2502 → 2342 行
=== 规范化模型对照 ===
   TreeOnly    444 章
   EditSource  444 章
   两者相等：True
```

"两种模式产出同一本书"在此之前只是一句设计意图，到这一步才被真的验证过。比的是章节顺序、标题、
层级、是否进目录，以及**每章拥有的正文内容** —— TreeOnly 用原文取文本，EditSource 用渲染后的
文本，行号各自按自己的版本算。

### 7.3 反证写错了，而这暴露了一件更有用的事

反证的作用是防止"两者相等"只是因为模型太粗、什么都判成相等。**第一版反证是错的**：

> 原本问："把被移除的行留着不删，模型会不会不同？" 实测**不会**。

查下来原因很清楚：那 160 行在**重建后的树里本来就不归任何章节**（实测仍被认领的为 0）。对以
章节归属为准的模型来说，它们存不存在根本不影响结果。**那个问题问错了，不是模型有问题。**

换成真正该问的两条，都通过：

1. 同一棵树配「原文」与配「完全不同的正文」→ 判成不等 ✅
2. 只改**一行**正文 → 也判成不等 ✅

同时把"被移除的行确实不在任何章节的正文里"固定成断言。

> **教训**：反证不是"随便找个东西改一改看会不会不等"。反证要针对检查真正claim的那件事。
> 我第一版针对的是"文件里还有没有这些字节"，而等价性检查 claim 的是"每章拥有什么正文" ——
> 两者根本不是一回事。写反证之前要先问：这个检查到底在断言什么？
