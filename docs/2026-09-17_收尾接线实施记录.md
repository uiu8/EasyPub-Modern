# 收尾接线实施记录 — 恢复、快照、迁移与标签

日期：2026-09-17。范围：Phase 0–7 之后剩下的四条界面接线，外加一处标签不一致。
验收条件沿用重构那一轮的两条：**每一项都要在《六卷缺陷样书》上实测**，**按钮必须与代码走同一条链路**。

## 0. 这一轮补的是什么

Phase 0–7 把机制做完了，但有几样东西"只有代码能走到"：

| 能力 | 完成于 | 这一轮之前的实际状态 |
|---|---|---|
| `SourceEditRecovery.RecoverAsync` | Phase 5f | 全 `src/` 零调用点。崩溃中断后没有任何地方能触发收尾，只有 `sim recovery` 探针能走到 |
| `RestoreTransaction` | Phase 5e | Desktop 零引用。备份窗口只有导出，没有恢复 |
| 快照带树 | Phase 5d/5e | 面板两处都调用单参数 `EnsureSnapshot`，`FullStateSnapshotCount` 恒为 0，`FullBookState` 永远不可选 |
| `SourceVersionTransition` | Phase 5d | Desktop 零引用。工作台"刷新"走的是重新识别，实测 468 个身份里能保住的那些全丢 |

按用户给定的顺序逐条接上，每一项都有 Core 测试 + Desktop 链路测试 + 样书探针输出。

## 1. 未完成事务的恢复入口

### 新增

`SourceEditRecovery.RecoverAllAsync(transactionRoot, afterReplace, token)` —— 一次收尾**全部**未完成事务，最老的先做。一条失败不影响其余：两本书各留一次中断编辑正是它要处理的形状，停在其中一条上会让另一条无声地留着。

`SourceEditRecovery.Outstanding(root)` 与已有的 `Pending(root)` 并列：

- `Pending` 排除 `Conflict`（恢复对它无能为力）；
- `Outstanding` 包含 `Conflict` —— 一个只看 `Pending` 的窗口会在一条冲突记录一直摆在那里时报告"没有未完成的事"。两个清单回答的是不同的问题。

`SourceRecoveryReport` 带 `Completed` / `Discarded` / `NeedsAttention` 和一句 `Describe()`。

### 接线（两个入口，一个实现）

- `MainWindow.FinishInterruptedSourceEditsAsync()`：第一次激活时跑一次。放在激活而不是构造，是因为恢复会读写书稿，而一个还没显示的窗口没有地方报告它做了什么。有冲突时弹一次说明，并指向「原文备份…」。
- `SourceBackupWindow.FinishPendingAsync()` + 「完成未完成的原文修改…」按钮（标题会带上未收尾的条数）。

两个入口调的是同一个 `RecoverAllAsync`。

### 实测（`sim wiring` 第 3 段）

```
✓ 收尾之前能看到未完成记录
✓ 一次收尾处理了这条记录
✓ 结果是「已补完」
✓ 原文换成了那次事务商定的版本
✓ 不再有未完成记录
✓ 残留的临时文件已清掉
✓ 再收尾一次什么都不做
✓ 对不上的一条留给了人工
✓ 留给人工的那条没有碰文件
✓ 冲突记录仍然出现在 Outstanding 里
✓ 但它已经不在 Pending 里（恢复对它无能为力）
   第一次：上次的原文修改：补完 1 次原文替换。
   第二次：上次的原文修改：1 条需要人工确认。
```

## 2. 快照带树

### 改动

`ChapterRepairApplier` 的备份回调签名从

```csharp
Func<string, CancellationToken, Task<string?>>
```

改成

```csharp
Func<ChapterTreeDocument, ChapterTreePlan?, CancellationToken, Task<string?>>
```

并给了默认实现：`new SourceBackupStore(_transactionRoot).EnsureSnapshot(document, tree)`。

**这是这一条的关键决定。** 用户要的是"把工作台当前编排的树传进去"，但如果只在面板里传，那么探针、测试、以后任何新调用者仍然会得到只有字节的快照 —— 而"一个能力只有某一条调用路径拥有"正是这一轮要根除的形状。把树写进快照的责任放进应用器，任何调用者都自动得到它。

`ChapterAutoRepairPanel` 因此不再传 `backupPathFor`；它自己那句 `store.EnsureSnapshot(snapshot)`（TreeOnly 分支）仍然显式传 `snapshotPlan`，因为那条路不经过应用器。

### 实测（`sim wiring` 第 1 段）

```
✓ 改原文应用成功
✓ 写出了修复前快照
✓ 快照带章节树（HasSavedTree）
✓ 窗口那一栏会显示「含章节树」
✓ 清单 FullStateSnapshotCount > 0
✓ 能按内容校验值读回那棵树
✓ 树属于这份备份
✓ 树的章节数与修复前一致（468）
   修复前 468 章 → 清单 FullStateSnapshotCount = 1
```

## 4. 工作台「原文已变化 · 刷新」走版本迁移

### 改动

`ChapterEditorWindow` 现在在构造时读一份 `_baselineSource`（`SourceTextDocument`），即"这棵树的模型所描述的那一版文本"。**这一步必须发生在打开窗口时**：等到版本检查发现文件变了，旧文本已经从磁盘上消失了，没有它就只能猜用户改了什么。

`SourceVersionTransition.AfterExternalEditAsync(before, sourcePath, …)` —— 另一条换版本的路径：文件是本程序之外改的，手里没有任何补丁，所以补丁由 `SourceDiff` 逐行比出来。文件没变**不是失败**：这个检查在每次激活时都会跑，在那里报一次失败等于教用户忽略真正要紧的消息。

`ChapterEditorWindow.RebuildOrMigrateAsync(sender)` —— 从 `async void` 的点击处理器里抽出来，这样"按的是哪一个按钮"这条规则本身可以被断言。规则是：

- `RefreshSourceButton` 且 `_sourceChanged` → **迁移**；
- 其余 → 重新识别（用户明确要求丢掉手调树的那条路，行为不变）。

`AdoptMigratedState` 把迁移后的树装回窗口，并清掉撤销栈 —— 栈里的每个快照都写在旧行号上。

### 顺带修掉的一个真实缺陷

`ApplyRepairEntries` 过去只替换界面上的行，不换 `_document`。于是**改原文的修复刚写完 TXT，窗口就声称"原文已变化 · 刷新"** —— 说的是程序自己那次改动。现在它收下整份 `ChapterTreeDocument` 并更新 `_sourceChanged`、`_baselineSource`，原文换版本时一并清掉撤销栈与已确认组。

### 实测（`sim wiring` 第 4 段）

```
   迁移前：识别树 468 章，用户树 468 章
✓ 造出了一次外部编辑
✓ 迁移成功
✓ 没有回退成重新识别
✓ 迁移后仍然是一棵能通过校验的树
   原文版本迁移已完成。 章节身份：保留 468 个，无失效
```

## 5. 顺带修掉的 `SourceDiff` 缺陷

接第 4 条时在样书上撞出来的，不是"顺手改改"，是**真的会把书改坏**：

`SourceDiff.Operations` 只产生 `DeleteOriginalLine` 与 `InsertLineAtAnchor`。一行被改动 → 一删一插 → 坐标表对那一行**没有答案** → 包含它的章节正文出现一个洞。

第一次实测（`SourceVersionTransitionTests` 的 `An_edit_made_outside_the_program_keeps_the_chapters_it_did_not_touch`，五章小书改一句正文）：

```
第三章 转折 → LostNoBody（正文没了，身份被丢掉）
```

改成逐行配对成 `ReplaceOriginalLine`。配对规则按"一批插入对应它后面那一段连续被删掉的旧行"来做，三处边界都是实测撞出来的：

1. **多出来的插入锚在哪。** 一批新行比它换掉的旧行多时，剩下的必须锚在**这一批改写掉的最后一行之后**。锚在原来的锚点上会让它们排到改写行前面（文件顺序乱掉）；锚在一个被删掉的行上更糟 —— 渲染器跳过被删除的行，连它后面的插入一起跳过，那几行会**从结果里消失**。
2. **文件开头那一批不配对。** `BeforeOriginalLine(1)` 与 `ReplaceOriginalLine(1)` 在渲染上不是同一个位置：前者让插入行取默认行尾，后者保留原来那一行的行尾 —— 而空文件那一行没有行尾，配上去会把头两行粘成一行。
3. **同锚点插入的排序是序数字典序。** `ins-10` 排在 `ins-9` 前面，一批十个是普通情况。`OperationId` 改成六位零填充。

`SourceDiffTests` 从 11 条加到 15 条，其中三条专门锁这三处边界（`A_run_of_changed_lines_is_paired_line_by_line`、`More_new_lines_than_dropped_ones_land_after_the_replacements`、`A_batch_of_ten_insertions_keeps_the_text_order`）。

### 一个测试基础设施上的坑

`OnSta(...) { action(window).GetAwaiter().GetResult(); }` 这种写法在本轮**第一次就全线失败**：窗口的 `await` 续体被 post 回**同一个 STA 线程**，而那个线程正阻塞在 `GetResult()` 上 —— 它停下来等的正是它自己。报出来的是"调用线程无法访问此对象"。

改成 `Dispatcher.InvokeAsync(async () => …)` + `Dispatcher.PushFrame`：让 dispatcher 继续跑，工作完成后 `frame.Continue = false`。`SourceBackupRestoreTests` 与 `ChapterWorkbenchMigrationTests` 都用这个形状。

另外 `Show()` 自己会触发一次版本检查，而 `CheckSourceVersionAsync` 有 `_checkingSource` 守卫 —— 不等它跑完，测试里那次显式调用会被静默跳过。两个文件都在 `Show()` 之后 `await Dispatcher.InvokeAsync(() => { }, DispatcherPriority.ApplicationIdle)`。

### 一个会拖慢并可能越界的启动行为

`MainWindow_Activated` 里的自动收尾一开始是**每个窗口实例一次**。生产里只有一个主窗口，看不出差别；测试里每个 `MainWindowLayoutTests` 用例都构造一个主窗口，于是每个都全量扫一遍备份目录 —— 套件从 26 秒变成 50 秒，而且如果那台机器上真有未完成的记录，测试进程会去把它做完。守卫改成 `static`，并且**不再弹模态框**：启动时打断用户本来就不合适，冲突记录在磁盘上，「原文备份…」会列出来。

## 8. 补记：对比重复正文时，说出目录认定的位置

v1.60.0 实测反馈：一本书里「第五十四章 分头行事」在第 5234 行和第 10614 行各出现一次，正文 99.7% 相同。工作台的检查报出了这一对，对比窗把两段正文并排显示、让读者选保留哪一份 —— **但没说哪一份是原位置**。两处相隔 5380 行、正文又几乎一样，读者没有任何依据可选。

这是真实缺口，而且答案本来就在程序里：

- 目录修复的 `RemoveDuplicate`（`ReferencePlan.cs:186`）判据是"参考目录只出现一次、原文出现多次"，它的 `Line` 就是**目录认定的那个位置**，动作描述里也写着"保留第 X 行（与参考位置一致）"；
- 但那条信息只出现在**修复预览**里，而对比窗 —— 读者真正做决定的地方 —— 只比较正文，从头到尾没读过目录。

### 改动

- `ChapterEditorWindow.DescribeCatalogPosition`：有保存的目录时，用 `ReferenceLocator.Locate` 重算一次逐章定位，找出这两行属于哪一条目录记录，报出 `LocatedChapter.Line` 以及两处的距离。
- 对比窗顶部多一行结论；目录认定的那一侧标注「← 参考目录的位置」。
- 定位结果按源哈希缓存（`CatalogLocation()`），在 `InvalidateBreakpoints()` 里随目录一起失效 —— 一次定位要扫全书，而这个窗口是点一下打开的。
- 没有目录、目录里没有这一章、或者定位不出位置时**如实说**，不猜。

### 顺带：目录存储可以隔离了

`ReferenceCatalogInput.SettingsPath` 直接落在 `%LOCALAPPDATA%\EasyPub Modern\Catalogs`，没有覆盖手段 —— 任何为临时书稿保存目录的代码都会写进读者真实使用的文件夹。加上 `EASYPUB_REFERENCE_CATALOGS_PATH`，与 `EASYPUB_SOURCE_BACKUPS_PATH`、`EASYPUB_APP_SETTINGS_PATH` 一致。新测试因此完全跑在临时目录里。

### 实测

`ChapterWorkbenchCatalogPositionTests` 三条：目录里「第一章 甲」排在「第二章 乙」之前 → 说出第 1 行那一份是原位置、相隔 6 行、指向前一份；没有目录 → 说"没有参考目录……位置只有目录说得清"；目录里没有这一章 → 说"没有这一章，两处都不是它的位置"。

相关既有测试：Core 25 条、Desktop 31 条全部通过。

## 9. 仍然待办

- `InsertLineAtAnchor` 仍然只由 `RepairSourcePatchCompiler`（`SourceContentInsert`）和 `SourceDiff` 产生，没有任何修复动作走它。
- **`SnapshotRecognitionPath`（`.recognition.json`）仍然没人写。** 实测（`sim gaps`）恢复全文状态之后：树本身（章节、层级、目录勾选）与恢复前是同一棵；`ChapterTreePlan` 上带的数字标题四项（是否识别数字标题、最少正文行数、数字标题正则、标题纠错表）也一起回来了；**没回来的是 `Enabled`、`Level1/2/3Pattern`、`IncludeHtmlTocPage`、`IncludeChapterTopNavigation` 这六项** —— 它们不在 `ChapterTreePlan` 上，恢复后回到全局设置。后果只在"恢复之后又点了一次重新识别"时出现：那一次会用全局的卷/章/节正则，而不是这本书当时用的。已恢复的树本身不受影响。
- **`SourceDiff` 在两个版本行尾约定不同时，推出的补丁渲染不出目标文本**（既有，本轮未改）。实测（`sim gaps`）：当前版本是 `甲\n乙`（最后一行无行尾）、目标是 `甲\n乙\n丙\n` 时，补丁只有一个 `InsertLineAtAnchor(AfterOriginalLine 2, "丙")`，渲染出来是 `甲\n乙丙\n` —— 少了一个换行。

  **它对软件运行没有影响，这一点是实测出来的，不是推断的**：同一场景下真的走一次 `RestoreTransaction`，写进文件的是 `甲\n乙\n丙\n`，与目标版本逐字节相同。原因是恢复写入的是**目标版本的原始字节**（`targetDocument.Render()`），补丁只用于两件事 —— 执行清单的记录，以及坐标表；而坐标表是从**目标文本**读出来的（`SourceCoordinateMap.Verify` 里 `SourceTextDocument.Parse(newText)`），从头到尾不渲染补丁。所以坐标表判定 `IsSound = true`，恢复照常完成。

  它是一条**潜在陷阱**而不是当前缺陷：执行清单里存着一份"渲染不出当时字节"的补丁，而目前没有任何代码路径会去重新渲染它（恢复路径的 `ContinueReplace` 用的是事务当时已经渲染好、躺在源文件旁边的临时文件）。将来若有人写"从执行清单重放一次修复"，那个功能会在这种书上产出错行的文本。
- 备份窗口的「恢复此版本」目前只能用当前磁盘状态作为迁移起点（那里没有开着的工作台），所以 `SourceOnly` 恢复后的树是重新识别的。这是备份窗口的固有限制，不是缺陷；开着工作台时应当走工作台那条路（本轮已实现）。
- Desktop 全量套件的失败波动（本轮实测 6～12，基线 0～9）没有治理。崩溃已经修掉，剩下的来自 `Application` 单例被一条已结束的线程持有；要做就得把整套测试改成不依赖 `Application.Current`，那是独立的一件事。
