# 目录获取耗时取证与预算（v1.49.0）

**任务背景**：`docs/NEXT_TASK.md` 说《凡人修仙传》`auto` 要 14.3 秒，瓶颈是
`ReferenceLocator.Locate` 第三遍兜底搜索（「1405 章未定位 × 61752 行 ≈ 8700 万次迭代」），
已经失败过两次优化，要求先量数据再设计。

**结论：那个判断是错的。第三遍只占 1%，真正的瓶颈在网络目录获取。**

这一页记录取证过程、真实数据、以及为什么两个「失败方向」本来就不该做。

---

## 1. 取证：先量，不要跳步

没有凭空设计，先加分段计时与扫描命中计数（现在已固化进代码与测试）。

### 1.1 数字对不上：61752 行是别人的

```
凡人修仙传(忘语).txt      185 631 字节    1 078 行   ← 0.18 MB，小文件
疯巫妖的实验日志(…).txt  9 878 507 字节   61 753 行   ← 61752 就是这个
```

「1405 章未定位 × 61752 行」把**疯巫妖的行数**安到了凡人头上。凡人真实迭代量：

```
1397 章未定位（有词可搜）× 1 078 行 = 1 505 966 次，实测 89–145 ms
```

差了 58 倍。这是整条任务线走偏的起点。

### 1.2 分段实测（凡人修仙传）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **目录获取（网络）** | **7 754 – 27 922 ms** | **~98%** |
| 对齐 `ReferencePlanner.Build` | **0 ms**（内部 <1 ms） | ~0% |
| └ 候选行扫描 / 前两遍 / **兜底第三遍** | 9 / 34 / **89–145 ms** | **~1%** |
| 重建章节树 + 核对 | ~170 ms | ~2% |

第三遍的完整账（两个不同选源结果）：

| 选中的目录 | 前两遍定位 | 兜底扫描 | 兜底命中 |
|---|---|---|---|
| 1 004 章（书读谷） | **30 章** | 972 章 / 104 万行 | **0** |
| 1 408 章（偶书网→biquge365） | 3 章 | 1397 章 / 150 万行 | 27（**全部是「章号一致」**） |

1 004 章那次前两遍就把 30 章全部定位，兜底纯属陪跑；1 408 章那次兜底救回 27 章，
**证据是最强的「章号一致」**。

### 1.3 并发不是答案

把 `MaxConcurrentSources` 由 4 调到 6（正好等于 6 个书源），实测 **10.0 s / 8.8 s**，
与 8.4 s 同量级，**无改善，已回滚**。慢的是单个站的**目录抓取**，不是排队。

按源计时（同一本书，`DiscoverAsync` 新增的 `LastTimings`）：

```
源 书读谷        14 035 ms  1 个目录
源 爱下电子书     27 768 ms  无可用目录     ← 抓了 27.8 秒，什么也没拿到
源 偶书网         8 402 ms  2 个目录
源 和图书           935 ms  查询失败
源 起点中文网       296 ms  无可用目录
源 番茄小说           0 ms  无可用目录
```

**「爱下电子书」27.8 秒 / 0 结果**是最坏的一例：它一个人把整个查询拖到 28 秒。

## 2. 为什么两个「已经失败」的方向本来就不该做

它们都在优化**不是热路径**的东西：

1. **「目录远大于文本就跳过第三遍」** —— 阈值算错了比较对象只是表面问题；
   真正的问题是第三遍本来只有 92 ms，跳过它省不到 1%，却会丢掉那 27 个
   **靠「章号一致」定位到的真实章节**（30 章 → 3 章）。收益 <0，风险 >0。
2. **「把章号匹配建索引」** —— 实测更慢（14.3 → 18.5 s）之后被回滚，
   但那 14.3 s 的大头根本不在定位里，所以「查找 vs 压根找不到」的复盘也建立在错误前提上。

> **教训**：`NEXT_TASK.md` 里「网络部分只占 1–2 秒」这句话从未被验证过。
> 一句未经测量的判断，让两个方向被反复尝试、反复回滚。**先量，再设计。**

## 3. 本次改动

### 3.1 让耗时可见（这才是最该先做的一件事）

| 位置 | 改动 |
|---|---|
| `ReferenceLocator` | 三阶段分段计时 `ReferenceLocateTiming`：候选行 / 前两遍 / 兜底 |
| `ReferenceLocator` | `ReferenceLocationStats`：目录章数、候选行数、前两遍定位数、兜底扫描章数与行数、三类证据命中数、无词可搜章数 |
| `ReferenceLocator` | 抽出 `SearchEveryLine`（返回命中的**证据种类**），循环逻辑与原实现逐行等价 |
| `ChapterAutoRepair` | `AutoRepairTiming`：目录获取 / 对齐 / 重建 / 核对 / 合计 |
| `ReferenceCatalogClient` | `LastTimings`：每个书源的耗时、结果数、状态、被跳过的候选数 |
| `work/chapter-audit` | `auto` 模式打印以上全部 |

**下一句话就有数据可查，不必再猜。**

### 3.2 收紧网络时间预算

| 常量 | 值 | 作用 |
|---|---|---|
| `SearchTimeoutSeconds` | 6 | 搜索页很小；实测最慢 6.2 s 的源从未贡献过被选中的目录 |
| `FetchTimeoutSeconds` | 15 | 目录页是大响应，保持原值 |
| `SourceBudgetMs` | 15 000 | **单个源的搜索 + 全部目录读取的总预算** |
| `AnsweredChapters` | 50 | 拿到这么大的目录就不再试该源的后续候选 |

三个设计约束：

- **预算只决定「还开不开始下一个候选」，不取消已发出的请求** —— 已在途的抓取让它完成，
  不浪费已经付出的往返。
- **预算内拿到的目录照常参与比较** —— 所以**选源结果不受影响**，收益仍然按原来的
  「章数 ≥ 最全者 90%，取书源顺序第一个」来比。
- **被截断就说出来** —— `SourceTiming.SkippedCandidates` / `State` 会显示
  「预算用尽，跳过 N 个候选」，不静默变少。

### 3.3 实测效果

| | 改动前 | 改动后 |
|---|---|---|
| 凡人 `auto` 外部总耗时 | 22.7 / 8.5 / 10.7 / 27.9 s（大起大落） | **8.4 / 8.7 / 8.0 s（收敛）** |

诚实的说明：这三次运行里 15 s 预算**并未触发**（最慢的源 8.3 s），
所以数字的改善主要来自当时网络状况；预算的价值是**兜住尾部** ——
在出现 27.8 s 那种源时把它截在 15 s，而不是跟着它等下去。
`AnsweredChapters` 的提前退出在这几次也没触发（每源只抓到 1 个目录）。

**未触发的边界要记住**：随后一次实测「爱下电子书」用 9 483 ms 返回、**仍然拿到了 0 个目录**。
也就是说触发点比想象的近 —— 15 s 只在真正极端时生效，日常的 8–10 s 依然要等。

### 3.4 反证：对齐真的不慢（番茄语料）

同一套代码跑番茄的 7 本（目录走本地 `status.json` 记录，网络只 1.1–1.5 s）：

| 书 | 目录获取 | 对齐 | 兜底扫了 |
|---|---|---|---|
| 东京：我的青春没有固定公式（638 章） | 1 553 ms | **53 ms** | 13 章 / 171 万行 / 命中 1（标题词）|
| 福尔摩斯小姐今天也怀疑我是凶手（460 章） | 1 147 ms | **367 ms** | 30 章 / 249 万行 / 命中 0 |

兜底这里扫了 **171 万 / 249 万行**，仍然只有 100 ms 出头。
**所以「兜底搜索慢」这个假设，在任何一本书上都不成立。**

**没有把 8 秒变 1 秒**：首次目录获取要并发问 6 个站点、读它们的目录页，
这是网络固有的成本。真正的省时杠杆是第二次不再问（GUI 已保存目录，见 §4）。

## 4. 顺带发现的两个事实

1. **GUI 本来就有目录缓存**：`ReferenceCatalogInput.Load(document.SourceSha256)`
   命中时 `目录获取` 只有约 200 ms（疯巫妖 204 ms 就是走的这条路）。
   所以用户重复修同一本书时**不会**再等 8 秒；等 8 秒的只有第一次。
   `work/chapter-audit` 只读不写这个缓存，所以命令行每次都走网络。
2. **凡人的 1 408 章目录是另一本书的**：`biquge365.net/newbook/66282` 的首章是
   `第1章 狐女`，而用户文本的首章是 `第1章 山边小村` —— 那是《凡人修仙传》**仙界篇**的目录。
   目录能拿到、文本只有 30 章时，报告只会说「未定位 1378 章」，不会说
   「这个来源和你的文件对不上，建议换一个」。**这条还欠一句人话**（未做，见 §6）。
