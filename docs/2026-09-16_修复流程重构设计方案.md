# 修复流程重构设计方案：双依据 × 双落地

> 状态：设计稿，待实现
> 范围：章节工作台的修复流程（目录辅助修复 / 本地自助修复）、落地方式（不改原文 / 改原文）
> 前置决策（已确认）：允许修改原文；备份统一入备份文件夹；第四卷类缺标题可按目录插入；第六卷重复标题行直接删；「久→九」确认改写；备份设置同时支持"一次性偏好"与"每次询问"；「无目录 + 改原文」放第二期。

---

## 1. 背景与问题

### 1.1 现状的两条独立链路

目录辅助修复面板里有两条互不相干的链路，对同一棵树、同一份目录会给出不同结果：

| 界面元素 | 代码链路 | 建计划 | 应用 |
|---|---|---|---|
| 目录面板第二步「预览章节调整…」 | `ReferenceOutlineAssist` | `ReferencePlanner.Build` | 自建表 + 自建勾选 + `Apply` |
| 工作台「预览目录修复」 | `ChapterAutoRepair.RepairAsync` | `ReferencePlanner.Build` 再算一遍 | `RepairReviewWindow` + `RebuildWithSelection` |

后果已经出现过：新增 `AdoptHeading` / `MissingBody` 时只更新了后者，前者把新动作类型显示成「说明」，汇总数字也对不上。

### 1.2 依据混淆

同一对话框内混了三条依据不同的链路：

```
目录辅助修复（获取、核对、补建）
├─ 一、获取目录        自动获取（联网多书源）
├─ 一、手动            粘贴 / 导入目录 TXT
└─ 没有参考目录时       本地扫描 + 检测并预览补建   ← 根本没有目录
```

第三条的依据是"独立短行 + 上下空行 + 同名分段"，与参考目录无关。同一棵章节树，有目录时能看到"第四卷 50–60 章整段缺失"，无目录时只能看到"编号从 49 跳到 61"。把两者混在一个「待核对 N 组」列表里，用户无法判断每条结论的依据。

### 1.3 「不改原文」造成的间接性

现行模型是**纯引用**：章节树的条目只记 `TitleLineNumber` + `ContentRanges`（指向原文件的行号区间）。删除一个重复章节 = 从树里移除条目，那几行仍在 TXT 中、只是不进成品。

这在六卷缺陷样书上产生了这些后果：

| 需求 | 引用模型下的做法 | 代价 |
|---|---|---|
| 删重复章 | 只移除树中条目 | 需要 `RemovedDuplicate` + 移除清单 + 行守恒校验 |
| 补标题（原文无该行） | 只能在**已存在的行**上立标题（`AdoptHeading`） | 找不到行时只能报"正文缺失" |
| 改标题 | 只改树，TXT 里仍是旧标题 | 成品与原文不一致 |
| 顺序错乱 | 只能报告，不能修 | 「顺序异常 31 处」无出口 |
| 定位 | 文本重复导致按章号抓错行 | 曾出现 41 处错绑 |

### 1.4 样书所需的文本操作（实测推演）

| 缺陷 | 操作 | 数量 |
|---|---|---|
| 第一卷 30–40 整章重复（150–255 行） | 删行 | 55 |
| 第二卷 20–40 副本错位（663–767 行） | 删行 | 105 |
| 第三卷 40–60 原文本就没有 | 无操作（无法补造正文） | — |
| 第四卷 30–40 标题行不存在（1117–1149） | **插行**（11 个标题） | 11 |
| 第四卷 50–60 标题正文全缺 | 无操作 | — |
| 第五卷 101–120 三种写法 | 改行（补「第」、久→九、数字规范化） | ~7 |
| 第六卷 每章双标题行 | 删行 | 100 |

合计：**删 260 行、改 7 行、插 11 行**。绝大多数是删除，只有第四卷 30–40 需要插入——而那正是引用模型下唯一"修不好"的一类。

## 2. 设计目标

1. **一份计划，两种落地**：任何修复只计算一次，落地方式不改变计算结果。
2. **依据显式**：界面始终说明"当前依据是目录还是本地推断"，每条结论标注依据。
3. **两个入口清晰**：顶部并列「参考目录修复」与「本地快速修复」，各自内部不分叉。
4. **改原文安全**：备份先行、变更可审、崩溃可恢复、编码不变、原子替换。
5. **不重复代码**：四种组合共用一条主干，只在两处分叉。

### 非目标

- 不合并两段正文、不移动正文内容（第二期之后再说）
- 不做无目录情况下的正文补造（真正的缺失不猜）
- 不做多用户并发编辑
- 不改动 EPUB 导入路径（只处理 TXT）

## 3. 总体架构

### 3.1 主干与分叉点

```
[1] 加载与识别                    ← 四者共用
[2] 定依据 → ReferenceCatalog?     ← 分叉点 A：有/无目录
[3] 生成 ReferencePlan             ← 共用同一批检测器，输入不同
[4] 确认窗 + 逐条勾选               ← 共用同一窗口、同一份 Selection
[5] 落地                          ← 分叉点 B：改原文 / 不改原文
[6] 复核与存档                     ← 分叉点 B 决定写什么哈希
```

**分叉点只有两个且互不相干**：A 决定"计划里有什么"，B 决定"计划怎么落地"。组合数 2×2，代码分支 2+2。

### 3.2 两处入口（依据维度）

```
工作台顶部：
  [ 参考目录修复 ▾ ]                 [ 本地快速修复 ▾ ]
      ├ 一键获取目录并修复                ├ 本地扫描补建
      └ 手动粘贴 / 导入目录              └ 章节复核（结构恢复、重复标题、跳章）
  当前依据：未获取 / 《书名》480 章
```

- 「参考目录修复」= 现在的 `ChapterAutoRepair` 链路
- 「本地快速修复」= 现在的 `MissingChapterHeadings` / `UnnumberedHeadings` / `ChapterStructureRecovery` / `DuplicateChapterCleaner` 等本地启发式
- **目录辅助面板（`ChapterCatalogPanel`）只保留"选目录"职责**，删除第二步的「预览章节调整…」与大表（`OutlineRow` / `ReferenceOutlineAssist` / `ConfirmRepairChanges`）

### 3.3 落地开关（落地维度）

```
┌─ 修复确认窗 ─────────────────────────────────┐
│ 依据：目录《六卷样书》480 章                    │
│ ...                                          │
│ ☐ 直接修改原文件（会先备份）                    │  ← 默认关闭
│    关闭：原 TXT 不动，修复只作用于成品           │
│    开启：压实写回原文件；备份在 …               │
│                          [取消] [应用所选修改]  │
└──────────────────────────────────────────────┘
```

设置项：

```
设置 → 修复
  修改原文件： ○ 从不   ● 每次都问（默认）   ○ 总是修改
  ☑ 修改前始终备份（默认勾选，不可取消）
  备份位置：<书稿目录>\.easypub\backup
```

"总是修改"仍**每次备份**——该选项只省掉询问，不省掉备份。

## 4. 编辑模型：行号稳定 + 延迟压实

### 4.1 三个操作结构（全部以**原始行号**索引）

```csharp
public sealed class SourceEditLayer
{
    private readonly HashSet<int> _deleted = [];                    // 删除的行
    private readonly Dictionary<int, string> _replaced = [];        // 行号 → 新内容
    private readonly Dictionary<int, List<string>> _inserted = [];  // 在行号【之前】插入

    public bool IsDirty => _deleted.Count > 0 || _replaced.Count > 0 || _inserted.Count > 0;
    public int DeletedLines => _deleted.Count;
    public int ReplacedLines => _replaced.Count;
    public int InsertedLines => _inserted.Values.Sum(v => v.Count);
}
```

读取时按 `inserted → replaced → deleted → 原文` 依次求值；**编辑期间行号语义始终是原始的**。

### 4.2 压实（唯一改变行号的地方）

```
压实（一次性、流式）：
  temp = 原文件同目录下的 .tmp
  foreach 原始行号 1..N:
      if 该行有 inserted → 按顺序写出
      if _deleted 含该行 → 跳过
      else → 写出 _replaced[行号] ?? 原文行
  以【原编码 + 原换行符 + 原 BOM】写出 temp
  原子替换（File.Replace / Move）
  重新 LoadAsync，清空操作层
```

### 4.3 铁律

| 铁律 | 内容 | 违反后果 |
|---|---|---|
| 1 | 所有编辑以原始行号记录，编辑期间不做 remap | 行号错位（历史故障根源） |
| 2 | 读取按叠层求值，模块看到的都是"当前状态" | 同一行两种读法 |
| 3 | 只有压实改变行号；压实后必须重载并清空操作层 | 两种坐标共存 |
| 4 | 编码/换行符/BOM 原样写回 | 整本书乱码 |
| 5 | 存在 `manual` 条目时**拒绝**编辑模式 | 手工编辑无法映射回原文 |
| 6 | 压实前校验源文件哈希未变 | 覆盖用户在别处的修改 |

### 4.4 操作优先级：先删 → 再改 → 最后插

| 次序 | 操作 | 样书数量 | 理由 |
|---|---|---|---|
| 1 | 删除（重复章节、重复标题行） | 260 | 纯移除；被删的是已知坏数据，删错可见 |
| 2 | 改写（补「第」、久→九、数字规范化） | 7 | 单行替换，行数不变 |
| 3 | 插入（第四卷 30–40 的 11 个标题） | 11 | 唯一新增内容，放最后，不参与任何已有定位 |

建立卷层级**不改文本**：卷层级是树的属性，卷标题行若原文没有则用目录卷名（不写入 TXT）。

> 注：在叠层模型下行号稳定，次序**不是正确性要求**，而是让输出与变更清单更易读。真正的硬约束是下面这条。

**新增校验**：补建操作的候选行必须排除"已计划删除"的行。否则会出现"先删副本、再往同一位置插标题"的自相矛盾（第三卷 40–60 与第二卷副本重叠区正是这种形状）。

## 5. 备份设计

### 5.1 现状

`SourceBackupStore` 已实现内容寻址：

```csharp
var hash = SHA256.HashData(bytes);
var path = Path.Combine(..., "Snapshots", hash + ".bak");   // FileMode.CreateNew
```

问题：位置在 `%LOCALAPPDATA%`（系统隐藏目录）、无保留策略、无恢复入口。

### 5.2 新设计

| 项 | 设计 |
|---|---|
| 位置 | `<书稿目录>\.easypub\backup\`（跟书走；路径可配置） |
| 命名 | `原稿-<yyyyMMdd-HHmmss>-<sha8>.txt`，同 sha 已存在则跳过 |
| 时机 | ① 会话首次改动时；② 压实前 |
| 保留 | 上限 20 份，超出删最旧；**始终保留最早一份**（真正的原稿） |
| 压缩 | 超过 8MB 时视为压缩候选（可选，第二期） |
| 恢复 | 列出全部备份（时间、行数、sha），选一份还原；还原本身也先备份当前状态 |

### 5.3 变更清单（与备份并列产出）

`<书稿目录>\.easypub\backup\改动-<时间戳>.txt`

```
源文件：D:\...\缺陷样书.txt
原 SHA-256：...
新 SHA-256：...
操作统计：删除 260 行、改写 7 行、插入 11 行

类型    原行号   操作   原内容                          新内容                      依据
删除    205     删     第三十章 甲30 入城灯下           （移除）                    目录只出现一次
删除    206-209 删     正文段落一/二（第三十章…）        （移除）                    同上
改写    1889    改     第一百零九章 戊109 …            （不变）                    久→九（编号纠错表）
插入    1113前  插     （无）                          第三十章 丁30 临渊定计       目录有此章，原文无标题行
```

`依据` 字段是必需的：让用户能逐条判断程序为什么改，尤其「久→九」这类改写用户原文用字的操作。

### 5.4 操作日志（崩溃恢复）

`<书稿目录>\.easypub\journal\<sha8>.jsonl`，每行一条编辑记录，追加写：

```json
{"op":"delete","line":205,"reason":"duplicate","plan":"目录《六卷样书》"}
{"op":"replace","line":1889,"text":"第一百零九章 戊109 断后长夜","reason":"typo-rule"}
{"op":"insert","before":1113,"text":"第三十章 丁30 临渊定计","reason":"missing-heading"}
```

用途：崩溃后恢复未压实的操作；支撑撤销；审计。压实成功后清空该 journal。

## 6. 数据模型与接口

### 6.1 核心类型

```csharp
/// 一行文本的来源：原文、被替换、被插入
public enum SourceLineOrigin { Original, Replaced, Inserted }

public sealed record SourceLineView(int OriginalLine, string Text, SourceLineOrigin Origin);

/// 一份计划要动哪些行 —— 两种落地方式共用
public sealed record ReferenceEditSet(
    IReadOnlySet<int> DeleteLines,
    IReadOnlyDictionary<int, string> ReplaceLines,
    IReadOnlyDictionary<int, IReadOnlyList<string>> InsertBefore);

public enum ApplyMode { Reference, EditSource }
```

### 6.2 接口

```csharp
// 阶段 1：叠层（纯内存，磁盘不动）
public sealed class ChapterTreeDocument
{
    public SourceEditLayer Edits { get; }
    public IReadOnlyList<SourceLineView> CurrentLines();   // 叠层求值后的全量视图
    public string? LineText(int originalLine);             // 供读取
}

// 阶段 2：从计划推导编辑集（两种模式共用同一份推导）
public static class ReferenceEdits
{
    public static ReferenceEditSet FromPlan(
        ChapterTreeDocument document,
        IReadOnlyList<ChapterTreeEntry> entries,
        ReferencePlan plan,
        IReadOnlyCollection<ReferenceAction> selection);
}

// 阶段 3：落地
public static class RepairApplier
{
    /// Reference：只改树，原文件字节不变；产出移除清单
    public static RepairResult ApplyToTree(...);

    /// EditSource：压实写回；产出备份 + 变更清单；压实后重载
    public static RepairResult ApplyToSource(
        ChapterTreeDocument document, ReferenceEditSet edits, BackupOptions backup, ...);
}

public enum ApplyMode { Reference, EditSource }
```

**关键约束**：`ReferenceEdits.FromPlan` 是**纯函数**，两种模式的输入完全相同。这是防止"两个按钮结果不同"复发的结构性保证——测试可以断言"同一 plan 推出的 EditSet 与它推出的树变化一致"。

## 7. 冲突点与对策

| # | 冲突 | 后果 | 对策 |
|---|---|---|---|
| 1 | 行号语义混淆 | 同一本书两种坐标共存 | 编辑模式只认原始行号；压实后强制重载并清空叠层 |
| 2 | `manual` 条目与编辑模式 | 手工编辑无法映射回原文 | 存在 `manual` 时**拒绝**编辑模式（硬闸门） |
| 3 | 目录存档哈希失效 | 改一次正文后"目录没了" | 压实后把目录存档重新挂到新 SHA-256 |
| 4 | 移除清单 vs 备份 | 两个机制混用、留档语义混乱 | 编辑模式统一走备份；`.removed.txt` 只在引用模式产出 |
| 5 | 模式混用同一本书 | 树已变而叠层基于原文 | 应用只依据原文行号；换模式时提示"自上次修改正文后请重新预览" |
| 6 | 原文件被占用 | 压实失败被当成成功 | 预探测可写性；失败给出「请先关闭正在编辑此文件的程序」，**绝不静默降级** |
| 7 | 编码/换行符 | 整本书乱码 | 复用 `TextFileDecoder` 的编码与 BOM；写回用原换行符；单测覆盖 GBK |
| 8 | 崩溃丢操作 | 用户 300 项勾选全没 | 操作日志持久化；启动时检测未完成 journal 并提示恢复 |
| 9 | 目录哈希迁移遗漏 | 存档与树指向不同版本 | 存档不变量测试：压实后目录存档与章节树都指向新哈希 |

## 9. 测试策略

### 9.1 2×2 矩阵

|  | 不改原文 | 改原文 |
|---|---|---|
| **有目录** | 行守恒；TXT 字节不变 | TXT 行数 = 原文 − 删 + 插；压实后重识别章节数 = 计划章节数；目录存档迁到新哈希 |
| **无目录** | 同上 | 同上 |

三条不变量（每个用例都断言）：

1. **计划不变量**：同一 `ReferencePlan` 在两种落地方式下推导出的行集合完全一致；
2. **落地不变量**：TXT 不变，或变化量恰好等于计划的删/插；
3. **存档不变量**：改原文后目录存档与章节树都指向新哈希。

### 9.2 专项

| 项 | 内容 |
|---|---|
| 编码 | GBK 原文件压实后仍是 GBK；带 BOM 的 UTF-8 保持 BOM |
| 换行 | CRLF 文件压实后仍全 CRLF |
| 崩溃 | 写入 journal 后强制中断，重启能恢复叠层 |
| 文件锁 | 原文件被独占打开时，压实失败且提示明确、树未变 |
| 优先级 | 删/改/插混合时结果正确；候选行不与待删行重叠 |
| 幂等 | 压实后立即再跑一次修复，应无操作可做 |
| 大文件 | 8000 章 / 28MB：压实耗时与内存（基线：分析 224ms） |

### 9.3 样书端到端

`docs/samples` 的六卷缺陷样书跑四种组合，对照本文 §1.4 的操作数量：

```
删 260 行、改 7 行、插 11 行 → 压实后：
  第一卷 40 章（重复消失）
  第二卷 40 章（副本消失）
  第四卷 30–40 有标题、50–60 仍缺（如实报）
  第五卷 120/120（三种写法都规范）
  第六卷 100 章、0 组重复
```

## 10. 风险与回退

| 风险 | 缓解 |
|---|---|
| 压实写坏原稿 | 压实前强制备份 + 原子替换 + 写后校验（行数与内容对照） |
| 用户误以为"不改原文"却改了 | 默认关闭；开启时按钮二次确认；界面持续显示"已修改正文 N 行，备份在 X" |
| 无目录误判直接改原稿 | 第二期才开；额外确认闸门 |
| 编码问题 | 专项单测；首次压实前做一次"写回空操作"自检（压实但内容不变，比对字节） |
| 计划与实际不符 | `ReferenceEdits.FromPlan` 纯函数 + 计划不变量测试 |

**回退路径**：任何时刻可从备份还原；还原本身先备份当前状态，因此还原也可回退。
