## 0. 本版摘要

v3.1 的主干经复核成立。v3.2 修的是 v3.1 自己没做干净的地方：

1. **最重要的修正**：v3.1 §10.1 强制在恢复路径上重新校验三 fingerprint——**这是错的**，会永久卡死一个已成功的事务。核心修正是划出事务分界线 `SourceReplaced`。
2. 修正 v3.1 §10.2 恢复表里的一格危险项（`SourceReplaced + BaseSha` 自动重做 replace）。
3. `ExpectedNewSha` 移入不可变 manifest（v3.1 的顺序假设没有必要）。
4. 引入 `SourceEffectPolicy`，阻止 `InsertHeading` / `RetitleChapter` 静默降级。
5. 把三元组影响从文档硬规则升级为类型 `RepairEffect`。
6. 拆分 `DemoteHeading`；`BodyCut` → `BodyAssignment`（多区间）。
7. 修三处类型/术语不一致：`DecisionSnapshot.SourceAnchorLine`、`ProposalId` 碰撞、`析取/合取` 写反。
8. Phase 2 不提前开放真实的「恢复为当前原文件」。

**结论：v3.1 不需要推翻，v3.2 之后可以实施。**

## 2. P0：事务分界线 `SourceReplaced`（v3.1 的严重错误）

### 2.1 我在 v3.1 写错了什么

v3.1 §10.1「评审未提及的 3 个问题」的第一条，我写：

> `BaseVersion` 的三个 fingerprint 在恢复路径上**仍须校验一次**（对 `BaseSnapshotPath` 指向的快照重新计算），而不是只在提交前校验。

评审指出这条在 `SourceReplaced` 之后不成立。逐层核对，**评审对，我错**：

**第一层：数据不足。** `BaseSnapshotPath` 只保存源字节快照，只能重建 `BaseSourceSha256`。它无法独立重建 `BaseTreeFingerprint` 或 `RecognitionFingerprint`——除非 manifest 另外完整保存 `BaseTreeSnapshot` 与 `RecognitionSettingsSnapshot`，而 v3.1 并没有。所以「恢复时重新计算三个 fingerprint」在数据层就没有闭环。

**第二层：即使能算也不该算。** 这个反例是决定性的：

```text
TXT 已成功替换
→ 程序崩溃
→ 用户调整了识别规则
→ 程序再次启动
```

若恢复要求 `CurrentRecognitionFingerprint == old RecognitionFingerprint`，一个**已经成功修改了原 TXT 的事务**会因为 UI 设置变化而永久卡住，只能人工介入。这不可接受。

而且 `SourceReplaced` 之后 planner 已退出历史舞台：proposal 已编译成冻结的 `TreePatch` + `SourcePatch` + `ExpectedCanonicalResult`，恢复只需忠实执行已冻结的事实，没有理由再去问「旧计划是否仍有效」。

### 2.2 我原本想防的是什么，以及正确的防法

v3.1 §10.1 的动机是真实的：`TreePatch` 冻结了，但它所指的原始行可能在恢复时对应到不同章节。

**正确的防护是「校验它绑定的基线」，不是「重新计算 planner 的前置条件」。** 具体是：

```text
撤销：恢复时重算三 fingerprint
改为：校验 BaseSnapshot 字节 == manifest.BaseSnapshotSha256
      （TreePatch 的 SourceBinding 是相对 BaseSnapshot 的坐标）
```

这样 `TreePatch` 的坐标语义就是封闭的，不需要重建 Tree / Recognition fingerprint。

### 2.3 正式定义

```text
SourceReplaced 之前
→ 验证「旧计划是否仍然有效」
→ 三 fingerprint 全部必须匹配

SourceReplaced 之后
→ 不再重新判断旧计划
→ 只按冻结的 ExecutionManifest roll-forward
```

**`PreCommitValidation`**（状态 ∈ `Prepared` / `BackupCreated` / `TempWritten` 且源未替换）：

```text
CurrentSourceSha256          == BaseVersion.BaseSourceSha256
CurrentTreeFingerprint       == BaseVersion.BaseTreeFingerprint
CurrentRecognitionFingerprint == BaseVersion.RecognitionFingerprint
```

任一不符 → proposal 过期 → 禁止继续写盘。`LandingMode = TreeOnly` 时同样适用（树级落地也必须基于当前有效计划）。

**`PostCommitRecoveryValidation`**（状态 ∈ `SourceReplaced` / `DocumentReloaded` / `StateMigrated`，且 `CurrentSourceSha256 == manifest.ExpectedNewSha256`）：

```text
1. manifest 自身完整、schema 版本受支持、checksum 自洽
2. BaseSnapshot 实际字节 SHA == manifest.BaseSnapshotSha256
3. CurrentSourceSha256          == manifest.ExpectedNewSha256
4. TreePatch 能在新源上物化（SourceBinding 全部可解析）
5. Canonical(物化树) == manifest.ExpectedCanonicalResult
6. SourceVersionTransition 可安全重试（幂等，见 v3.1 §9.2）
```

**不再比较当前 Tree / Recognition 与旧 fingerprint。**

### 2.4 三 fingerprint 在新模型下的角色

| 字段 | 提交前 | 提交后 |
|---|---|---|
| `BaseSourceSha256` | 前提条件（必须匹配） | provenance / audit |
| `BaseTreeFingerprint` | 前提条件（必须匹配） | provenance / audit |
| `RecognitionFingerprint` | 前提条件（必须匹配） | provenance / audit |
| `BaseSnapshotSha256` | 写入 manifest | **恢复校验依据** |

若担心项目文件本身被用户或第三方改动，应另行引入 `ProjectStateFingerprint` / `PersistedProjectVersion`，**不得错误复用旧 `TreeFingerprint`**。

## 3. P0：修正恢复矩阵的危险格

### 3.1 我在 v3.1 写错了什么

v3.1 §10.2 的恢复表里有：

| journal 状态 | 磁盘 = BaseSha | 磁盘 = ExpectedNewSha | 磁盘 = 其他 |
|---|---|---|---|
| `SourceReplaced` | **重新执行替换** | 走恢复物化 | Conflict |

这一格**违反了我在同一张表里标下的原则**（「标异常的格子一律进 Conflict，不自动推测」）。

正常顺序是 `Replace` 先、`journal = SourceReplaced` 后。所以 `journal = SourceReplaced` 而磁盘仍是 `BaseSha`，至少四种可能：

```text
A. journal 被错误提前更新
B. replace 实际失败
C. replace 成功后用户手工恢复了旧文件
D. 第三方程序重新写回了 BaseSha
```

仅凭 SHA 无法区分。尤其 C——**自动重做 replace 会直接覆盖用户主动做出的恢复**。评审的这条判断是对的。

### 3.2 v3.2 恢复矩阵

| Journal 状态 | Disk = BaseSha | Disk = ExpectedNewSha | Disk = 其他 |
|---|---|---|---|
| `Prepared` | 放弃 / 清理 | Conflict | Conflict |
| `BackupCreated` | 放弃或继续 | Conflict | Conflict |
| `TempWritten` | **允许自动继续 replace** | 视为 replace 已成功 → roll-forward | Conflict |
| `SourceReplaced` | **Conflict** | roll-forward | Conflict |
| `DocumentReloaded` | **Conflict** | 重跑 transition（幂等） | Conflict |
| `StateMigrated` | **Conflict** | 完成最终验证并 `Committed` | Conflict |
| `Committed` | **Conflict** | 清理残留 temp，保留 receipt | Conflict |

**唯一允许「disk = BaseSha → 自动继续 replace」的状态是 `TempWritten`**，因为 journal 明确表明事务尚未宣称跨过 replace 边界。

`TempWritten + BaseSha` 继续 replace 时仍需重新校验：

```text
重新渲染 temp → TempBytes' 
TempBytes' == 原 TempBytes（若 temp 文件仍在）
SHA(TempBytes') == manifest.ExpectedNewSha256
CurrentSourceSha == BaseVersion.BaseSourceSha256
```

任一不符 → `Conflict`，不替换。

## 4. `ExpectedNewSha256` 移入不可变 manifest

### 4.1 v3.1 的顺序假设没有必要

v3.1 的理由是：

> `ExpectedNewSha256` 在写入 manifest 的时刻还不存在（temp 尚未渲染）。

评审指出：真正的约束只有「manifest 必须在替换源文件以前完全持久化」，它**不要求 manifest 一定早于 temp render**。所以只要把渲染提前即可。

而且更关键的是：`transaction.json` 在 v3.1 被定义为**高频更新状态文件**（`state`、`updatedAt`），恰恰是崩溃时最可能滞后于磁盘的文件；而 `ExpectedNewSha` 又是恢复判断最重要的事实之一。把它只放在最容易滞后的文件里不合理。

### 4.2 v3.2 的执行顺序

```text
A. Validate proposal / decisions
B. Normalize patch（SourcePatchNormalizer）
C. Create backup（baseline + snapshot）
D. Render temp（原编码 / 原换行 / 原 BOM）
E. flush temp
F. SHA256(temp) → ExpectedNewSha256
G. Build final RepairExecutionManifest（含 ExpectedNewSha256）
H. Write + flush execution-manifest.json（含目录项）
I. 重新读取 manifest，校验字节 == 刚写入的字节（durable 确认）
J. Replace source
K. journal = SourceReplaced
L. reload → DocumentReloaded
M. SourceVersionTransition
N. 持久化 project / catalog / recovery
O. StateMigrated
P. Committed
Q. 清理 temp；保留 receipt
```

**硬规则不变**：

> manifest durable（步骤 I 通过）以后，才能 Replace source（步骤 J）。

### 4.3 Manifest 与 transaction 的职责

**`execution-manifest.json`（不可变，记录「要做什么」与「做完必须是什么」）**：

```csharp
public sealed record RepairExecutionManifest(
    int SchemaVersion,
    string TransactionId,
    string ProposalId,
    RepairBaseVersion BaseVersion,
    IReadOnlyList<RepairDecisionSnapshot> Decisions,
    TreePatch TreePatch,
    SourcePatch? SourcePatch,
    CanonicalChapterModel ExpectedCanonicalResult,
    string ExpectedNewSha256,
    string BaseSnapshotSha256,
    NewLinePolicy NewLinePolicy);
```

**`transaction.json`（可变，只记录「执行到哪一步」）**：

```text
SchemaVersion, TransactionId, SourcePath, BaseSourceSha256,
State（Prepared | BackupCreated | TempWritten | SourceReplaced
      | DocumentReloaded | StateMigrated | Committed | Conflict | RolledBack）,
CreatedAt, UpdatedAt
```

**从 `transaction.json` 移除**：`candidateId`（改由 manifest 持有 `ProposalId`）、`expectedNewSha256`、fingerprint 字段（改由 manifest 持有）。

**为何不冗余保存 `ExpectedNewSha`**：manifest 不可变，`transaction.json` 里的 `state` 已经能定位事务位置；两者若不一致（理论上不该发生），以 manifest 为准并在 recovery 时进 `Conflict`。

## 5. `SourceEffectDecision` 的精度修正

### 5.1 v3.1 文案混淆了整体与单动作

v3.1 §1.2 写：

```text
ApplyIfAvailable → 编译成功，manifest.SourcePatch == null，
                   UI 标「本项不改原文」，SourceEffectOutcome = Downgraded
```

`manifest.SourcePatch == null` **只在整份 proposal 中没有任何 SourceOperation 时才成立**。评审的反例准确：

```text
Action A → Applied
Action B → Applied
Action C → Downgraded
```

此时 `manifest.SourcePatch` 仍然存在，只是不含 C 的 `SourceOperation`。

### 5.2 v3.2 正式表述

> `ApplyIfAvailable` 且无法产生安全 `SourcePatch` 时，只将**该动作**标记为 `Downgraded`，该动作不生成对应的 `SourceOperation`；**不得据此推导整份 manifest 的 `SourcePatch == null`**。

判据（单动作级）：

```text
DecisionSnapshot(ActionId).Outcome == Downgraded
⇔
SourcePatch.Operations 中不存在 ActionId == 该动作 的 SourceOperation
```

`manifest.SourcePatch == null` 的判据是独立的：

```text
SourcePatch == null  ⇔  所有 Outcome == NotRequested 或 NotApplicable
```

### 5.3 `SourceEffectOutcome` 完整语义

```csharp
public enum SourceEffectOutcome
{
    NotApplicable,   // 该动作类型只改树（Policy = NotApplicable）
    NotRequested,    // 用户/策略决定不动原文（Decision = None）
    Applied,         // 有 SourceOperation 覆盖本动作
    Downgraded       // 请求了但无可靠 SourcePatch；已明确标注
}
```

## 6. `SourceEffectPolicy`：防止核心动作静默降级

### 6.1 问题

v3.1 让 `InsertHeading` / `RetitleChapter` 默认 `ApplyIfAvailable`。这意味着用户明确选了 `EditSource` 之后，若这两个动作无法生成可靠 `SourcePatch`，系统仍然允许降级为「只改树」——TXT 里依然没有标题 / 标题依然是旧的。**这违背用户选择「改原文」的核心意图。**

评审对。

### 6.2 定义

区分两个层次：

- **`SourceEffectPolicy`**：动作**类型**的静态属性，由编译器给出，不由用户选择
- **`SourceEffectDecision`**：**本次决定**的实际取值，由 UI 依据 `Policy + LandingMode + 用户选择` 生成

```csharp
public enum SourceEffectPolicy
{
    NotApplicable,          // 本动作类型不涉及原文
    Optional,               // 有则更好，可降级
    RequiredInEditSource,   // EditSource 下必须能改原文，否则编译失败
    ExplicitOptIn           // 只有用户显式要求才改原文
}
```

### 6.3 映射表

| RepairAction | `Policy` | `TreeOnly` 下的 `Decision` | `EditSource` 下的 `Decision` |
|---|---|---|---|
| `AddChapter` | `NotApplicable` | `None` | `None` |
| `BuildVolumeLevel` | `NotApplicable` | `None` | `None` |
| `KeepExtra` | `NotApplicable` | `None` | `None` |
| `MissingBody` / `OutOfOrderFinding` | `NotApplicable` | `None` | `None` |
| `AdoptHeading`（文本规范化） | `Optional` | `None` | `ApplyIfAvailable` |
| `InsertHeading` | `RequiredInEditSource` | `None` | **`ApplyRequired`** |
| `RetitleChapter` | `RequiredInEditSource` | `None` | **`ApplyRequired`** |
| `RemoveDuplicate`（物理删除） | `ExplicitOptIn` | `None` | 用户勾选 → `ApplyRequired`；未勾选 → `None` |

**生成规则**：

```text
Policy == NotApplicable        → Decision = None
Policy == Optional             → EditSource: ApplyIfAvailable
Policy == RequiredInEditSource → EditSource: ApplyRequired
                                 TreeOnly:  None
Policy == ExplicitOptIn        → 用户勾选 → ApplyRequired
                                 未勾选   → None
```

**用户能否改成更弱？** 不能。用户可以把 `ExplicitOptIn` 从 `None` 提升为 `ApplyRequired`，但不能把 `RequiredInEditSource` 降为 `ApplyIfAvailable`——那等于让用户在一个明确标注「会改原文」的模式里悄悄放弃改原文。若用户不想改原文，正确做法是选 `TreeOnly`。

### 6.4 编译失败时的 UI

`ApplyRequired` 无法生成安全 `SourcePatch` → **编译失败**。UI 只标红该项，允许用户取消勾选或改进选择后重新编译（见 v3.1 §14 待决问题 3 的处置）。

## 7. `RepairEffect`：把三元组升级为类型

### 7.1 v3.1 只写了硬规则

v3.1 §10.3 修正四：

> 每个可执行 `RepairAction` 必须在编译时静态产出（树形态影响, 文本内容影响, 正文归属影响）。任一维度无法确定 → 该动作在 `EditSource` 下禁用。

方向正确，但只是文字约束，依赖开发者记得读文档。评审建议类型化。

### 7.2 定义

```csharp
public sealed record RepairEffect(
    TreeEffect           Tree,
    SourceContentEffect  Source,
    BodyOwnershipEffect  Body);

public enum TreeEffect
{
    None,
    InsertEntry, RetitleEntry, RemoveEntry,
    ChangeLevel, ReassignBodyRanges, BuildVolumeNode
}

public enum SourceContentEffect
{
    None,                 // 不触碰源文本
    ReplaceLine,          // 替换某原始行文本
    DeleteLines,          // 删除若干原始行
    InsertLines,          // 插入若干新行
    Indeterminate         // ← 非法：一旦出现，EditSource 下禁用本动作
}

public enum BodyOwnershipEffect
{
    None,                 // 正文归属不变
    Assign(IReadOnlyList<SourceSpan> Spans),   // 正文归属改变，且已显式确定
    Indeterminate         // ← 非法：同上
}
```

编译器前置条件：

```text
RepairEffect.Source == Indeterminate  → 该动作在 EditSource 下禁用
RepairEffect.Body   == Indeterminate  → 该动作在 EditSource 下禁用
```

**实现层的强制方式**：`SourceContentEffect.Indeterminate` 与 `BodyOwnershipEffect.Indeterminate` 是**必须显式书写**的枚举成员。新增动作类型时，若忘记定义语义，编译器会要求填这三个维度——填 `Indeterminate` 会被 `EditSource` 拒绝，而不是默认放行。

**与 `Policy` 的关系**：两者互补而非重复。

```text
RepairEffect  描述「这个动作实际上做了什么」（客观）
Policy        描述「这个动作在 EditSource 下的可降级性」（约定）
```

先算 `RepairEffect`，再查 `Policy`，共同决定 `Decision` 是否可满足。

## 8. 拆分 `DemoteHeading`

### 8.1 v3.1 的定义仍有内部冲突

v3.1 §10.3 修正三：

```csharp
public sealed record DemoteHeading(
    string ActionId, int Level, bool MergeTextIntoBody, SourceAnchor? Anchor);
```

评审指出两处冲突，均成立：

**冲突一：`MergeTextIntoBody` 与物理删除互斥。**

```text
MergeTextIntoBody = true  → 原标题行文字必须保留并作为正文
DeleteOriginalLine        → 该文字被物理删除
```

两者不能同时成立。v3.1 却写了「`Level = 0` 时若用户选择物理删除该行，则产生 `DeleteOriginalLine`」——此时 `MergeTextIntoBody` 必须为 `false`，但文档没规定。

**冲突二：`Level > 0` 不等于「并回正文」。**

`Level 1 → Level 2` 仍是 heading/node，只是层级改变。这和「移除章节边界」完全不是同一种语义。v3.1 把两者塞进同一个动作。

### 8.2 v3.2 拆为两个动作

```csharp
// 动作一：只改层级，仍是章节/节点
public sealed record ChangeHeadingLevel(
    string ActionId,
    string SemanticTarget,
    int NewLevel,
    RepairEffect Effect) : RepairAction;

// 动作二：移除章节边界
public sealed record RemoveHeadingBoundary(
    string ActionId,
    string SemanticTarget,
    int HeadingLine,
    RemovedHeadingTextDisposition TextDisposition,
    BodyAssignment BodyOwner,
    RepairEffect Effect) : RepairAction;

public enum RemovedHeadingTextDisposition
{
    KeepAsBody,     // 该行文字保留，成为正文
    DeleteText      // 该行文字从原文删除
}
```

**约束**：

```text
TextDisposition == KeepAsBody  → SourceContentEffect 只能为 None 或 ReplaceLine
                                 绝不允许 DeleteLines
TextDisposition == DeleteText  → 必须由用户显式确认（Policy = ExplicitOptIn）
                                 且 BodyOwner 不得包含该行
```

**「这行文字最终归哪个章节」由 `BodyOwner` 显式表达**，不再依赖 `MergeTextIntoBody = true` 这种布尔叙述。这才是评审说的「真正重要的是 `BodyOwnershipEffect`」。

### 8.3 语义对照

| 用户意图 | 正确动作 | `SourcePatch` |
|---|---|---|
| 卷标题降为章标题 | `ChangeHeadingLevel` | 空 |
| 章标题降为小节（仍进目录） | `ChangeHeadingLevel` | 空 |
| 某行不再当标题，文字留在正文 | `RemoveHeadingBoundary(KeepAsBody)` | 空（文字本来就在正文流里） |
| 某行不再当标题，且该行要规范化 | `RemoveHeadingBoundary(KeepAsBody)` | `ReplaceLine` |
| 某行不再当标题，文字一并删掉 | `RemoveHeadingBoundary(DeleteText)` | `DeleteLines` |

## 9. `BodyCut` → `BodyAssignment`（多区间）

### 9.1 v3.1 表达能力不足

v3.1 §10.3 修正二给 `InsertHeading` 加了：

```csharp
public sealed record BodyCut(int FirstLine, int LastLineExclusive);
```

单一连续区间。但现有章节树本来就支持**多个 `ContentRanges`**——正文归属不应退化成单一区间。

### 9.2 定义

```csharp
public sealed record SourceSpan(int StartLine, int EndLineExclusive);

public sealed record BodyAssignment(
    IReadOnlyList<SourceSpan> Spans);      // 允许为空（空章节）
```

**坐标约定（硬规则）**：

> 所有 `BodyAssignment` 的坐标都使用 **`BaseSource` 坐标**。

```text
TreeOnly：
    直接使用这些 Base spans

EditSource：
    Base spans
    → SourceCoordinateMap（逐原始行 → 新行号，被删行为 null）
    → 过滤 null
    → 相邻区间合并
    → NewSource spans
```

**必须验证**：`TreeOnly` 的 spans 与 `EditSource` 映射后的 spans 在 canonical 层面产生相同的 `BodyContentHashes`。两者不同即为真实缺陷，应暴露而不是放宽 canonical。

### 9.3 适用范围

`BodyAssignment` 不只属于 `InsertHeading`。以下动作都必须携带：

| 动作 | `BodyAssignment` 语义 |
|---|---|
| `InsertHeading` | 新章节的正文区间 |
| `RemoveHeadingBoundary` | 边界移除后该行及后续内容的归属 |
| `RemoveDuplicate` | 副本移除后，保留章节的正文区间 |
| `AdoptHeading` | 采纳标题行后正文从哪里开始 |

v3.1 只给 `InsertHeading` 加了，是覆盖不全。

## 10. 三处类型/术语不一致

### 10.1 `DecisionSnapshot` 的 anchor 字段已过时

v3.1 §2.3：

```csharp
int? SourceAnchorLine,         // 例如替换/删除所在原始行
```

但同一份文档 §7.2 已把 `SourceAnchor` 改为判别联合：

```text
BeforeOriginalLine / AfterOriginalLine / EndOfFileAnchor
```

`int?` 无法表达 `Before / After`、`Ordinal`、EOF（`EndOfFileAnchor` 根本没有 line）。

**v3.2 定义**：

```csharp
public sealed record RepairDecisionSnapshot(
    string ActionId,
    RepairActionKind Kind,
    string? SemanticTarget,        // 章节语义 ID，非物理行号
    string? DesiredValue,          // 例如目标标题
    SourceAnchor? Anchor,          // ← 完整判别联合
    SourceBinding? Binding,        // ← 补：坐标解析所需
    BodyAssignment? Body,          // ← 补：正文归属
    bool Selected,
    SourceEffectDecision SourceEffect,
    SourceEffectOutcome Outcome);
```

目的：**恢复 manifest 完全自足**，不需要能重建 planner。

### 10.2 `ProposalId` 碰撞

v3.1 §12.1：

```text
ProposalId = H(BaseVersion, Basis, PlannerSchemaVersion)
```

评审反例成立：

```text
同一本 TXT、同一章节树、同一识别规则
第一次导入目录 A
第二次导入目录 B
```

此时三个输入完全相同，但 `RepairActions` 可能完全不同 → **`ProposalId` 相同**。

**v3.2 定义**（采用评审给出的第二种，最直接且不需要额外定义 planner 输入规范）：

```text
ProposalId = H(BaseVersion, Basis, PlannerSchemaVersion, OrderedActionIds)
```

`OrderedActionIds` 为 `RepairProposal.Actions` 按稳定顺序排列的 `ActionId` 序列。

由于 `ActionId = H(ActionKind, SemanticTarget, SourceLocator/Anchor, DesiredValue, BasisIdentity)`（v3.1 §12.1），目录 A 与目录 B 若导致不同动作集合，`ProposalId` 必然不同；若动作集合完全相同，则两份 proposal 在语义上确实是同一份，ID 相同是正确行为。

**附加好处**：`ProposalId` 同时成为「动作集合指纹」，可用于验证重算的幂等性（同一环境重算两次应得同一 `ProposalId`）。

### 10.3 「析取/合取」术语写反

v3.1 §9.1 我写：

> 这是**析取→合取写反**。

评审指出术语反了，**评审对**：

```text
v3 原文失败条件：  !CanWriteSource && !CanWriteBackup    → 这是「合取」
正确失败条件：      !A || !B || !C || !D                 → 这是「析取」
等价成功条件：       A && B && C && D                    → 这才是「合取」
```

v3.2 改为准确表述：

> v3 §16 第 6 条把「替换源文件所需的四项能力**全部具备**」错写成了「源目录与备份目录**同时**不可写」。失败条件应为析取（任一不具备即禁用），v3 写成了合取，条件过宽。

代码结论不变（`CanEditSource = A && B && C && D`）。

## 11. Phase 2 不提前开放真实 source restore

### 11.1 问题

v3.1 §11.1 把「恢复入口」列进 Phase 2，并说 Phase 1/2 可立即开工。但「恢复入口」如果意味着：

```text
backup bytes → 覆盖当前 source file
```

那么它本质上也是一次 **Source mutation**，恢复后同样必须处理：

```text
ChapterTreeDocument / ChapterTreeDocumentCache / undo-redo /
ConfirmedReviews / ChapterTreePlan / ReferenceCatalog /
_sourceChanged / project recovery state
```

即 `SourceVersionTransition` 的完整职责。在正式事务层出现之前开放它，等于引入一条**没有 transaction 保护的 Source 写入通道**。

### 11.2 v3.2 划分

```text
Phase 2（可立即做）
    备份创建、列出、浏览、导出到任意位置、retention、manifest、
    备份位置设置、未完成 journal 的只读诊断
    「恢复」按钮存在，但行为是「导出为…」，不覆盖当前源文件

Phase 5（正式开放）
    通过 RestoreTransaction
      = SourceEditTransaction 的一个特化（源 = backup bytes）
      + 完整 SourceVersionTransition
    真正开放「恢复为当前原文件」
```

`RestoreTransaction` 复用同一套 preflight / manifest / journal / roll-forward / canonical 校验，**不新增协议**。它的 `SourcePatch` 特殊之处仅在于是「整文件替换」而不是行级操作。

`baseline` 语义仍然遵守 v3 §12.2：**界面不得称其为「绝对原稿」**。

## 14. 对 v3.1 保留清单的确认

1. `ChapterTreeDocument` 保持固定源版本的不可变快照

## 16. 结论

v3.1 引入的恢复期三 fingerprint 校验是**本设计到目前为止最危险的一处错误**——它会让一个已经成功修改原文件的合法事务因用户事后改设置而永久卡住。本版通过明确 `SourceReplaced` 事务分界线修正，并连带收敛了恢复矩阵、manifest 内容与 fingerprint 职责。

第二个收口点是动作语义：`DemoteHeading` 拆为 `ChangeHeadingLevel` / `RemoveHeadingBoundary`，`BodyCut` 升为 `BodyAssignment`，三元组影响升级为 `RepairEffect` 类型，`SourceEffectPolicy` 阻止核心动作静默降级。

**本版之后不再做 v4。下一步是 Phase 0，Phase 1 与 Phase 2 可立即开工。**
