## 2. 两条规则决定整张恢复表

### 2.1 文件说了算，不是记录说了算

journal 是本程序自己写的，而它恰恰是最可能落后的东西 —— 崩溃就落在"做了某件事"与"记下它"之间。
所以事务边界由文件判定：

```
当前 SHA == BaseSha      → 提交还没发生
当前 SHA == ExpectedSha  → 提交已经发生
否则                      → 冲突
```

journal 只说明程序**以为**自己在做什么，用于交叉验证两者是否自洽。

### 2.2 只有一格允许自动完成

整张表里**只有一格**允许自动继续替换：`TempWritten` + 磁盘仍是 Base。那一个例外之所以安全，是因为
`TempWritten` 本身就是一句"本次事务从未跨过边界"的话。

其余"记录领先于文件"的组合一律进冲突。最要紧的是这一格：

> 记录说已替换、文件却是旧的 —— **不自动重做**。最可能的成因是人把旧版本放了回来，
> 再替换一次就会把他刚做的事悄悄毁掉。

有一条测试专门断言这张表里 `ContinueReplace` **恰好出现一次**：多一格就意味着某处的自动行为会
覆盖用户的动作。

## 3. 修掉 v3.3 记录的写权限错误

旧检查问的是：

> 源目录与备份目录**都**不可写吗（`!A && !B`）

而正确的条件是四项能力**全部**具备：

```csharp
CanEditSource = CanReplaceSourceFile && CanCreateSiblingTemp
             && CanWriteJournal && CanWriteBackupTarget
```

失败的判定应是析取（缺任一即失败），旧检查写成了合取，条件过宽。**源目录只读时备份目录通常可写**，
旧问题答"否"，却根本无法替换源文件 —— 因为同目录的临时文件建不出来。

`SourceEditPreflightInspector` 逐项**实际尝试**，而不是读只读属性：只读属性、缺少权限、磁盘满、
文件被锁都会表现为"不能写"，只有真的写一次才能区分。探测过程不留任何东西。

## 4. 执行清单：让被中断的事务可恢复

替换之后崩溃时，程序手里有补丁、有候选 id、有两个哈希，却**不知道章节树本该变成什么样**。
补丁说的是哪几行变了，没有任何地方说本该存在哪几章。

而它**不能重新推导**：重跑 planner 会基于已经替换过的文件、可能已经不同的识别规则，结果不保证
是用户当初接受的那份。所以意图在动任何东西之前写一次，之后**读回来**而不是重算。

**写入纪律**：`WriteThrough` + `Flush(flushToDisk: true)`，然后读回校验。读回只证明"写入的内容
没损坏、没写错文件"——持久性是 flush 的责任，注释里也这么写，不宣称更强的东西。

`ExpectedNewSha256` 放在清单里而不是 journal 里：恢复信任的那份文件，必须是不能漂移的那份。

## 6. 实现中途改掉自己一处错误

第一版把预期章节存成**一行文字描述**：

```
Kind|Level|是否进目录|标题来源|父路径|标题|正文段数
```

只存了正文哈希的**个数**，没存哈希本身。于是恢复只能比对树的形状、**不能比对内容** —— 而带着预期
结果的全部意义就是证明"建出来的树正是当初商定那棵"。

改成逐字段结构化存储。测试也据此加强：断言往返之后 `EqualsByContent` 为真、且正文哈希**总数**相等。

> 教训：把结构压成一句给人读的文字时，要想清楚**还有谁会读它**。这里还有一个读者是恢复逻辑，
> 而它需要的是能比对的内容，不是能读懂的一句话。

## 8. 5c：事务状态机与真实的原子替换（已完成）

### 8.1 六步顺序，每步都有理由

| # | 步骤 | 为什么是这个位置 |
|---|---|---|
| 1 | 确认文件仍是计划所依据的那一版 | 不是就说明别人改过它，计划描述的书已经不存在 |
| 2 | 备份 | 第一次写入之后再做的备份不算备份 |
| 3 | 渲染到**源文件旁边**的临时文件 | 替换必须是一次卷内改名；跨卷复制可能只做一半，留下一本写了一半的书 |
| 4 | 清单先落盘并 flush | 文件一改，崩溃留下的工作就只能靠清单完成 |
| 5 | `File.Replace` 原子替换 | 要么发生要么不发生；不支持的平台回退到 staged move，**且失败时把原文件放回去**而不是留下空路径 |
| 6 | 之后才记进度 | journal 允许落后，清单不允许缺失 |

事务本身不决定**写什么** —— 它接收一份早已冻结的清单并执行它。

### 8.2 六卷样书实测

```
=== 场景：真的把样书副本换成修复后的版本 ===
   Committed：已改动原文；备份：…\事务备份\原始.bak
   新版本哈希符合预期：True
   备份就是旧版本：    True
   临时文件已清掉：    True
   文件可按章节树读回：True
   记录状态：          Committed
   还有未完成事务：    False
   重启恢复判定：      RollForward（文件已是新版本，应继续完成而非再次替换）
   恢复后文件未被二次改动：True

=== 样书本体 ===  SHA-256 未变：True  正文未变：True
```

「重启恢复判定 RollForward」这一项是模拟"替换之后崩溃、重启"：把记录退回 `SourceReplaced`，再让恢复逻辑判断。它选择**继续完成**而不是再次替换 —— 这正是"不重复应用补丁"那条规则在真实文件上的样子。

### 8.3 修掉一个真实缺陷：`Encoding.UTF8` 的 BOM

`SourceTextDocument.Parse` 的默认编码是 `Encoding.UTF8`，而那个实例的 `GetPreamble()` **返回 BOM**。
于是渲染写盘时凭空多出三个字节，与按文本算出的 `ExpectedNewSha256` 对不上：

```
Expected: "5C686D95691AAAED…"   ← 按文本算
Actual:   "080D1F67F98AE9AE…"   ← 实际写进文件的（前面多了 EF BB BF）
```

**是真实替换把这件事抓出来的** —— 纯内存的 Phase 4 永远发现不了，因为那时没有人去问"磁盘上的字节是什么"。
样书本身没有 BOM（75029 字节、SHA 完全匹配），所以问题 100% 出在编码对象的默认值上。

改为 `new UTF8Encoding(encoderShouldEmitUTF8Identifier: false)`，并在注释里写明为什么不能图省事用
`Encoding.UTF8`。

### 8.4 测试里也修掉自己两处错误

1. 手写行数算术去重复 `RepairIntegrity` 已有的检查 —— 第一次就算错了（把 front matter 算成第一个标题
   之前的行数，少了 567 行）。改用现成的验证器。

2. 断言「每一行都被某个章节认领」—— **这条本来就错**：第六卷每章两行相同标题，识别阶段把重复那行从
   条目里剔除，所以那 100 行不属于任何章节正文，**而那是对的**（它们不出现在成品里）。2503 行认证
   2403 行，差的正是那 100 行。

> 顺带说明：旧的行守恒检查看不出这件事，因为它管的是"行有没有凭空消失"，不是"行有没有出现在不该
> 出现的地方"。盯后者的是 `LandingModeEquivalenceTests` 那一层。

## 9. 5d：坐标表与版本迁移（已完成）

替换原文只解决了"盘上的文件"，内存里的东西全都还指着**旧的**行号：章节树的标题行、目录的落点、
按行号确认过的复核、断点。行号只对一个版本的文本有意义，所以文件一换，"第 812 行"这句话就作废了。

### 9.1 `SourceCoordinateMap`：唯一的那座桥

它记录每个旧行号去了哪里，**并且被验证**。验证分五条，每条都针对一种"表是错的但不报错"的形状：

| 检查 | 挡住的形状 |
|---|---|
| 映射与补丁的声明一致 | 表是照另一个补丁造的 |
| 排出的行数 = 原文 − 删 + 插 | 排行的循环少走了一行（我第一版就漏了文件最后一行） |
| 新文本行数与补丁算出的行数一致 | 文本被多塞了一行 |
| 每一行的新文本内容 = 它声称来源的那一行（除非表说它被替换） | 表把改动过的行当成"原样保留" |
| 没被任何操作提到的行，内容必须没变 | 补丁之外偷偷改了字 |

第四、五条是**唯一**能发现"补丁与文本不一致"的检查：前三条都在拿表和补丁互相印证，
而一个空补丁配一份被改写过的文本，在前三条下完全自洽。实测里"补丁为空但文本已变"这一格正是
靠第四条拦下来的。

### 9.2 `SourceVersionTransition`：六步，每步自证

每一步回答三个问题：**还需不需要做**（`Applies`）、**做了返回新状态**（`RunAsync`，不原地改）、
**做完是否达到它自己声明的条件**（`Verify`）。第二个问题的答案是新状态而不是就地修改，
是为了让"后置条件不满足"时不会留下一半改动。第三个问题让这个流程可重复执行
（`Applies` 为假就跳过），所以迁移跑第二遍什么都不做 —— 实测确认。

| 步骤 | 做什么 | 后置条件 |
|---|---|---|
| 采用新文本并作废旧解析 | 从**文件**重读（不相信调用方递来的字符串），作废缓存 | 内存文本与磁盘逐字节一致、且缓存不再复用 |
| 核对坐标表与新文本 | 拿第九节的五条检查表 | 文本满足补丁的声明 |
| 按新原文重新识别章节树 | 不带旧计划重新读（旧计划的哈希与新文件不符，读入会正确地拒绝） | 识别树描述的是新版本的字节 |
| 把已保存的章节树移到新行号 | 逐条重绑身份，见 9.3 | 通过 `ValidatePlan` |
| 作废按旧行号记录的复核与断点 | 直接丢弃 | 不再保留任何旧行号结论 |
| 把已保存目录挂到新版本 | 目录按源哈希存放，换版本后按新哈希什么都找不到 | 新哈希下能读到同样的记录 |

### 9.3 身份存亡：五条规则，逐条有据

| 情况 | 结局 | 理由 |
|---|---|---|
| 标题行还在 | `Rebound`，行号更新 | 这一行还是这一章 |
| 标题行被删 | `LostLineDeleted`，改成靠标题记 | 它还有正文；身份退回"待插入标题"那一类 |
| 标题行被**改写** | `LostLineReplaced`，条目丢弃 | 那一行现在是别的字，"L812"不再指这一章 |
| 连标题带正文都没了 | `LostNoBody`，条目丢弃 | 空章节不是章节 |
| 本来就没有标题行 | `TitleKeyed`，原样保留 | 它的身份从来不是行号 |

实测（六卷样书，对齐目录补丁）：**469 个条目 → 保留 400、失效 69**。69 个全部是
`LostLineReplaced`，也就是 `Retitle` 改过的那 69 行所在的章节；每一行的文本都被改写或消失了。

### 9.4 六卷样书实测

**第一段：真实补丁（69 个替换）**

```text
原文版本迁移已完成。 章节身份：保留 400 个，失效 69 个（第六十四章 丙64 重逢古渡、…）
身份存亡：Rebound 398、TitleKeyed 2、LostLineReplaced 69
行数守恒：1936 − 317 = 1619，迁移后实际 1619
失效原因分布：非「标题行被改写」的失效 0 个
每一个失效都对应一行真的被改写：True
第二次运行：执行 0 步、无需执行 0 步、新重绑 0 条；第二次的树与第一次逐条相同：True
```

"行数守恒"这一条是专门为"317 行不见了"设的：先按**原始条目**逐条比（而不是按身份记录反查，
反查会漏掉没有身份记录的条目），把减少的行数算出来，再要求 `迁移前 − 减少 = 迁移后`。

**第二段：真实删除（100 行重复标题）**

```text
由连续重复标题块推导出 100 个删除操作，确认与前一行完全相同：100/100
删除后：2402 行（删 100、改 0、插 0）
坐标表自洽：True  原文 2502 行 → 新文 2402 行，删除 100、替换 0、插入 0
被删的 100 行里原本有主的：0 行
迁移后正文断成多段的章节：0 个
迁移后的正文行落到该章旧正文之外：0 行
```

"原本有主的 0 行"是关键的一条实测事实：样书里那 100 行重复标题**不属于任何章节的正文区间**
（整本 2503 行里有 567 行无主，这是识别规则的既有边界，Phase 2 已记录）。所以"删掉它们会让正文
断成两段"在这本书上**不会发生** —— 分段的代码路径没有被这本书走到，这不是缺陷，是数据如此。

**第三段：四种篡改全部被拒**

```text
替换行号整体 +1：     成功 False（第 783 行被记为原样保留，但内容变了）
补丁为空但文本已变：   成功 False（同上）
新文本多一行：         成功 False（补丁声明应得 2502 行，新文本却有 2504 行）
补丁谎称删掉第 1 行：   成功 False（补丁声明应得 2501 行，新文本却有 2502 行）
样书本体 SHA-256 未变：True
```

### 9.5 实测抓到的一处真实缺陷：重新识别覆盖了用户的树

`ReloadRecognitionTreeStep` 最初写成 `state with { RecognitionTree = tree, Plan = tree.CreatePlan(tree.Entries) }`
—— 顺手把"计划"也换成了重新识别的结果，而**计划是用户编排过的那棵树**。

后果是静默的：迁移报告"章节身份：保留 0 个，0 个失效"，看起来一切正常，实际上用户调过的章节树
已经被一次重新识别替换掉了。实测里表现为"待迁移的树 469 个条目"变成"没有身份要搬"。

修正是这行只替换识别结果，计划留给下一步去搬：

```csharp
// Only the recognition result is replaced. The plan — the tree the user arranged — is deliberately
// left alone: it still carries the old version's hash, and the next step is what moves it onto the
// new numbering.
return state with { RecognitionTree = tree };
```

这条现在有一个专门的测试（`Reloading_the_recognition_tree_does_not_replace_the_users_own_tree`）。

### 9.6 实测抓到的第二处：相邻区间被合并，一章吞掉下一章

`RebindRanges` 最初合并"相邻"的区间。但两个区间可以**因为中间的行被删掉**而在新行号下变得相邻 ——
删除把间隔抹平了。这时合并会把后一章的标题和正文整段划给前一章。

实测形状（样书第六卷）：第七章的正文 1941–1944 与新行号相邻的、原本属于第八章的 1945–1950
被并成一段，第七章因此"拥有"了第八章。

修正：只有区间之间的那些新行**确实都是被删掉的行腾出来的空位**（`SourceMap` 说它们没有来源、
且文本为空）时才合并。这是一条防御性修正 —— 在六卷样书上没有触发（那 100 行本来无主），
但它是"合并"这个动作唯一说得通的条件。

### 9.7 顺带修掉的一处同类缺陷：两个解码器

内存里的 `SourceTextDocument` 原先用 `File.ReadAllText`（永远假定 UTF-8），而章节树走
`TextFileDecoder`（BOM 探测、严格 UTF-8、GBK 回退）。同一份 GBK 书稿在两条路径下会得到**不同的字符**，
因而**不同的行号** —— 坐标表在这种情况下不可能对。

现在两边都走 `SourceTextDocument.Decode`（内部就是 `TextFileDecoder`）。同时
`SourceFileHasher.HashOfRendered` 成为"事务写出的字节"的规范哈希：它把 BOM 算进去，
而旧的事务代码用 `Encoding.UTF8.GetBytes(text)` 做哈希 —— 带 BOM 的文件在**替换之后**
才会发现哈希对不上。

### 9.8 测试

新增 **29** 个（`SourceCoordinateMapTests` 14、`SourceVersionTransitionTests` 15），
Core 总数 673 → **702，全部通过**。

其中 14 个是"必须拒绝"方向的：表与补丁不符、文本与补丁不符、多一行、被偷改的行、
空补丁配改写过的文本。验证器的价值在它能挡住什么。

### 9.9 探针新增两个命令

- `sim transition` —— 上面三段的完整实测。
- `sim ranges <行号…>` —— 打印一本小书在删除若干行前后的章节范围与身份存亡。

第二个是**写测试断言之前必须先跑的东西**：章节的正文区间从哪里开始到哪里结束，规则不止一条

## 10. 5e：恢复事务与恢复目标（已完成）

### 10.1 先解决一个前置问题：两版文本之间没有补丁

修复自带补丁；**恢复没有**。要恢复的那个版本是早先存下的，手上只有"当前文本"和"那一版文本"。

而 `SourceVersionTransition` 需要补丁：它靠补丁建立坐标表，靠坐标表把章节树搬过去。所以先要能从两版
文本推出补丁 —— `SourceDiff`（最长公共子序列）。

为什么必须是**最省**的那一份脚本，而不是随便一份能用的：一个三次编辑之前的版本与当前版本只差几行，
而"整本替换"的脚本会让每一个章节都判成"标题行被改写"，把从来没动过的身份全部丢掉。
LCS 就是让没动过的行保持没动过的东西。对齐表超过 4000 万格时退化为"全部不同"
（对两本真的毫无共同之处的书，答案本来就是同一个，而调用方拿到的是这个答案，不是一次二次方爆炸）。

实测（六卷样书，2502 行 × 2502 行 ≈ 626 万格）：修复前后的两个版本，脚本只提到 ≤140 行，
没有退化成整本替换。

### 10.2 `RestoreTargetPolicy`：两种产品语义，不是一个功能的两条路

| | 恢复什么 | 章节树从哪来 | 什么时候可用 |
|---|---|---|---|
| `SourceOnly`（默认） | 只有原文 | 按恢复后的文本重新识别 | 总是可用 |
| `FullBookState` | 原文 + 当时的章节树 | 随快照保存的那一棵 | 只有那一版存了树 |

默认取 `SourceOnly`，这是设计文档 §10.5 留给实测决定的一项。理由有三条：它总是可用（不依赖当初是否
存了树）、行为可预期（恢复 = 回到那版文本）、并且是"我只想把原文拿回来"的读者要的东西。
`FullBookState` 是明确的高级选项。

**没有保存的树时，`FullBookState` 必须拒绝。** 拿一棵重新识别的树顶替，会把这次恢复本来要救回来的东西
丢掉（用户编排的那些章节），却报告成功。拒绝的消息里指出改用「只恢复原文」。

### 10.3 恢复不是一条特殊路径

这是这次实现里唯一需要坚持的设计判断。恢复走的是同一个事务：前置检查、先备份、sibling 临时文件、
清单先落盘、原子替换、journal 收尾、roll-forward。区别只有两点 —— 目标文本来自快照而不是编译出来的
补丁，以及事后那棵树是重新识别的还是快照里的。

理由很直接：**两条写源文件的路径就是两个地方可以忘记"先备份"这条规则。**

```
RestoreTransaction.ExecuteAsync
  1. 备份不在 / 原文不在 / 原文本已被外界改过      → 拒绝，不碰任何东西
  2. FullBookState 而没有树，或树不属于这份备份     → 拒绝
  3. 已经是这个版本                                → 拒绝（替换是 no-op，而 journal 分不清两个状态）
  4. SourceDiff 推出补丁 → 坐标表 → 逐行验证        → 不一致就拒绝
  5. 事前算好"恢复后应当是什么"（快照的树 / 新文本的识别结果）并写进清单
  6. SourceEditTransaction：先备份当前版本，再原子替换
  7. afterReplace 回调：SourceVersionTransition 把树搬到恢复后的文本
     FullBookState 时，搬完再用快照的树覆盖计划（迁移仍然先跑 —— 它负责报告哪些身份没跟过来）
```

第 5 步是"恢复也自足"的关键：崩溃之后，清单里已经有"这本书应该变成什么"，
不需要重新识别（那会取决于恢复时生效的规则，而不是用户当初同意的规则）。

### 10.4 5a 就要求、5e 才落地的预留位

设计文档 §10.4 要求 Phase 2 的备份层**预留** `FullBookState` 的位置，即使当时不写内容。5e 补齐：

```text
<备份根>/<路径哈希>/
    manifest.json                              ← 新增 FullStateSnapshotCount 字段
    baseline/original.bak
    snapshots/<sha256>.bak
    snapshots/<sha256>.tree.json               ← 5e 开始写入
```

`.tree.json` 用手写 DTO 而不是直接序列化 `ChapterTreePlan`：树的条目是记录，但序列化器一旦接手，
类型名就成了文件格式的一部分。行数与源哈希一起存，读回来时**真的校验** —— 一棵行号越界的树
读成"没有树"，而不是"大概能用"。这比没有树更危险：它看起来完全正常。

清理快照时会连 `.tree.json` 一起删。否则会留下一棵"有树但没有字节"的孤儿，
而 `FullStateSnapshotCount` 会把它算进去 —— 界面于是提供一个点了会失败的恢复。

### 10.5 六卷样书实测

```text
要恢复的版本  69D722398237438E…  2502 行  （快照带树：True，468 个条目）
当前版本      5C686D95691AAAED…  2502 行（删 0、改 69、插 0）

策略一：只恢复原文
   Restored：已恢复原文。… 有 69 个章节身份没能跟过来
   磁盘哈希回到原版：True      正文逐字节等于原版：True
   被换掉的那一版已存下：True   事务记录状态：Committed   还有未完成事务：False
   临时文件已清掉：True        恢复后的状态哈希与磁盘一致：True
   身份存亡：Rebound 398、TitleKeyed 1、LostLineDeleted 69

策略一再来一次（已经是这个版本）：Refused，磁盘未被再次改动：True
备份不在了：Refused

策略二：恢复完整书稿状态
   Restored：已恢复原文与章节树
   磁盘哈希回到原版：True      章节树来自快照：True（468 vs 468）

没有保存的树却要求完整状态：Refused（指出可以改用「只恢复原文」），书稿未被改动：True
样书本体 SHA-256 未变：True
```

**一个值得记下来的细节**：同一个 69 行，在两次迁移里失效的原因不同 ——

- 修复时（`Retitle` 改写标题行）：`LostLineReplaced 69`
- 恢复时（那一行变回原文的标题）：`LostLineDeleted 69`

两次都对。判定用的是**标题行的身份是否还在**，而不是"这一行有没有被改过"：
改写让身份失效，删除让身份退回标题键（而这些章节连正文都没有，于是也失效）。同一套规则、
两种方向的改动，结论不同而各自成立 —— 这正是把规则写成"按坐标表判"而不是"按操作类型判"的收益。

### 10.6 顺带补上的加载入口

`ChapterTreeDocument.Load` 现在可以从**字节**读，不只从路径。恢复要识别的是快照的文本，
而快照是 `.bak` 文件，路径入口按扩展名拒绝非 `.txt`。绕开的办法是复制成临时 `.txt` ——
为一个已经读进内存的东西写一份书稿大小的文件，而且进程中途死掉就留在盘上。

共 29 个中的 20 个属于 5e），Core 总数 702 → **731**，全部通过。

## 11. 5f：六个阶段各崩一次（已完成）

Phase 5c 结束时只覆盖了"替换之后失败"这一格。事务有六步，就是六个可以落地的崩溃点，而恢复规则
在每一格都不同 —— 那张表只有真的停在每一个点上才算被检查过。

### 11.1 在真实事务里中断，而不是手工捏一条记录

`SourceEditTransaction` 多了一个 `AfterStep` 钩子：每一步之后调用一次，抛异常就当作这一步失败。
生产环境为 null，没有任何地方设置它。

为什么不手工造一条 journal 再问"接下来该怎样"：那样测的是**我理解的记录**，不是事务真正留下的记录。
一步之后到底写没写、写了什么，只有让事务自己跑到那里才知道。

配套的 `TransactionInterrupted` 是一个独立异常类型而不是 `IOException`：两者留下的记录必须一样，
但只有后者意味着机器出了问题。

**钩子不能改写记录。** 第一版在捕获中断时把 `RolledBack` 写了回去，于是"崩在 TempWritten"
变成了"崩在 RolledBack"，测试拿到的是被自己改过的状态。中断路径不碰源文件，
所以记录停在哪儿、文件就配得上哪儿。

### 11.2 恢复从"只报告"变成"真的做完"

5a/5c 的 `RecoverAsync` 对替换之后的几格只返回一句"需要按事务清单继续完成"。
结果是六个崩溃点里有一半要人来收尾 —— 而程序明明知道怎么收尾。现在它真的做：

| 记录状态 | 磁盘 | 恢复动作 | 做什么 |
|---|---|---|---|
| `Prepared` / `BackupCreated` | 原文 | `Discard` | 作废记录，没有改动需要撤销 |
| `TempWritten` | 原文 | `ContinueReplace` | **自动完成替换**（改名前核对临时文件的哈希） |
| `SourceReplaced` / `DocumentReloaded` | 新版本 | `RollForward` | 补做替换之后的步骤，**绝不再次替换** |
| `StateMigrated` | 新版本 | `Finish` | 只清残留 |
| `Committed` | 新版本 | `CleanUp` | 只清残留 |
| 任意 | 都不是 | `Conflict` | 停下来，交给人工 |

`TempWritten` 那一格**刻意不依赖清单**。这是修一个自己刚写出来的矛盾：崩溃可以正好落在
"写完临时文件"与"写清单"之间，那时要求清单就等于宣布这一格永远无法自动完成，
而恢复表说它是唯一可以自动完成的一格。判据改用记录里本来就有的两个哈希 —— 足够做那个核对。

### 11.3 `Recovery_never_replaces_the_source_a_second_time`

这条不变量值得单独一个测试。文件里已经是商定的那一版时再替换一次，是恢复唯一能毁掉
"本程序之外有人改过它"的动作。测试对六个崩溃点各跑两遍恢复，要求第二遍不改变任何东西。

写这条时我先写错了断言：以为"恢复不该改变文件"。但 `TempWritten` 那一格恢复**就该**完成替换 ——
"没变"对它不成立。正确的不变量是**恢复两次 == 恢复一次**，而不是"恢复 == 不动"。

### 11.4 测试

新增 **28** 个（六个崩溃点 × 4 条断言 + 4 条单点），Core 总数 733 → **761**。

覆盖：崩在哪一格文件都只能是两个版本之一；替换之前的三格原文一字未动、且从 `BackupCreated` 起
备份已存在；六个点恢复之后都不再有未完成记录；替换之后的三格恢复补完且文件停在新版本上；
`SourceReplaced` 崩溃时恢复会补做替换之后的步骤；`StateMigrated` 崩溃时恢复**不**重跑它；
外界改过文件时判定为冲突并且不碰那个文件。
