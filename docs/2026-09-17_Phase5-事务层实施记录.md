## 2. 两条规则决定整张恢复表

### 2.1 文件说了算，不是记录说了算

journal 是本程序自己写的，而它恰恰是最可能落后的东西 —— 崩溃就落在"做了某件事"与"记下它"之间。
所以事务边界由文件判定：

```
当前 SHA == BaseSha      → 提交还没发生
当前 SHA == ExpectedSha  → 提交已经发生
否则                      → 冲突
```

journal 只说明程序**以为**自己在做什么，用于交叉验证两者是否自洽。

### 2.2 只有一格允许自动完成

整张表里**只有一格**允许自动继续替换：`TempWritten` + 磁盘仍是 Base。那一个例外之所以安全，是因为
`TempWritten` 本身就是一句"本次事务从未跨过边界"的话。

其余"记录领先于文件"的组合一律进冲突。最要紧的是这一格：

> 记录说已替换、文件却是旧的 —— **不自动重做**。最可能的成因是人把旧版本放了回来，
> 再替换一次就会把他刚做的事悄悄毁掉。

有一条测试专门断言这张表里 `ContinueReplace` **恰好出现一次**：多一格就意味着某处的自动行为会
覆盖用户的动作。

## 3. 修掉 v3.3 记录的写权限错误

旧检查问的是：

> 源目录与备份目录**都**不可写吗（`!A && !B`）

而正确的条件是四项能力**全部**具备：

```csharp
CanEditSource = CanReplaceSourceFile && CanCreateSiblingTemp
             && CanWriteJournal && CanWriteBackupTarget
```

失败的判定应是析取（缺任一即失败），旧检查写成了合取，条件过宽。**源目录只读时备份目录通常可写**，
旧问题答"否"，却根本无法替换源文件 —— 因为同目录的临时文件建不出来。

`SourceEditPreflightInspector` 逐项**实际尝试**，而不是读只读属性：只读属性、缺少权限、磁盘满、
文件被锁都会表现为"不能写"，只有真的写一次才能区分。探测过程不留任何东西。

## 4. 执行清单：让被中断的事务可恢复

替换之后崩溃时，程序手里有补丁、有候选 id、有两个哈希，却**不知道章节树本该变成什么样**。
补丁说的是哪几行变了，没有任何地方说本该存在哪几章。

而它**不能重新推导**：重跑 planner 会基于已经替换过的文件、可能已经不同的识别规则，结果不保证
是用户当初接受的那份。所以意图在动任何东西之前写一次，之后**读回来**而不是重算。

**写入纪律**：`WriteThrough` + `Flush(flushToDisk: true)`，然后读回校验。读回只证明"写入的内容
没损坏、没写错文件"——持久性是 flush 的责任，注释里也这么写，不宣称更强的东西。

`ExpectedNewSha256` 放在清单里而不是 journal 里：恢复信任的那份文件，必须是不能漂移的那份。

TempWritten       Expected    RollForward       文件已经是替换后的版本，继续完成其余步骤。

## 6. 实现中途改掉自己一处错误

第一版把预期章节存成**一行文字描述**：

```
Kind|Level|是否进目录|标题来源|父路径|标题|正文段数
```

只存了正文哈希的**个数**，没存哈希本身。于是恢复只能比对树的形状、**不能比对内容** —— 而带着预期
结果的全部意义就是证明"建出来的树正是当初商定那棵"。

改成逐字段结构化存储。测试也据此加强：断言往返之后 `EqualsByContent` 为真、且正文哈希**总数**相等。

> 教训：把结构压成一句给人读的文字时，要想清楚**还有谁会读它**。这里还有一个读者是恢复逻辑，
> 而它需要的是能比对的内容，不是能读懂的一句话。
