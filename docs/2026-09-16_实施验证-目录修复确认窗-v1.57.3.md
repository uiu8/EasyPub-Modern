## 2. 原窗口为什么"简陋"（已复查确认）

不是没信息，是顺序把重点埋了。旧 `ChapterAutoRepairPanel` 把文本拼成一个只读 `TextBox`：
参考来源 → verdict → **264 个未匹配标题** → 分类账目 → 最后才是「实际变化」。
窗口 580 高、默认停在顶部，用户真正想看的东西在几百行之外。

更关键的是**没有任何复选框**：`apply.Click` 直接 `DialogResult = true`，随后套用
`plan.DefaultSelection`。底层其实早就具备逐项选择的条件（`ReferenceAction.Recommended`
就是为此准备的），只是 UI 从未暴露。

## 4. 两个必须知道的实现细节

### 4.1 为什么不能直接再调一次 `ReferencePlanner.Apply`

预览（`Build`）已经用 `plan.DefaultSelection` 套用过一次，`outcome.Entries` 是那次的结果。
确认窗里若再对 `snapshot.Entries` 跑 `Apply`，等于让同一棵树自己验证自己；而且
`Apply` 内部会再调 `RepairIntegrity.Verify`，行守恒一旦不满足就抛异常。

`RebuildWithSelection` 是唯一同时知道"用户选择"和"卷重建"的地方：它用原始
`document.Entries` 重算，并按 `outcome.VolumeRestartIndexes` 重放推断卷那一步。
**重启点不从重建后的树反推** —— 那是另一个问题。

### 4.2 主题必须用 `SetResourceReference`，不能直接读 `Application.Current.Resources`

`ThemeManager.Apply` 是替换 `Application.Current.Resources` 里的画刷实例。
构造时直接取 `(Brush)Application.Current.Resources["..."]` 会**钉死**在当时的主题上，
深色模式不生效。窗口全部用 `SetResourceReference(...)` 才跟随主题（实测已确认）。

## 6. 复现与核对用的探针

`work/repair-review-capture/`（Git 忽略）：用一本真实书稿跑
`ChapterAutoRepair.Prepare`，再渲染**真实的** `RepairReviewWindow`（不是设计稿、也不是
原型里的示例数据），产出 PNG。

```powershell
$d = "D:\software\dotnet-sdk-10.0.302\dotnet.exe"; $p = "work\repair-review-capture"
& $d run --project $p -c Release -- outputs\repair-review\v5-light.png Light
& $d run --project $p -c Release -- outputs\repair-review\v5-dark.png Dark
```

> 探针每次都会打印 `resolved[Light]` / `resolved[Dark]` 两行已解析画刷，用来核对主题：
> `RenderTargetBitmap` 渲染屏幕外窗口时会保留它**最初解析到的**画刷，所以深色截图曾经与浅色
> **字节完全相同**。像素不可信时，读元素实际解析到的颜色才是可信的。
>
> 另外两个会让截图"看起来没变、其实是假的"的坑，都实测踩过：
> 1. **探针只重建自己，会用过期的 `EasyPub.Desktop.dll`** —— 症状同样是截图没变。
>    改动 Core/Desktop 后要先清 `obj`/`bin` 再渲染。
> 2. **`App.xaml` 的 `StartupUri="MainWindow.xaml"`** —— 探针一旦 `Show()` 窗口，WPF 会把真正的
>    `MainWindow` 也建出来，而它的构造函数按**用户保存的主题**重设了一遍，把探针要的主题覆盖掉。
>    深色因此渲染成浅色。探针现在用反射清掉 `Application` 的 `_startupUri` 字段
>    （该属性不接受 null，只能清字段）。一处渲染一个窗口的探针不该把整个应用带起来。

`work/repair-dialog-preview/`（上一轮的原型）与 `outputs/repair-dialog-preview/v3-*.png`
是**设计阶段**的产物，数字是示例；真实实现以 `v4-*.png`（右栏底部清单版）与
`v5-*.png`（左栏改动清单版）为准。

### AtomGit：先是 400，重试后成功（结论：暂时性限制）

首次运行 `publish-atomgit.ps1` 在创建 release 时失败：

```
POST /api/v5/repos/Wohl/EasyPub-Modern/releases
400 {"error_code_name":"UN_KNOW",
     "error_message":"gitcode: this operation is not allowed because the repository is an image repository."}
```

当时的排查（都排除了）：

- 不是令牌：同一令牌 `GET /releases/latest` 返回 200。
- 不是请求体：最小 payload（仅 `tag_name`）同样 400。
- 不是脚本：`v1.57.2` 就是今天 15:25:30 用同一个脚本、同一个仓库创建的。
- 仓库字段正常：`fork=false`、`repository_type=code`、`public=true`。

**约 20 分钟后重试，`HTTP 200` 创建成功，随后上传两个附件并回校验通过。**
期间仓库**没有任何配置改动**。所以这是一个**暂时性**限制（很可能是镜像同步任务执行期间
对仓库加了临时写锁），**不是"AtomGit 发不了版"**。这条判断我一开始写错过，已改正；
`docs/RELEASING.md` §3.5 也补了对应的处置办法：遇到它先等一会儿重试，再去看仓库的镜像设置。

**顺带修掉了脚本的一个真问题。** 原逻辑是"查到版本已存在就整体退出"，但创建与上传是两步，
中途断掉会留下一个**没有附件、又永远删不掉**（DELETE 返回 405）的 release —— 而本次恰好
就是这个状态（release 已建、附件为零）。现在脚本改成**幂等续做**：版本号已存在时转入补传，
只上传缺失的附件，已存在的不重传。首次发布与中断后补传走同一段代码，这两条路本次都实测过。

**回退路径验证**（`work/update-probe 1.57.2 --atomgit`）：

## 8. v1.57.3 之后：用户实测反馈的第二轮（问题 1–5）

用户在真机上完成 v1.57.2 → v1.57.3 更新后，发来五条反馈。全部落地，提交 `7df798f`、`b491980`、`faa559f`、`50fe7d1`。

### 「实际变化 286 项」的真正来源（两个真缺陷）

**① `DescribeChanges` 的参数传反了。** 新增的结构化 `Describe(after, before)` 被兼容层以
`Describe(before, after)` 调用，于是增删完全颠倒。表现是"新增"和"移除"互换，极具迷惑性；
排查中一度误判为 MSBuild 缓存、列表不稳定，最后靠打印参数本身才定位。
**教训：两个同为 `IReadOnlyList<ChapterTreeEntry>` 的参数，编译器不会帮你检查顺序。**

**② 按树的 `Id` 判断增删，而重建会换 `Id`：**

- 重建卷层级时每个卷拿到新 `Guid`（`ReferencePlan.cs:242`）→ 同一个卷被算成"移除 + 新增"，
  措辞还是「移除章节项」，读起来像正文被删了；
- 前言同样换 `Id`（`ReferencePlan.cs:207`）→ 报出「移除章节项：序」。实际上前言是被**复用**
  的（`ReferencePlan.cs:206` 用 `entries.FirstOrDefault(IsFrontMatter)`），不是删除。

现在改为：先按 `Id` 匹配；`Id` 不在了才用**稳定身份**——卷按标题、其余按原文行。

### 变化清单改成按类型聚合

一行一条的平铺清单本身就是用户最初抱怨的东西。现在按 `RepairChangeKind` 聚合成十来行，
每行给数量与一个例子，明细收进 `Expander` 默认折叠。真实书稿：**286 项 → 18 项 4 类**。

并且**随勾选实时重算**——之前是窗口构造时用预览结果算死的，勾选变化后不更新。
选择与预览一致时直接复用预览结果，避免重复验证整棵树。

### 层级变化必须独立成类

14 条「层级 1→2」是章节**归入卷下**，与新建卷是两回事。混在一起会报出
「建立卷层级 16 个」，而侧栏只有 2 卷。拆出 `ChangedLevel` 后：
「章节归入卷层级 14 章」+「建立卷层级 2 个」，与侧栏一致。

### 「将做什么」曾经漏报软件会自动做的事

卷层级由对齐过程内部建立（`Apply` 的 `buildVolumeLevels`），不进分类栏，用户却在
「实际变化」里看到它——两个数字对不上。现在逐卷列出并标注**自动**、不给复选框：
它不是可选项，而是这次修复的一部分。`RepairReportItem.Automatic` 承担这个标记。

### 其余三处

| 问题 | 根因 | 修法 |
|---|---|---|
| 更新按钮被挤出窗口 | 设置窗固定 780 高、全窗无滚动；`UpdateCard` 在检测到版本后展开，被 `TabControl` 裁掉 | 只给「更新与关于」页套 `ScrollViewer`（其它页用星号行自适应高度，套滚动会被压扁） |

| 书源只能选一个、不能预览 | 真正收敛成一个的是 `ReferenceCatalogInput.Pick` 静默只留最大的一份；书源窗口确实没有预览/打开能力 | 列出落选候选及各自目录条数；新增「预览目录」与「浏览器打开」，后者复用 `BuildSearchUri` |

### 关于默认全选

「除目录外章节外全选」在实现上其实**已经成立**：`DefaultSelection` 覆盖的四类动作
（`AddChapter` / `Retitle` / `RemoveDuplicate` / `DemoteExtra`）正是所有可能
`Recommended == true` 的类型，各自的条件恰好对应三条红线。补了测试把它钉死，
没有改 `DefaultSelection` 本身。

### 本轮验证

Core **424 通过**、Desktop **127 通过**。真实书稿渲染核对（`work/repair-review-capture`，
示例书稿已加入两卷以覆盖卷层级）：19 项 4 类，侧栏与实际变化的数字自洽。

## 9. 本轮之后：左栏改成「改动清单」

### 用户的原话与它指出的错

> 「其实我的意思是把这实际应用也放到左边的分栏里，这样才合理啊，谁会来下面看这一堆东西？
> 用户需要清晰的知道到底变了什么，能明白吗。」

上一轮我把「实际变化」清单放在**右栏明细的末尾**（`_detailItems` 之后），并且只描述**当前
选中的那一类**。两处都错：

1. 位置——它是整套界面里唯一回答「这次修复到底改了什么」的东西，却放在最没人往下滚的地方；
2. 范围——一次只显示一类，用户要逐类点开才拼得出全貌，而全貌正是他问的。

### Core：让变化自己说明它是哪个动作造成的

窗口原先靠**按行号反查**把变化映射回动作，这条路在关键行上必然失败：条目被并回正文时，
变化报在标题行上，而那个动作在同一行下换了标题，于是本该带复选框的行没有复选框，
用户无法取消它。这次不再补猜，改由知道答案的一侧直接给出：

- `ReferenceAction.Key`（`Kind|Line|Title`）——动作的稳定标识；
- `RepairChange.ActionKey` ——造成这条变化的动作；
- `RepairChange.ActionKind` ——**动作类别**；
- `RepairIntegrity.DescribeWithActions(plan, after, before)` ——装配以上三者。

`ActionKind` 不是冗余：`RemovedEntry` 这一种变化既可能来自「标题并回正文」（`DemoteExtra`），
也可能来自「移除重复正文」（`RemoveDuplicate`），只看变化种类无法归类，而这两件事该出现在
改动清单的不同组里。**上一轮那个失败的 `ActionFor` 反查就是在这一点上反复修不对的。**

自动类的变化（重建卷层级、层级变化、正文重新分配）**不带动作**，`ActionKind` 为 null ——
它们无论如何都会发生，把它们做成可取消的选项是撒谎。

### UI：左栏 = 改动清单，右栏 = 说明

左栏现在是一行一个**改动类别**，直接可勾选：

```
✓ 标题改按目录写法            2/2
   ☑ 第 43 行 第13章 余烬
   ☑ 第 45 行 第14章 回声
✓ 标题并回正文                1/1
   ☑ 第 41 行 番外 主角的人物卡
● 建立卷层级                  2 卷
   自动 第 1 行 第一卷 风起
   自动 第 20 行 第二卷 云涌
```

- 分组**固定存在**（即使当前为 0），只在数字变化时把有内容的排到前面，勾选框跟着行一起移动，
  从不重建——列表不会在用户手底下重排，勾选也不会被刷新撤销。
- 「自动」的行没有方框，且该类显示**纯数量**（`2 卷`）而不是分数（`0/2`）：
  `0/2` 会被读成「这两卷不会发生」，而它们一定会发生。
- 右栏：未选中时说明这次修复将做什么；点任意一行/一个分组，换成那一项的说明；
  底部仍是两个**不是改动**的目录事实（参考目录未匹配、疑似公告）。

### 这一轮踩到的四个坑（都值得记住）

| 现象 | 真正的原因 |
|---|---|
| 左栏数量永远是 `0/…`，勾选明明在 | `Refresh()` 在**重建行之前**读 `SelectedActions()`，而复选框就是那份记录：读的时候它们还不存在，于是每次都把选择读成空。改为重绘后再读 |
| 头部数字停在 `0`，与边上的勾选冲突 | `CheckBox` 构造时赋 `IsChecked` 会触发 `Checked` → 重入 `Refresh()`，被防重入标志提前挡掉，于是统计停在**第一次**（空选择）的值。改为构造期间挂起事件（`_building`） |
| 「并回正文」的项出现在「移除章节项」组 | 变化种类不足以定组，见上文的 `ActionKind` |
| 第一版改动清单只有 1 个复选框 | 不是 bug：`AddChapter@0`（目录有、原文中定位不到行）**不产生任何树变化**，因此没有可勾选的行。见 §11 第 1 条 |

### 验证

Core **431 通过**、Desktop **128 通过**。新增测试：

- Core `RepairChangeAttributionTests`（7 个）：动作键稳定；补齐/改名/并回/去重各自指向造成它的
  动作；**自动类变化不带动作**；窗口手里的每个键都能在计划里解析（这是窗口赖以工作的不变量）。
- Desktop 新增 1 个：自动类分组不显示分数。已有的 3 个断言按新结构改为按名字读统计块。

`标题改按目录写法 2/2`、`标题并回正文 1/1`、`建立卷层级 2 卷`、`章节归入卷层级 14 章`。

## 10. 本次没做的事

1. **`AddChapter@0`（目录有、原文中定位不到行）不出现在改动清单里。** 它不产生任何树变化，
   所以没有可勾选的行，只在头部的「章需你核对」和「参考目录未匹配」组里体现。
   在用户那本 385 章的书上不算问题（能定位的都进了清单），但严格说这是个缺口：
   真实书稿里若有大量无法定位的章，用户在改动清单里看不到它们。要做的话，
   应当是一组「目录有、原文没找到——需人工核对」，且**默认不勾选**、不产生变化。
2. 交接文档 §4 的其余待办原样未动：Gitee 源、更新包 SHA-256 校验、公告通道。
3. 「疑似公告」目前**不带复选框**（它们本来就无法应用）。若日后想让用户手动把某个
   公告标记为正文，那是一次新的取舍，不属于本次范围。
4. `RepairReviewWindow` 的 `_verified` 门禁只覆盖「来源与文件对不上」一种情况，
   与旧窗口一致。
5. **AtomGit 不提供附件 size**，所以那条路上连字节数都校验不了（GitHub 那条有 size，
   但也只比字节数）。交接文档 §4 第 4 条现在更值得做了。
6. **AtomGit 的时间字段实际是 UTC**（`published_at` 报 `09:47:15Z`，而 release 创建于北京时间
   17:47:15）。本次不影响"发现新版本"，但按版本时间对比或展示时要留意这 8 小时。
