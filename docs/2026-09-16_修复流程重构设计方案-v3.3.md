# 修复流程重构设计方案 v3.3（协议冻结）

> 状态：**冻结稿**。本版之后停止迭代，进入 Phase 0 / Phase 1 实现
> 前身：v3.2《修复流程重构设计方案 v3.2》（本仓库 `docs/2026-09-16_修复流程重构设计方案-v3.2.md`）及其前序版本
> 本版性质：**增量补丁**。v3.2 未经修正的部分继续有效，本文只写差异
> 变更来源：外部 v3.2 评审意见（9 条）；全部采纳，其中 1 条需补强

## 0. 本版摘要

v3.2 的架构不再改动。v3.3 补两个状态机的**数学前提**，并把 v3.2 已提出的理念落到类型系统：

**两个 P0（状态机前提，不是新架构）**

1. **事务分界线由磁盘事实决定，不由 journal 枚举决定。** 修正 v3.2 §2.3 与 §3.2 之间的自相矛盾：`TempWritten` 同时被两节按两套规则解释。
2. **任何 `SourceEditTransaction` 都必须真正改变源字节。** 否则 `BaseSha == ExpectedNewSha`，恢复矩阵退化为不可判定。

**七条 P1（类型与验证器落地）**

3. `SourcePatch == null` 直接由 `Operations.Count == 0` 派生，不由 `Outcome` 反推。
4. `RepairEffect` 改为真正合法的 C# 判别类型（v3.2 的 enum 携带 payload 不可实现）。
5. 新增 Proposal 级 `BodyOwnershipValidator`。
6. `ActionId` 改为 executable semantic payload 指纹。
7. manifest 补 `SourceIdentity` / `BaseSnapshotRef` / `LandingMode`。
8. read-back 不称 durability proof。
9. `RestoreTransaction` 定义 `RestoreTargetPolicy`。

**结论：v3.2 → v3.3 只是补丁，不做 v4；本版即可作为实施依据。**

## 2. P0：物理提交状态与事务分界线

### 2.1 v3.2 的矛盾

**v3.2 §2.3 写：**

> `PreCommitValidation`（状态 ∈ `Prepared` / `BackupCreated` / `TempWritten` 且源未替换）

**v3.2 §3.2 又写：**

> `TempWritten` + `disk = ExpectedNewSha` → 视为 replace 已成功 → roll-forward

同一个 `TempWritten`，一处划入 PreCommit，一处划入 PostCommit roll-forward。

评审的判断准确：

> 实现者若分别按这两节实现，恢复路径就会分叉。

而且 v3.2 §2.3 的括号里补了「且源未替换」这个条件——说明我当时已经意识到 journal 状态不足以判定，但仍然把 journal 枚举写成了主判据。这是本末倒置。

### 2.2 修正：两层状态分离

**第一层：物理提交状态（由磁盘事实唯一决定）**

```csharp
public enum PhysicalCommitState { Base, Expected, Conflict }

public static PhysicalCommitState Classify(string currentSha,
                                           string baseSha, string expectedNewSha)
{
    if (currentSha == baseSha)        return PhysicalCommitState.Base;
    if (currentSha == expectedNewSha) return PhysicalCommitState.Expected;
    return PhysicalCommitState.Conflict;
}
```

**前提硬不变量**（见 §3）：

```text
BaseSha != ExpectedNewSha
```

违反此前提时 `Classify` 不可用，因此**不得创建 `SourceEditTransaction`**。

**第二层：恢复判定**

```text
PhysicalCommitState == Base     → PreCommitValidation
PhysicalCommitState == Expected → PostCommitRecoveryValidation
PhysicalCommitState == Conflict → 禁止自动处理
```

**`journal.State` 的唯一职责**：

> 描述应用记录的逻辑执行阶段，用于与磁盘真实状态**交叉验证**，判断二者是否构成合法组合。

它**不是**事务真相。

### 2.3 修正后的正式表述

> **真正的事务分界线是磁盘从 `BaseSha` 变成 `ExpectedNewSha`，而不是 journal 枚举值从 `TempWritten` 变成 `SourceReplaced`。**
>
> `SourceReplaced` 只是应用对这件事实的持久化确认。它可能尚未写入（崩溃），也可能被错误提前写入（此时磁盘状态会把它判为非法组合）。

### 2.4 v3.2 §2.3 修订

原：

```text
**`PreCommitValidation`**（状态 ∈ `Prepared` / `BackupCreated` / `TempWritten` 且源未替换）
```

改为：

```text
**`PreCommitValidation`**（`PhysicalCommitState == Base`）
三 fingerprint 全部必须匹配。此判定与 journal.State 无关。
journal.State 若 ≥ SourceReplaced 而物理状态为 Base，属非法组合 → Conflict。
```

原：

```text
**`PostCommitRecoveryValidation`**（状态 ∈ `SourceReplaced` / `DocumentReloaded` / `StateMigrated`，
且 CurrentSourceSha256 == manifest.ExpectedNewSha256）
```

改为：

```text
**`PostCommitRecoveryValidation`**（`PhysicalCommitState == Expected`）
journal.State 只需 ∈ { TempWritten, SourceReplaced, DocumentReloaded, StateMigrated }
即为合法组合。TempWritten 是合法的——journal 只是落后于磁盘事实。
```

## 3. P0：空 / no-op `SourcePatch` 禁止进入事务

### 3.1 v3.2 隐含了一个未声明的前提

v3.2 §3.2 恢复矩阵的全部判别力依赖：

```text
BaseSha != ExpectedNewSha
```

否则 `Disk = BaseSha` 与 `Disk = ExpectedNewSha` 是同一个状态。

### 3.2 反例

若 `SourcePatch` 是 no-op：

```text
BaseBytes → Render → BaseBytes
→ ExpectedNewSha == BaseSha
```

此时：

```text
journal = TempWritten, disk = BaseSha
```

无法判断是：

```text
A. 尚未 replace
B. replace 已执行，但字节没有变化
```

整个恢复矩阵失去判别能力。评审这条 P0 成立。

### 3.3 补强：评审给的 Invariant 2 严格来说不成立

评审写：

> Invariant 2：进入 `SourceEditTransaction` ⇒ `ExpectedNewSha != BaseSha`

但评审在 §3.2 同时说「只有满足 `SourcePatch != null`、`Operations.Count > 0`、`ExpectedNewSha != BaseSha` 三者」才允许创建事务——这三者是**并列条件**，意味着评审也承认前两者不蕴含第三者。

确实不蕴含。反例：

```text
ReplaceOriginalLine(Line = 5, ExpectedOldText = "第一章 开始", NewText = "第一章 开始")
Operations.Count == 1，但渲染后字节不变
```

所以正确的表述是把「三重条件」写成一个合取式，且**第三条必须由渲染结果验证**，而不是由前两条推导：

```text
EnterSourceEditTransaction
  ⇔ SourcePatch != null
  ∧ SourcePatch.Operations.Count > 0
  ∧ SHA256(Render(BaseSnapshotBytes, SourcePatch)) != BaseSnapshotSha256
```

**三重条件是合取，缺一不可。** 前两条是必要条件（结构上非空），第三条是充分保证（语义上真的改变了字节）。第三条是唯一真正保证恢复矩阵可判定的条件。

### 3.4 no-op 的处置：Normalizer 负责剔除

以下情况应在 `SourcePatchNormalizer` 阶段被移除或判非法：

```text
ReplaceOriginalLine(old, old)          → 移除
InsertLineAtAnchor("")                 → 非法（空标题不应产生插入操作）
同一行先 Replace 后被另一个动作 Replace 成原文 → 移除
最终渲染字节 == BaseBytes              → 整个事务不成立
```

规则：

> 任何进入 `SourceEditTransaction` 的 `SourcePatch` 都必然改变源字节。

### 3.5 不满足时的落地行为

```text
SourcePatch == null
  ∨ Operations.Count == 0
  ∨ ExpectedNewSha == BaseSha
        ↓
   NoSourceMutation
        ↓
   只提交 TreePatch
   不创建 SourceEditTransaction
   不创建 replace journal
   不进入 SourceReplaced 状态机
   UI 明确提示：本次修改不需要改动原文
```

**`LandingMode = TreeOnly` 天然落入这一类**，因此 TreeOnly 从不创建 `SourceEditTransaction`（与 v3.2 Phase 计划一致，此处正式确认为不变量）。

### 3.6 `RestoreTransaction` 的同类约束

恢复备份时若备份字节恰好等于当前源字节：

```text
CurrentSourceSha == BackupSha
→ ExpectedNewSha == BaseSha
→ 不创建事务
→ 提示「当前文件已与所选备份一致，无需恢复」
```

不要为了「让流程统一」而把一个 no-op 恢复硬塞进事务。

## 4. `SourcePatch` 存在的判据

### 4.1 v3.2 判据不完整

v3.2 §5.2 写：

```text
SourcePatch == null  ⇔  所有 Outcome == NotRequested 或 NotApplicable
```

**漏了全部 `Downgraded` 的情形**——此时同样不产生任何 `SourceOperation`，但判据不成立。

### 4.2 修正

```csharp
SourcePatch? sourcePatch =
    operations.Count == 0 ? null : new SourcePatch(...);
```

> `SourcePatch` 是否存在，由**实际编译出的 operation 集合**决定。

`SourceEffectOutcome` 只解释：

> 为什么这个动作有或没有对应的 `SourceOperation`。

不要让 Outcome 反过来决定全局 `SourcePatch` 是否存在。

### 4.3 数据流向

```text
正确方向：RepairDecision[] → Compile → Operations → SourcePatch?
错误方向：RepairDecision[] → Compile → Operations → Outcome[] → 反推 SourcePatch?
```

`Outcome` 是**解释性输出**，不是**判定性输入**。

## 5. `RepairEffect`：改为合法的 C# 判别类型

### 5.1 v3.2 的示例不可实现

v3.2 §7.2：

```csharp
public enum BodyOwnershipEffect
{
    None,
    Assign(IReadOnlyList<SourceSpan> Spans),   // ← C# enum 不能携带 payload
    Indeterminate
}
```

C# 的 `enum` 不能携带 `Assign(...)` 这样的 payload。文档若要直接指导实现，必须改成判别类型。评审对。

### 5.2 修正后的类型

```csharp
// ── TreeEffect ──
public abstract record TreeEffect;
public sealed record TreeEffectUnchanged                      : TreeEffect;
public sealed record TreeEffectInsertEntry(string SemanticId)  : TreeEffect;
public sealed record TreeEffectRetitleEntry(string SemanticId, string NewTitle) : TreeEffect;
public sealed record TreeEffectRemoveEntry(string SemanticId)  : TreeEffect;
public sealed record TreeEffectChangeLevel(string SemanticId, int NewLevel)     : TreeEffect;
public sealed record TreeEffectReassignBodyRanges(string SemanticId)            : TreeEffect;
public sealed record TreeEffectBuildVolumeNode(string SemanticId, int Level)    : TreeEffect;
public sealed record TreeEffectIndeterminate                  : TreeEffect;

// ── SourceContentEffect ──
public abstract record SourceContentEffect;
public sealed record SourceContentUnchanged                        : SourceContentEffect;
public sealed record SourceContentReplace(IReadOnlyList<ReplaceIntent> Replacements) : SourceContentEffect;
public sealed record SourceContentDelete (IReadOnlyList<SourceSpan>     Spans)        : SourceContentEffect;
public sealed record SourceContentInsert (IReadOnlyList<InsertIntent>   Inserts)      : SourceContentEffect;
public sealed record SourceContentIndeterminate                    : SourceContentEffect;

// ── BodyOwnershipEffect ──
public abstract record BodyOwnershipEffect;
public sealed record BodyOwnershipUnchanged                        : BodyOwnershipEffect;
public sealed record BodyOwnershipAssigned(BodyAssignment Assignment) : BodyOwnershipEffect;
public sealed record BodyOwnershipIndeterminate                    : BodyOwnershipEffect;

// ── 聚合 ──
public sealed record RepairEffect(
    TreeEffect          Tree,
    SourceContentEffect Source,
    BodyOwnershipEffect Body);

public sealed record ReplaceIntent(int Line, string ExpectedOldText, string NewText);
public sealed record InsertIntent(SourceAnchor Anchor, string Text);
```

**命名修正**：`None` → `Unchanged`。

理由（评审提出，接受）：

```text
「没有正文」与「正文归属没有变化」不是同一个语义
```

### 5.3 `Indeterminate` 的强制作用

```text
RepairEffect.Source is SourceContentIndeterminate → 该动作在 EditSource 下禁用
RepairEffect.Body   is BodyOwnershipIndeterminate → 该动作在 EditSource 下禁用
```

实现层：`*Indeterminate` 是**必须显式书写**的类型。新增动作若忘记定义语义，编译器要求填这三个维度；填 `Indeterminate` 会被 `EditSource` 拒绝，而不是默认放行。

### 5.4 类型化后的额外收益

`SourceContentReplace` / `Delete` / `Insert` 携带具体意图后，`RepairEffect` 不再只是「类别描述」，而是**可执行的语义载荷**：

```text
RepairEffect.Source  →  可直接构造 SourceOperation
RepairEffect.Body    →  可直接构造 BodyAssignment
RepairEffect.Tree    →  可直接构造 TreeMutation
```

这使 `TreePatch` / `SourcePatch` 的生成成为 `RepairEffect[]` 的**确定性投影**，而不是另一套独立逻辑。三元组从「校验用的元数据」升级为「编译的中间表示」。

## 6. Proposal 级 `BodyOwnershipValidator`

### 6.1 问题

单动作有合法 `BodyAssignment`，不代表组合后整体合法。评审的反例：

```text
Action A: BodyAssignment = 100..150
Action B: BodyAssignment = 140..200
```

单独都合法；组合后 `140..150` 同时被两个章节拥有。反向也可能出现本应保留的行 `owner count == 0`，形成正文泄漏。

### 6.2 与现有 `RepairIntegrity.Coverage` 的关系

现有 `RepairIntegrity.Verify` 已经强制 coverage 守恒，但它的语义是**行不被凭空丢失**（修复前后的行集合相等）。它**不检查**「每行恰好归属一个章节」——章节树本来就允许多个 `ContentRanges` 有重叠。

所以 `BodyOwnershipValidator` 不是重复，而是**第二层全局约束**：

| 验证器 | 层次 | 语义 |
|---|---|---|
| `RepairIntegrity.Verify` | 行集合 | 没有行凭空消失 |
| `BodyOwnershipValidator` | 归属 | 每行 owner count 唯一 |

两者必须**交叉验证**。

### 6.3 正式不变量

在 `RepairProposal + RepairDecision[]` 编译完成后、且 `LandingMode` 已知时验证：

```text
对 BaseSource 的每一行 L（空白 separator 行除外）：

    ownerCount(L) + removedCount(L) == 1

其中：
    ownerCount(L)   = 最终树中包含 L 的 ContentRange 数量
    removedCount(L) = L 是否在本次决定的 RemovedLines 集合中（0 或 1）
```

**推导出的两条约束**：

```text
禁止：ownerCount(L) > 1                              （正文重叠）
禁止：ownerCount(L) == 0 ∧ removedCount(L) == 0      （正文泄漏）
允许：ownerCount(L) == 0 ∧ removedCount(L) == 1      （该行被明确移除）
```

### 6.4 为什么用 `RemovedLines` 而不是「源字节里是否还在」

关键区别：

```text
TreeOnly 下 RemoveDuplicate：
    副本行物理上仍在源文件里
    但它被明确排除在语义之外
    → ownerCount = 0, removedCount = 1   ✓

EditSource 下 RemoveDuplicate：
    副本行物理上被删除
    → ownerCount = 0, removedCount = 1   ✓
```

**两种模式的判定完全相同**，这正是 canonical 等价所需要的。若改用「源字节里是否还在」，两种模式会得到不同结果——那是把落地实现混进了语义判定，正是 v3.2 §5.1 已经批判过的错误。

`RemovedLines` 在 v3 中已由 `RepairIntegrity` 保存，此处复用，不新增状态。

### 6.5 验证时机与失败处置

```text
Phase 4（内存）：
    编译后立即验证；违规 → 编译失败，预览期报错，不进入 Prepare Commit

Phase 5（事务）：
    物化后再次验证；违规 → PostCommitRecoveryValidation 失败 → Conflict
```

## 7. `ActionId`：executable semantic payload 指纹

### 7.1 v3.2 公式已被新模型淘汰

v3.2 §10.2 沿用 v3.1 的：

```text
ActionId = H(ActionKind, SemanticTarget, SourceLocator/Anchor, DesiredValue, BasisIdentity)
```

但 v3.2 新增了多个**会改变实际执行结果**的字段：

```text
BodyAssignment
RemovedHeadingTextDisposition
NewLevel
RepairEffect
```

它们若不参与 `ActionId`，就会发生语义碰撞。评审的反例：

```text
两个 InsertHeading
    Title 相同、Anchor 相同、SemanticTarget 相同
    BodyAssignment A = 100..120
    BodyAssignment B = 100..140
→ 相同 ActionId，但生成不同章节树
```

### 7.2 修正：不再手工列字段

```text
ActionId = SHA256(
    ActionSchemaVersion
  ‖ CanonicalExecutableActionPayload
  ‖ BasisIdentity
)
```

`CanonicalExecutableActionPayload` 包含**所有会影响以下结果**的字段：

```text
TreePatch
SourcePatch
BodyOwnership
```

**明确排除**：

```text
UI 文案
RepairEvidence.Description
显示排序
纯提示字段
```

### 7.3 实现层要求

`CanonicalExecutableActionPayload` 必须是**可枚举、可测试**的：

```text
1. 提供 Canonicalize(RepairAction) → byte[]，字段顺序固定、编码固定
2. 提供单元测试：新增执行语义字段时，若忘记加入 payload，
   ActionId 碰撞测试必须失败
3. ActionSchemaVersion 在 payload 结构变化时递增
```

第 2 条是关键——它把「以后别漏」从约定变成回归测试。

### 7.4 连带影响

`ProposalId`（v3.2 §10.2）定义为 `H(BaseVersion, Basis, PlannerSchemaVersion, OrderedActionIds)`，其中 `OrderedActionIds` 由新的 `ActionId` 构成，因此自动继承修正，无需改动。

## 8. Manifest 进一步自足

### 8.1 v3.2 manifest 仍缺恢复核心身份字段

v3.2 §4.3 的 `RepairExecutionManifest` 已含 `ExpectedNewSha256`、`BaseSnapshotSha256`、`TreePatch`、`SourcePatch`、`ExpectedCanonicalResult`、`Decisions`，明显优于 v3.1。但仍缺三项。

### 8.2 补充定义

```csharp
public sealed record RepairExecutionManifest(
    int SchemaVersion,
    string TransactionId,
    string ProposalId,
    RepairBaseVersion BaseVersion,
    IReadOnlyList<RepairDecisionSnapshot> Decisions,
    TreePatch TreePatch,
    SourcePatch? SourcePatch,
    CanonicalChapterModel ExpectedCanonicalResult,
    string ExpectedNewSha256,
    string BaseSnapshotSha256,
    NewLinePolicy NewLinePolicy,
    // ── v3.3 新增 ──
    SourceIdentity Source,
    BackupSnapshotRef BaseSnapshot,
    RepairLandingMode LandingMode);
```

**`SourceIdentity`**——判断当前路径是否仍指向同一源对象：

```csharp
public sealed record SourceIdentity(
    string NormalizedAbsolutePath,
    string? VolumeIdentity,      // Windows: volume serial
    string? FileIdentity);       // Windows: FileId（NTFS file index）
```

`FileIdentity` 在 Windows 上通过 `GetFileInformationByHandle` 取得。它解决一个真实问题：用户把 TXT 换成另一个同名文件后，仅凭路径无法察觉，而 `FileIdentity` 能发现。

**`BaseSnapshotRef`**——仅 `BaseSnapshotSha256` 不足以**定位** snapshot 字节：

```csharp
public sealed record BackupSnapshotRef(
    string SnapshotId,
    string RelativePath,         // 相对备份根
    string ContentSha256);
```

恢复时必须能打开这个文件，而不是只知道它的哈希。

**`LandingMode`**——审计用户当时的选择：

```text
TreeOnly | EditSource
```

**为何必需**：当 `SourcePatch` 最终为 `null` 时，单靠 `SourcePatch == null` **无法反推**用户原本选的是哪种模式。没有它，收据无法忠实记录「用户选的是 EditSource，但本次没有任何动作需要改原文」与「用户选的就是 TreeOnly」这两种不同情形。

## 9. read-back 不是 durability proof

### 9.1 v3.2 的表述过强

v3.2 §4.2 步骤 I：

```text
I. 重新读取 manifest，校验字节 == 刚写入的字节（durable 确认）
```

评审指出重新读取只能证明：

> 当前文件系统视图返回了相同字节。

不能证明：

> 断电以后这些字节一定仍然存在于持久介质。

因为 read 可能直接命中文件缓存。表述应收紧。

### 9.2 修正后的步骤与术语

```text
H. Write + Flush(flushToDisk: true) manifest
I. Read-back integrity check
   —— 校验读回字节 == 写入字节
   —— 只证明「写入内容没有明显损坏或错文件」
   —— 不证明持久性；持久性由 H 的 flush 负责
J. Replace source
```

**用词规范**（本文档与实现注释统一遵守）：

| 不写 | 改写 |
|---|---|
| durable 确认 / durability proof | flush-to-disk 后的 read-back integrity check |
| read-back 证明已持久化 | read-back 只做完整性检查 |

**实现要求**：

```csharp
using var fs = new FileStream(path, FileMode.Create, FileAccess.Write, FileShare.None,
                              bufferSize: 4096, FileOptions.WriteThrough);
// ... 写入 ...
fs.Flush(flushToDisk: true);
```

### 9.3 目录项的边界

Windows 上**目录项是否已持久化无法通过 read-back 间接推断**。`Flush(true)` 保证文件数据刷盘，但目录项元数据的持久化边界不由该 API 定义。

**v3.3 处置**：

- 不声称目录项已经 durable
- 不通过 read-back 推断目录项状态
- 若将来确实需要更强的保证，单独评估 `MoveFileEx(MOVEFILE_WRITE_THROUGH)` 或 NTFS 事务，**不在此处预设结论**
- journal 目录的创建本身用 `Directory.CreateDirectory` + 事后存在性检查

诚实的能力边界 > 虚假的保证。

## 10. `RestoreTransaction` 的产品语义

### 10.1 v3.2 定义不完整

v3.2 §11.2：

```text
RestoreTransaction = SourceEditTransaction 的特化（源 = backup bytes）
```

这只定义了**机制**，没定义**产品语义**：恢复备份时，到底恢复「TXT 字节」还是「完整书稿状态」？

### 10.2 两种合法语义

**A. `SourceOnly`**——只恢复 TXT

```text
backup source bytes → 覆盖当前 source
→ 丢弃当前 ChapterTree
→ 对恢复后的 source 重新识别
```

不保证恢复当时的 `ChapterTreePlan`、人工章节结构、`RecognitionSettings`。

**B. `FullBookState`**——恢复完整书稿状态

snapshot 必须同时保存：

```text
Source bytes
ChapterTreePlan
相关 project metadata
（可选）RecognitionSettings
```

恢复后才能声称「回到当时的完整书稿状态」。

### 10.3 定义

```csharp
public enum RestoreTargetPolicy { SourceOnly, FullBookState }
```

`RestoreTransaction` 复用相同的 preflight / manifest / journal / replace / roll-forward / `SourceVersionTransition`，**不新增协议**；canonical target 与 tree 恢复方式由 `RestoreTargetPolicy` 决定。

### 10.4 与现有备份结构的关系

v3 §12.2 的备份目录已有 `baseline/` 与 `snapshots/`，只存源字节。`FullBookState` 需要**扩展 snapshot 的内容**：

```text
<书稿目录>/.easypub/backup/<原文件名>/
    manifest.json
    baseline/<sha256>.bak
    snapshots/<sha256>.bak
    snapshots/<sha256>.tree.json          ← FullBookState 新增
    snapshots/<sha256>.recognition.json   ← FullBookState 新增（可选）
    receipts/...
```

**Phase 2 的影响**：Phase 2 的备份层应**预留**这两个文件的位置与 `manifest.json` 中的对应字段，即使当时不写入内容。否则 Phase 5 开放 `FullBookState` 时需要迁移既有备份目录格式。

### 10.5 默认值

**待决**：`RestoreTargetPolicy` 的默认值。

倾向 `SourceOnly` 为默认（行为可预期、不需要额外快照内容），`FullBookState` 作为明确的高级选项。**但不在此处定死**，Phase 5 前由实测决定。

## 12. 恢复判定模型（最终版）

```text
┌─ 第一步：磁盘事实 ────────────────────────────────┐
│  前提：BaseSha != ExpectedNewSha（硬不变量 2）     │
│                                                    │
│  CurrentSha == BaseSha        → Physical = Base    │
│  CurrentSha == ExpectedNewSha → Physical = Expected│
│  else                         → Physical = Conflict│
└────────────────────────────────────────────────────┘
                        ↓
┌─ 第二步：结合 journal.State 交叉验证 ─────────────┐
│                                                    │
│  Physical = Base                                   │
│      journal ∈ {Prepared, BackupCreated, TempWritten}│
│          → pre-commit 区域                         │
│          TempWritten 可安全继续 replace，但必须先： │
│              · 重新验证三 fingerprint               │
│              · 重新渲染 expected bytes              │
│              · 验证 == manifest.ExpectedNewSha256   │
│      journal ≥ SourceReplaced                      │
│          → Conflict（journal 声称已提交，磁盘没有） │
│                                                    │
│  Physical = Expected                               │
│      journal ∈ {TempWritten, SourceReplaced,       │
│                 DocumentReloaded, StateMigrated}   │
│          → PostCommitRecoveryValidation            │
│          → frozen manifest roll-forward            │
│          → 不重新检查 planner 的 Tree/Recognition   │
│                                                    │
│  Physical = Conflict                               │
│      → 一律人工处理，生成诊断                       │
└────────────────────────────────────────────────────┘
```

**与 v3.2 §3.2 恢复矩阵的关系**：矩阵继续有效，但**第 3.2 节的 `TempWritten + ExpectedNewSha → roll-forward` 现在有了正确的解释**——它不是特例，而是 `Physical = Expected` 的一般规则。矩阵从「journal 为主键」变为「物理状态为主键，journal 为交叉验证」。

### 12.1 Conflict 诊断内容

进入 `Conflict` 时生成用户可见诊断（v3.2 §15 已定）：

```text
journal.State
期望的 BaseSha / ExpectedNewSha
磁盘实际 SHA
判定依据（哪一条规则命中）
建议动作（人工核对 / 从备份恢复 / 联系支持）
```

## 15. 结论与冻结声明

v3.2 的架构经本轮复核继续成立。v3.3 补的是两个状态机的数学前提，而非新架构：

```text
1. 物理提交状态由磁盘 SHA 决定，不由 journal 枚举决定
   → 解决 TempWritten + ExpectedNewSha 的判定归属

2. 任何 SourceEditTransaction 都必须真正改变源字节
   → 保证 Base / Expected / Conflict 三态可唯一判定
```

其余七条把 v3.2 已提出的理念落到类型与验证器：`RepairEffect` 判别类型化、`BodyOwnershipValidator`、`ActionSemanticFingerprint`、manifest 自足、read-back 术语、`RestoreTargetPolicy`。
