## 4. 新发现的真实缺陷：第六卷 100 行重复标题泄漏进正文

### 4.1 现象

`缺陷样书.txt` 第 1904–2498 行是第六卷，每章形如：

```
第九章 己9 尘落余温      ← 标题行（识别为章节条目）
第九章 己9 尘落余温      ← 紧邻完全相同的标题行
(空行)
正文段落一（第九章 己9 尘落余温）。
正文段落二（第九章 己9 尘落余温）。
(空行)
```

### 4.2 测量（`-- census` 探针）

```
全书「与上一行完全相同」的非空行：100 行
其中落在某个正文范围里（因而会输出到成品）：100 行，分布在 100 章
默认移除清单 160 行；其中属于上述重复行的：0 行
→ 成品仍会输出 100 行重复标题
```

每章的正文范围都以重复行**开头**：

```
第一章 己1 尘落尘落（正文范围 1904–1908）  ← 重复行 1904
第二章 己2 尘落收网（正文范围 1910–1914）  ← 重复行 1910
第三章 己3 尘落对坐（正文范围 1916–1920）  ← 重复行 1916
…（每章 5 行，共 100 章）
```

### 4.3 根因

`ChapterEditingDocument.cs:107-108` 在识别阶段把紧邻重复的标题行 `continue` 掉：

```csharp
if (index > 0 && string.Equals(lines[index - 1].Trim(), title, StringComparison.Ordinal)
    && chapterRegex.IsMatch(rawLine)) continue;
```

这一行因此**不会成为章节条目**——「同名重复标题 0 组」是这么来的，这部分是对的。

但它**仍然是源文件里的一行字节**，而正文范围的分配从「标题行的下一行」开始，于是这一行被算进了本条的正文范围。

> **合并发生了，但只发生在"章节条目"这一侧，没有发生在"正文范围"这一侧。**

### 4.4 影响

- 成品里每章标题出现两次：一次是导航标题，一次是正文首行。
- `RepairIntegrity` 的行守恒检查**通过**（100 行确实被认领了），所以这个错误不会被现有任何验证器发现。
- 用户决策 4 是「第六卷重复标题行直接删除」，目前一个字都没删。

### 4.5 为什么现有测试没抓到

`RepairIntegrity` 校验的是「行有没有凭空消失」，不是「行有没有出现在不该出现的地方」。而 v3.3 §6 新增的 `BodyOwnershipValidator`（`ownerCount + removedCount == 1`）同样会放过它——因为该行**恰好有一个 owner**。这是 owner 唯一性之外的第二个问题：**owner 是错的**。

> 由此得到一条对 v3.3 §6 的补充：`BodyOwnershipValidator` 还需要一条规则 ——
> **被识别阶段合并掉的重复标题行，不得被任何正文范围认领。**
> 否则「每行恰好归属一个章节」这个不变量成立，而成品仍然是错的。

### 4.6 处置

留到 Phase 1 一并修（它属于「链路合并」的一部分：正文范围的分配要显式化）。修法与验收见 Phase 1 报告。

### 7.2 Phase 1 修掉的两处缺陷

**缺陷 A：第六卷 100 行重复标题泄漏进正文（§4）**

`ChapterTree` 新增 `SkipRepeatedHeadingRun`：正文范围从紧邻重复标题组的最后一行之后开始，
而不是从标题行的下一行开始。

- 只跳与标题行逐字节相同的连续行
- 上限 `MaximumRepeatedHeadingRun = 4`，避免病态文件吃掉整章正文
- 实测：`落在某个正文范围里` **100 → 0**
- 全部既有 Core 测试（447 个）通过，说明没有影响其他书的正文分配

**缺陷 B：修复确认窗在生产路径上整片空白**

`RepairReviewWindow.PreviewChanges()` 从复选框读当前选择，而构造函数第一次调它时复选框还没建
出来 —— 判据在它第一次被使用时必然为假，于是清单建成空的。

只有传 `previewDocument` 才走这条路径，而生产代码始终传它（`RunRepairReviewAsync` 传
`snapshot`），既有测试**全都不传**。所以这个分支从来没有被看过一眼。

| | 修复前 | 修复后 |
|---|---|---|
| 标题 | 本次**没有**需要应用的改动 | 本次将做 **6 类修改，共 109 项** |
| 左栏 | 全空，所有分组 0 | 收录章节 8/8、标题改按目录写法 69/69 … |
| `SelectedActions()` | 0 | 77 |

修法：复选框存在之前以 `plan.DefaultSelection` 为准（`_building` 标志）。
新增 `A_preview_document_draws_the_same_change_list` 把两条路径绑在一起。

> 这个缺陷是「每个阶段都必须用样书实测」这条要求的直接收益：只跑既有测试永远发现不了它。

**顺带修掉：`Progress<T>` 在无同步上下文线程上崩掉进程**

`RunRepairReviewAsync` 原用 `new Progress<string>(...)`。`Progress<T>` 捕获构造它的
`SynchronizationContext`，没有时就**退回线程池**，回调于是跑在错误线程上，碰第一个 UI 元素
即抛跨线程异常。按钮点击恰好有上下文所以从不发作；从测试宿主驱动就必崩。
改为 `DispatcherProgress` 显式编组 —— 不再依赖「谁调用了我们」。

### 7.3 判据 3 为什么只算半达成

`RemoveDuplicate` 仍然只移除**判定为副本**的那 160 行（第一卷 55 + 第二卷 105），
第六卷那 100 行没有进入移除清单。

这是**正确的**，不是遗留问题：

- 那 100 行在源文件里仍然存在（Phase 1 明确不改原文）
- 它们已经不被任何正文范围认领，所以**不会出现在成品里** —— 这才是用户能感知的部分
- 「从 TXT 里物理删掉这 100 行」属于改原文，是 Phase 6 的工作

所以 §6 判据 3 的表述需要修正：`移除行数` 在 Phase 1 之后仍应是 **160**，
它变成 260 是 **Phase 6** 的验收点。原判据把「成品不含」与「源文件已删」混为一谈了。
